# 통신 임베디드가 알아야 할 점

> 기준일: 2026-08-02
> 대상: Jetson/로봇 통신·상태·Mission·Command 구현 담당자
> 계약 버전: MQTT v2 (`tbs/v2`, `schema_version: "2.0"`)

이 문서는 임베디드팀이 웹 Backend와 연결할 때 놓치기 쉬운 규칙과 현재 구현의
확인 항목을 한곳에 모은 인계 문서다. Payload의 전체 필드 정의는
[`web/docs/final-mqtt-topic-schema-v2.md`](../../../web/docs/final-mqtt-topic-schema-v2.md)와
[`web/docs/mqtt-v2/schemas/`](../../../web/docs/mqtt-v2/schemas/)를 정본으로 삼는다.

## 1. 지금 가장 중요한 변경 두 가지

### 1.1 `zone_id`에는 형식 제약이 없다

- 웹의 `patrol_area.area_code`가 MQTT `START_MISSION.parameters.zone_id`로 전달된다.
- `zone_id`는 `A-01` 전용 값이 아니라 **불투명 문자열**이다.
- 영문·숫자·하이픈 조합을 가정하거나 정규식으로 검사하지 않는다.
- 로봇은 서버가 준 값을 수정·정규화·재계산하지 않고 Mission 동안 그대로 보존한다.
- Incident를 발행할 때 `location.zone_id`에 같은 값을 그대로 echo한다.
- Backend DTO·JSON Schema의 패턴 검증은 제거됐고,
  `V36__relax_zone_id_format.sql`이 기존 DB CHECK 제약 세 개를 제거한다.
- 배포 DB에 Flyway V36이 실제 적용됐는지는 별도로 확인한다.
- 과거 문서의 `A-01`, `^[A-Z]-[0-9]{2}$` 표기는 예시 또는 폐기된 제약이다.

즉, 아래와 같은 동작은 금지한다.

```python
# 금지: 값의 문자 구성에 업무 의미를 부여하지 않는다.
if not re.match(r"^[A-Z]-[0-9]{2}$", zone_id):
    reject_command()
```

현재 구현 위치:

- [`embedded/commands.py`](../../commands.py): START 시 받은 값을 그대로 저장
- [`embedded/events.py`](../../events.py): Incident에 저장된 값을 그대로 echo
- [`embedded/test/test_commands.py`](../../test/test_commands.py): 임의 문자열 보존 회귀 테스트

### 1.2 긴급정지 뒤 Mission은 버리지 않고 `PAUSED`로 보존한다

정상 복구 흐름은 반드시 다음 순서다.

```text
PATROLLING / RUNNING
  → EMERGENCY_STOP
SAFE_STOP / PAUSED
  → CLEAR_EMERGENCY_STOP
PAUSED / PAUSED
  → RESUME_MISSION
PATROLLING / RUNNING
```

세부 규칙:

1. `EMERGENCY_STOP`을 받으면 MQTT 응답보다 **모터를 먼저 정지**한다.
2. 실행 중 Mission ID와 `zone_id`, 시작 시각, 집계값은 지우지 않는다.
3. Robot mode를 `SAFE_STOP`, reason을 `REMOTE_ESTOP`으로 바꾼다.
4. Mission이 `RUNNING`이었다면 `PAUSED`로 바꾸고 같은 Mission ID의
   `MISSION_PAUSED` Event를 한 번 발행한다.
5. 이미 `PAUSED`였으면 `MISSION_PAUSED`를 중복 발행하지 않는다.
6. `SAFE_STOP`에서 `RESUME_MISSION`이 바로 오면
   `REJECTED/SAFETY_CONDITION_NOT_CLEARED`로 거절한다.
7. `CLEAR_EMERGENCY_STOP`은 안전 잠금만 해제한다. 활성 Mission은 `PAUSED`로
   유지하며 자동으로 바퀴를 움직이지 않는다.
8. 이후 별도 `RESUME_MISSION`이 성공해야 `PATROLLING/RUNNING`으로 전환하고
   `MISSION_RESUMED`를 발행한다.

`commands/result`의 완료만 보내고 `MISSION_PAUSED`를 생략하면 Backend Mission은
`RUNNING`에 남는다. 그러면 Backend가 PAUSED Mission을 찾지 못해 재개 명령 생성이
막힌다. Safety Event나 State Payload는 Mission Event를 대신하지 않는다.

### 1.3 Mission 상태 사이클과 종료 의미를 구분한다

웹과 임베디드는 다음 상태 사이클을 같은 의미로 사용한다.

```text
새 임무 배정
  CREATED → READY → START_MISSION → RUNNING

일시정지와 재개
  RUNNING → PAUSE_MISSION → PAUSED
  PAUSED → RESUME_MISSION → RUNNING

긴급정지 복구
  RUNNING → EMERGENCY_STOP → SAFE_STOP / PAUSED
  → CLEAR_EMERGENCY_STOP → PAUSED / PAUSED
  → RESUME_MISSION → PATROLLING / RUNNING

정상 종료
  RUNNING → COMPLETE_MISSION → MISSION_COMPLETED → COMPLETED

관리자 취소
  READY·RUNNING·PAUSED → CANCEL_MISSION → MISSION_CANCELLED → CANCELLED
  SAFE_STOP 중 취소해도 로봇은 SAFE_STOP을 유지

오류 종료
  RUNNING 또는 PAUSED → MISSION_FAILED → FAILED
```

핵심 규칙:

1. 화면의 **임무 완료**는 정상 수행 종료이므로 `COMPLETED`가 되어야 한다.
2. `CANCEL_MISSION`은 정상 종료가 아니라 **임무 취소**이며 결과는 `CANCELLED`다.
3. `FAILED`는 복구 불가능한 임무 오류 종료다.
4. `COMPLETED`, `CANCELLED`, `FAILED`는 모두 종료 상태이며 같은 Robot에 새 Mission을
   배정할 수 있다.
5. `PAUSED`는 종료 상태가 아니다. Mission ID와 `zone_id`를 유지하고
   `RESUME_MISSION`으로 다시 `RUNNING`이 될 수 있다.
6. `READY`, `RUNNING`, `PAUSED` Mission이 남아 있으면 같은 Robot에 새 Mission을
   배정하지 않는다.
7. 계획시간이 끝난 RUNNING Mission에 Backend가
   `SYSTEM/COMPLETE_MISSION`을 발행한다. 임베디드는 구동을 멈추고
   `MISSION_COMPLETED`를 발행해야 하며, Backend는 이 Event 전에 Mission을 거짓
   COMPLETED로 바꾸지 않는다.
8. `PAUSED`는 실행 상태이지 종료 결과가 아니다. 일반 일시정지와 긴급정지 모두
   `COMPLETE_MISSION`을 거부하고, `RESUME_MISSION`으로 `RUNNING`이 된 뒤에만
   정상 완료한다. `SAFE_STOP`은 반드시 먼저 `CLEAR_EMERGENCY_STOP`으로 해제한다.
9. `SAFE_STOP` 중 `CANCEL_MISSION`은 허용한다. Mission은 `CANCELLED`로 끝내되
   로봇은 계속 `SAFE_STOP`을 유지하고, 취소 명령으로 안전 정지를 해제하지 않는다.

`COMPLETE_MISSION`은 화면의 **임무 완료**, `CANCEL_MISSION`은 **임무 취소**로
분리한다. 두 명령 모두 Mission 보관함을 비우지만 발행 Event와 Backend 종료
상태가 다르다.

## 2. 식별자를 서로 바꾸어 쓰지 않는다

| 값 | 의미 | 임베디드 처리 |
| --- | --- | --- |
| `mqtt_id` | MQTT 외부 Robot 식별자 | Topic, Payload, username에 동일 값 사용 |
| `robot.uuid` | DB 내부 Robot UUID | 이미지 업로드용이며 MQTT `mqtt_id`와 별개 |
| `boot_id` | 현재 프로세스 부팅 세션 UUID | 프로세스 재시작 때 새로 만들고 단순 재접속에는 유지 |
| `seq` | 같은 `boot_id` 안의 공용 증가 번호 | State·Telemetry·모든 Event가 하나의 순번을 공유 |
| `command_id` | 서버가 발급한 명령 멱등 키 | 재수신해도 같은 동작을 다시 실행하지 않음 |
| `event_id` | Event 멱등 키 | 재전송할 때 절대 바꾸지 않음 |
| `mission_id` | START에서 받은 Mission 업무 코드 | 파싱하지 않고 활성 Mission 동안 보존 |
| `zone_id` | START에서 받은 Patrol Area 업무 코드 | 형식 검사 없이 그대로 보존·echo |

`mqtt_id`, MQTT username, Topic 경로의 Robot 값이 서로 다르면 안 된다. 내부 UUID를
Topic에 넣거나 `mqtt_id`를 이미지 업로드의 `robotId`로 보내지 않는다.

## 3. Topic·QoS·Retain

모든 Topic은 다음 prefix를 사용한다.

```text
tbs/v2/robots/{mqtt_id}/...
```

| 방향 | suffix | QoS | Retain | 주의사항 |
| --- | --- | ---: | :---: | --- |
| 로봇→서버 | `presence` | 1 | O | ONLINE Birth와 OFFLINE/LWT |
| 로봇→서버 | `state` | 1 | O | 연결 직후, 상태 변경 즉시, 최대 30초 주기 |
| 로봇→서버 | `telemetry` | 0 | X | 기본 5초 주기, 최신 표본 중심 |
| 로봇→서버 | `events/incident` | 1 | X | Outbox 저장 후 발행 |
| 로봇→서버 | `events/battery` | 1 | X | Outbox 저장 후 발행 |
| 로봇→서버 | `events/safety` | 1 | X | Outbox 저장 후 발행 |
| 로봇→서버 | `events/mission` | 1 | X | Mission DB 상태 전이의 정본 |
| 로봇→서버 | `commands/result` | 1 | X | ACK와 최종 Result를 분리 |
| 서버→로봇 | `commands/request` | 1 | X | 유일한 필수 하향 구독 Topic |

QoS·Retain은 [`embedded/comms/topics.py`](../../comms/topics.py)의 정책을 사용하고
호출부에서 임의로 덮어쓰지 않는다.

## 4. 연결·인증·Presence

- TLS는 필수다. 운영에서 평문 MQTT로 낮추지 않는다.
- 환경변수 핵심은 `MQTT_ID`, `MQTT_USERNAME`, `MQTT_PASSWORD`, `MQTT_HOST`,
  `MQTT_PORT`, `MQTT_CA_CERT`, `MQTT_CLIENT_ID`다.
- `MQTT_USERNAME`을 별도로 지정하더라도 `MQTT_ID`와 같아야 한다.
- 비밀번호, API Key, CA 원문을 Git·로그·스크린샷에 남기지 않는다.
- 첫 접속은 새 세션, 재접속은 기존 세션을 사용하며 Session Expiry는 3600초다.
- 재접속 백오프는 1→2→4→…→30초다.
- 연결할 때 Retained `ONLINE`을 다시 발행해 이전 OFFLINE을 덮는다.
- 비정상 종료는 Retained LWT `OFFLINE/UNGRACEFUL_DISCONNECT`로 표시한다.
- 정상 종료는 `OFFLINE/GRACEFUL_SHUTDOWN`을 발행한다.
- 같은 `mqtt_id`로 실제 Robot과 Mock Robot을 동시에 연결하지 않는다. 같은 Client ID가
  서로의 연결을 끊고 상태가 섞인다.

환경변수 예시는 [`embedded/scripts/orincar.env.example`](../../scripts/orincar.env.example),
실기 순서는 [`2026-08-01_1515_jetson-mqtt-v2-day7-runbook.md`](2026-08-01_1515_jetson-mqtt-v2-day7-runbook.md)를 참고한다.

## 5. 시간·순번·재전송

- 모든 시간은 ISO 8601 UTC `Z`로 보낸다.
- Robot 관측 시각과 전송 시각을 구분한다. 재전송한다고 `occurred_at`을 현재 시각으로
  바꾸지 않는다.
- Event Envelope는 `schema_version`, `event_id`, `mqtt_id`, `boot_id`, `seq`,
  `source_component`, `occurred_at`, `sent_at`, `ttl_sec`, `mission_id`를 계약대로 채운다.
- Event `ttl_sec`는 60~300초이며 현재 기본값은 300초다.
- Event 4종은 발행 전에 SQLite Outbox에 저장하고 PUBACK 뒤에만 전송 완료로 표시한다.
- 재전송할 때 `event_id`, `occurred_at`, `ttl_sec`, 본문은 유지하고 `sent_at`만 바꾼다.
- QoS 1은 중복 전달될 수 있다. 멱등 키를 새로 만들면 서버에서 새 Event로 저장된다.
- Jetson의 UTC 시간이 틀리면 정상 Payload도 stale/future 데이터로 거절될 수 있으므로
  NTP 동기화를 실기 전에 확인한다.

## 6. State와 Telemetry

### State

- 연결 직후 1회, Mode·Reason·Mission·Health 변경 즉시, 변화가 없어도 30초마다 발행한다.
- `mode`와 `reason_code`는 유효한 조합으로만 바꾼다.
- Mission이 활성 상태면 `mission_id`와 `mission.state`를 함께 보낸다.
- 긴급정지 시 `mode=SAFE_STOP`, `reason_code=REMOTE_ESTOP`,
  `mission.state=PAUSED`가 함께 보여야 한다.

### Telemetry

- 기본 주기는 5초다.
- GPS가 무효면 `position.valid=false`와 함께 좌표를 `null`로 보낸다.
- `PAUSED`, `SAFE_STOP`, `ERROR`에서는 `motion.moving=false`다.
- Mission이 활성 상태면 최상위 `mission_id`와 `mission` 블록을 함께 보낸다.
- `mission.elapsed_sec`는 Mission 시작 후 벽시계 누적값이며 PAUSED 중에도 증가한다.
- 측정할 수 없는 값을 그럴듯한 기본값으로 만들지 말고 계약이 허용하는 `null` 또는
  `UNKNOWN`을 사용한다.

## 7. Command 6종

| Command | Parameters | TTL | 성공 후 핵심 동작 |
| --- | --- | ---: | --- |
| `START_MISSION` | `mission_id`, `zone_id` | 60초 | `PATROLLING/RUNNING`, `MISSION_STARTED` |
| `PAUSE_MISSION` | `reason` | 30초 | `PAUSED`, `MISSION_PAUSED` |
| `RESUME_MISSION` | 빈 Object | 30초 | 안전 해제·PAUSED 확인 후 `MISSION_RESUMED` |
| `COMPLETE_MISSION` | 빈 Object | 30초 | 모터 정지, `MISSION_COMPLETED` 후 Mission 보관함 정리 |
| `CANCEL_MISSION` | `reason` | 30초 | `MISSION_CANCELLED` 후 Mission 보관함 정리 |
| `EMERGENCY_STOP` | `reason` | 10초 | 모터 정지, `SAFE_STOP/PAUSED`, 필요 시 `MISSION_PAUSED` |
| `CLEAR_EMERGENCY_STOP` | `reason` | 30초 | `REMOTE_ESTOP`만 해제하고 활성 Mission은 PAUSED 유지 |

Command 처리 규칙:

1. 알 수 없는 schema version은 실행하지 않는다.
2. 만료된 명령은 실행하지 않고 `EXPIRED` Result를 보낸다.
3. 같은 `command_id`는 다시 실행하지 않는다.
4. 일반 명령은 `ACCEPTED`로 수신 사실을 알린 뒤 실행한다.
5. `EMERGENCY_STOP`은 모터 정지와 상태 전이를 먼저 끝낸 뒤 `ACCEPTED`를 보낸다.
6. `ACCEPTED`는 성공이 아니다. 최종 `COMPLETED`, `FAILED`, `REJECTED`, `EXPIRED`를
   별도로 발행한다.
7. `commands/result.state`에는 각 Result 생성 시점의 처리 후 Mode와 Reason을 넣는다.
8. 처리 완료한 `command_id`의 Result를 캐시해 중복 수신 시 같은 최종 Result를
   재발행하는 방식을 권장한다. 어떤 경우에도 동작 자체를 반복하면 안 된다.

`RETURN_TO_CHARGE`, `UPDATE_CONFIG`, `RETURNING_TO_CHARGE`, `CHARGING`은 호환성
예약값일 뿐 현재 MVP 제어·상태 전이 구현 범위가 아니다.

## 8. Mission Event와 Safety Event를 혼동하지 않는다

- Mission 상태가 바뀌면 `events/mission`을 발행한다.
- 장애물·센서·배터리 원인의 안전 정지는 `events/safety` 또는 `events/battery`를
  추가로 발행할 수 있지만 Mission Event를 대체하지 않는다.
- START·PAUSE·RESUME에는 `result` 블록을 넣지 않는다.
- COMPLETED·CANCELLED·FAILED에는 종료 집계를 담은 `result` 블록을 넣는다.
- 같은 상태의 Event를 반복 발행하지 않는다. Backend는 동일 상태 전이를 충돌로 본다.
- Mission 종료 Event Payload를 만든 뒤 Mission 보관함을 정리한다. 먼저 지우면 Event의
  `mission_id`와 결과 집계를 잃는다.

## 9. Incident·이미지

- Incident `location.zone_id`는 현재 Mission의 `zone_id`를 그대로 사용한다.
- GPS 위치 유효성, 촬영시각, bbox 정규화 값, 모델 이름·버전을 계약대로 보낸다.
- bbox의 폭과 높이는 0보다 커야 한다.
- 이미지 업로드가 실패해도 Incident를 버리지 않는다. `image_id: null`로 Event를
  발행해 탐지 메타데이터는 보존한다.
- 이미지 REST 업로드의 Robot 식별자는 MQTT ID가 아니라 `ROBOT_UUID`다.

```powershell
cd embedded

```

긴급정지 복구에서 직접 확인할 순서:

```text
1. START_MISSION
   - State: PATROLLING/RUNNING
   - Event: MISSION_STARTED

2. EMERGENCY_STOP
   - 실제 모터 정지
   - State: SAFE_STOP/REMOTE_ESTOP + Mission PAUSED
   - Event: MISSION_PAUSED 1회
   - Result: ACCEPTED → COMPLETED

3. SAFE_STOP 상태에서 RESUME_MISSION
   - Result: REJECTED/SAFETY_CONDITION_NOT_CLEARED

4. CLEAR_EMERGENCY_STOP
   - State: PAUSED/REMOTE_PAUSE + Mission PAUSED
   - 바퀴는 움직이지 않음

5. RESUME_MISSION
   - State: PATROLLING/NONE + Mission RUNNING
   - Event: MISSION_RESUMED
   - Result: ACCEPTED → COMPLETED
```

실기에서는 Robot 로그만 보지 말고 Broker Topic, Backend Mission 상태 이력,
Command Result, 관리자 화면 버튼 상태를 같은 `command_id`·`mission_id`로 대조한다.
