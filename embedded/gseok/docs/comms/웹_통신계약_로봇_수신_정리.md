# 웹 통신 작업 ↔ 로봇 수신 정리

작성일 2026-08-01 · 기준 브랜치 `ags` · 계약 `tbs/v2` (`schema_version: "2.0"`, 2026-07-30 FROZEN)

웹(Spring 백엔드)이 만들어 둔 통신 관련 구현을 **로봇(임베디드)이 실제로 어떻게 받는지** 코드 기준으로 정리한다.
문서가 아니라 현재 `web/backend` · `embedded/` 소스에서 확인한 내용이다.

---

## 0. 한눈에 보기

로봇과 웹은 채널이 **4개**다. 이 중 로봇이 "받는" 것은 2개뿐이다.

| # | 채널 | 방향 | 로봇 측 진입점 | 비고 |
|---|---|---|---|---|
| 1 | MQTT `commands/request` | 웹 → 로봇 | `comms/client.py:_on_message` → `commands.py` | **로봇이 구독하는 유일한 topic** |
| 2 | MQTT 8종 발행 | 로봇 → 웹 | `comms/client.py:publish` | 웹이 6단계 관문으로 검증·거부 |
| 3 | HTTP `POST /api/v1/images` | 로봇 → 웹 | `comms/uploader.py` | 증거 이미지, `X-API-Key` |
| 4 | HTTP 자격증명 발급 | 웹 → (관리자) → 로봇 | 사람이 환경변수로 주입 | 로봇이 직접 호출하지 않음 |

`ingest/receipt`(웹 → 로봇)는 계약에는 있으나 **로봇이 구독하지 않고**, 웹도 `local` 프로필 수동 테스트 컨트롤러에서만 발행한다. MVP 미사용.

## 1. 접속 (Broker 연결)

### 웹이 정하는 값

| 값 | 출처 | 현재 값 |
|---|---|---|
| Broker URI | `mqtt.credential-provisioning.public-broker-uri` | 기본 `ssl://localhost:8883` (`MQTT_PUBLIC_BROKER_URI`) |
| username | `robot.robot.mqtt_id` | `RBT-001` |
| password | `MqttCredentialSecretGenerator` 32바이트 난수 | 발급 시 1회만 평문 반환 |
| 만료 | `insertActiveCredential` | 발급 후 **180일** |

### 로봇이 붙는 방법 (`comms/client.py`)

```
MQTT 5 / client_id = config.client_id or robot_id
username = robot.id  ← config.py 가 robot.id 와 다르면 기동 거부
clean_start = MQTT_CLEAN_START_FIRST_ONLY   (첫 접속만 새 세션, 재접속은 세션 승계)
SessionExpiryInterval = 3600s               (재접속 사이 구독·미수신 명령 보존)
keepalive = 30s
```

접속 순서가 계약상 중요하다.

1. `will_set()` — LWT `presence OFFLINE / UNGRACEFUL_DISCONNECT` (QoS 1, retain)
2. `connect_async` + `loop_start` — 브로커가 죽어 있어도 기동을 막지 않고 1→2→4→…→30초 백오프
3. `_on_connect`: birth `presence ONLINE` 발행 → `commands/request` 구독 → Outbox 플러시 → `on_connected` 훅(현재 state 재발행)
4. `_on_subscribe`: **SUBACK 거부를 반드시 확인한다.** ACL로 읽기가 막히면 로봇은 멀쩡해 보이는데 명령을 영원히 못 받는다. `client.subscribed`/`subscribe_reason_codes`에 남는다.

정상 종료는 `presence OFFLINE / GRACEFUL_SHUTDOWN`을 직접 발행한 뒤 `disconnect()` → 브로커가 LWT를 버린다.

## 2. 로봇이 받는 것 — `commands/request`

```
topic  tbs/v2/robots/{mqtt_id}/commands/request
QoS    1     Retain  절대 금지
MQTT5  Message Expiry Interval = max(1, expires_at - issued_at) 초
```

### 2.1 웹에서 여기까지 오는 경로

`web/backend/.../robot/api/RobotCommandController.java:52`

```
POST /api/v1/robots/{robotId}/commands       (관리자 세션 + Idempotency-Key)
  └ RobotCommandCreationService.create()
      ├ 멱등키 선점 (request_control.idempotency_request)
      ├ 로봇 조작 권한 확인 → mqtt_id 획득 (RobotScopeService)
      ├ command_id = UUID.randomUUID()
      ├ issued_at = 서버 Clock, expires_at = issued_at + TTL
      ├ 미션 대상 해석 (아래 2.3)
      └ robot.robot_command INSERT (status = CREATED)
  └ RobotCommandService.createAndPublish()
      ├ MqttV2Publisher.publishCommand(mqttId, payload)
      ├ 성공 → command_status = SENT
      └ 실패 → PUBLISH_FAILED (재시도 없음, 로봇은 이 명령을 영영 못 받는다)
```

> 로봇이 명령을 못 받는 경우, 로봇 쪽 로그만 봐서는 알 수 없다. 웹 DB `robot_command.command_status`가 `PUBLISH_FAILED`인지 먼저 확인해야 한다.

`MqttV2PublishController`(`/api/mqtt/v2/robots/{mqttId}/commands/request`)는 `@Profile("local")` — **로컬 수동 발행 전용**이다. 운영 경로가 아니다.

### 2.2 실제 payload (`CommandRequestPayload`)

```json
{
  "schema_version": "2.0",
  "command_id": "a75d9cec-b04d-4f66-b18a-4c48782f805a",
  "command_type": "START_MISSION",
  "issued_at": "2026-07-30T01:10:00.000Z",
  "expires_at": "2026-07-30T01:11:00.000Z",
  "requested_by": { "actor_type": "ADMIN", "actor_id": "ADM-0042" },
  "parameters": { "mission_id": "MIS-20260730-001", "zone_id": "A-01" }
}
```

- 직렬화는 `snake_case`. `requested_by.actor_type`은 항상 `ADMIN`(현재 REST 경로 고정), `actor_id`는 `auth.admin_user.user_code`다.
- `command_id`는 UUID지만 로봇은 **불투명 문자열로만** 다룬다(`commands.py`는 파싱하지 않음).

### 2.3 ⭐ `mission_id` · `zone_id`가 무엇인지 (가장 헷갈리는 지점)

| 필드 | 실제 값 | UUID인가 |
|---|---|---|
| `parameters.mission_id` | `robot.mission.mission_code` (예: `MIS-20260730-001`) | **아니오, 문자열** |
| `parameters.zone_id` | `robot.patrol_area.area_code` (예: `A-01`) | **아니오, 문자열** |

서버는 `START_MISSION` 시 `resolveStartMissionTarget()`에서 다음을 **먼저 검증**하고 통과한 값만 보낸다.

- `mission_code` + `robot_id` + `status IN ('CREATED','READY')`로 미션이 존재해야 함 → 없으면 `MISSION_NOT_FOUND`
- 관리자가 보낸 `zone_id`가 그 미션의 `patrol_area.area_code`와 **일치**해야 함 → 아니면 `COMMON_BUSINESS_RULE_VIOLATION`

따라서 **로봇에 도달한 `mission_id`·`zone_id`는 이미 서버 DB와 정합성이 검증된 값**이다. 로봇은 그대로 보관했다가 그대로 되돌려 보내면 된다(`events.py`가 incident의 `location.zone_id`에 echo).

`PAUSE`/`RESUME`/`CANCEL`은 서버가 내부적으로 활성 미션을 찾아 `robot_command` 행에는 기록하지만 **payload `parameters`에는 넣지 않는다**(`reason`만). 로봇은 자기가 들고 있는 `mission_id`로 처리해야 한다.

### 2.4 명령별 parameters와 TTL

서버(`RobotCommandCreationService.ttl()`)와 로봇(`commands.py: REQUIRED_PARAMETERS`)이 **일치**한다.

| command_type | parameters | TTL | 로봇 처리 |
|---|---|---:|---|
| `START_MISSION` | `mission_id`, `zone_id` (reason 금지) | 60s | `start_patrol()` → `start_mission()` → `MISSION_STARTED` |
| `PAUSE_MISSION` | `reason` | 30s | `pause()` → `MISSION_PAUSED` |
| `RESUME_MISSION` | 빈 객체 (셋 다 null) | 30s | `resume()` → `MISSION_RESUMED` |
| `COMPLETE_MISSION` | 빈 객체 (셋 다 null) | 30s | 모터 정지 → `MISSION_COMPLETED` → `stand_by()` |
| `CANCEL_MISSION` | `reason` | 30s | `MISSION_CANCELLED` 발행 후 `stand_by()` |
| `EMERGENCY_STOP` | `reason` | **10s** | 모터 정지 먼저 → `SAFE_STOP`; RUNNING Mission은 `PAUSED` + `MISSION_PAUSED` |
| `CLEAR_EMERGENCY_STOP` | `reason` | 30s | 원격 정지 해제 후 활성 Mission은 `PAUSED` 유지 |

`RETURN_TO_CHARGE`·`UPDATE_CONFIG`는 서버 enum에 아예 없고, 로봇도 `RESERVED_COMMAND_TYPES`로 두어 와도 실행하지 않는다.

### 2.5 로봇 수신 처리 순서

```
paho 네트워크 스레드
  └ client._on_message
      ├ topic != commands/request  → 무시 + warn 로그
      ├ JSON 디코드 실패           → drop + payload 앞 120자 로그
      └ queue.put(command)          ← 여기까지만. 해석하지 않는다.

메인 루프 (매 tick)
  └ CommandRunner.poll()  ← 큐가 빌 때까지 전부 처리 (EMERGENCY_STOP 지연 방지)
      └ handle(command)
```

`handle()` 검증 순서와 결과 (`commands.py:111`):

| # | 조건 | commands/result 발행 |
|---|---|---|
| 1 | dict 아님 | **없음** (로그만) |
| 2 | `schema_version != "2.0"` | **없음** — command_id조차 믿을 수 없음 |
| 3 | `command_id` 없음 | `REJECTED` / `INTERNAL_ERROR` |
| 4 | 최근 64개 안의 중복 `command_id` | **없음** (조용히 무시) |
| 5 | 예약·미지원 `command_type` | `REJECTED` / `INTERNAL_ERROR` |
| 6 | `expires_at` 경과 | `EXPIRED` / `OK` |
| 7 | 필수 `parameters` 누락 | `REJECTED` / `INTERNAL_ERROR` |
| 8 | 실행 | `ACCEPTED` → `COMPLETED`\|`REJECTED`\|`FAILED` (2건) |

- 중복 판정을 검증보다 **앞**에 둔다 — 거부한 명령이 재전송돼도 조용해야 하므로.
- `EMERGENCY_STOP`만 **모터 정지 → 그 다음 `ACCEPTED` 발행** 순서다(소켓보다 바퀴가 먼저).
- 실행 중 긴급정지는 같은 Mission ID의 `MISSION_PAUSED`를 발행하고, 해제 후에도
  자동 주행하지 않는다. 별도 `RESUME_MISSION`이 성공해야 `MISSION_RESUMED`로 돌아간다.
- `expires_at` 판정이 로봇 시계에 의존한다 → **NTP 동기가 전제**다. 웹의 freshness 검사(§3.4)도 마찬가지라 시계가 밀리면 양방향으로 깨진다.

거부 사유 `SAFETY_CONDITION_NOT_CLEARED`가 나오는 경우가 운영 중 헷갈린다.

- `SAFE_STOP` 상태에서 `START_MISSION`/`RESUME_MISSION` → 명령 하나로 안전 정지를 지나칠 수 없음
- `CLEAR_EMERGENCY_STOP`인데 정지 사유가 `REMOTE_ESTOP`이 아님 (예: `OBSTACLE`로 서 있음)

## 3. 로봇이 보내는 것 — 웹의 수신 관문

로봇 발행 8종은 `MqttMessageParser.parse()`를 통과해야 처리된다. **하나라도 걸리면 조용히 버려진다.**

```java
// MqttInboundMessageDispatcher.dispatch()
catch (BusinessException exception) {
    log.warn("MQTT inbound message rejected. topic={}, qos={}, errorCode={}", ...);
}
```

> ⚠️ 거부는 **웹 로그와 `gilbom.mqtt.inbound.rejected` 메트릭에만** 남는다. 브로커는 이미 PUBACK을 보냈으므로 로봇 Outbox는 `sent`로 지워진다. → **로봇이 알 수 없는 조용한 유실**이다. `ingest/receipt`가 MVP에서 미사용이라 이 구멍을 메울 채널이 없다.

### 3.1 관문 6단계

| # | 검사 | 실패 시 error_code |
|---|---|---|
| 1 | topic이 `tbs/{v}/robots/{mqtt_id}/...` 형식 | `MQTT_TOPIC_INVALID` |
| 1b | 버전 세그먼트가 `v2` | `MQTT_SCHEMA_VERSION_UNSUPPORTED` |
| 1c | 상대경로가 등록된 10종 중 하나 | `MQTT_TOPIC_UNSUPPORTED` |
| 2 | **QoS가 topic별 값과 정확히 일치** | `MQTT_QOS_MISMATCH` |
| 3 | JSON 역직렬화 (아래 주의) | `MQTT_PAYLOAD_MALFORMED` |
| 4 | `schema_version == "2.0"` | `MQTT_SCHEMA_VERSION_UNSUPPORTED` |
| 5 | Bean Validation (필수·범위·조건부) | `MQTT_PAYLOAD_VALIDATION_FAILED` |
| 6 | topic의 `mqtt_id` == payload의 `mqtt_id` | `MQTT_ID_MISMATCH` |
| 7 | 신선도 (§3.4) | `MQTT_MESSAGE_EXPIRED` / `MQTT_TIMESTAMP_IN_FUTURE` |

**3단계 주의** — ObjectMapper 설정이 엄격하다.

```java
.setPropertyNamingStrategy(SNAKE_CASE)
.enable(FAIL_ON_UNKNOWN_PROPERTIES)   // 계약에 없는 필드 하나만 있어도 전체 거부
.enable(FAIL_ON_TRAILING_TOKENS)      // JSON 뒤에 잉여 바이트 금지
```

→ **payload에 임의 필드를 추가하면 안 된다.** 디버그용 필드, 주석성 키, 미래 대비 필드 전부 거부 사유다. 계약 동결 문서도 "선택 필드 추가 = Major 변경"으로 못박고 있다.

### 3.2 필드 이름은 `robot_id`가 아니라 `mqtt_id`

DB 마이그레이션 `V15__rename_robot_code_to_mqtt_id.sql` 이후 **payload 식별자 필드명은 `mqtt_id`**다.

- 웹: `RobotIdentifiedPayload.mqttId()` — 8종 전부
- 로봇: `factory.py:_head()`가 `"mqtt_id": self.robot_id` 발행 ✅ 이미 맞음
- 다만 `embedded/config.yaml` 주석은 아직 "payload 의 robot_id"라고 적혀 있다(값은 정상, 문구만 옛날).

이미지 업로드 form 필드는 **여전히 `robot_id`**다(§4). 이름이 채널마다 다르다는 점을 헷갈리지 말 것.

### 3.3 topic별 QoS·Retain (양쪽 일치 확인 완료)

| topic | QoS | Retain | 로봇 발행 주기 |
|---|:---:|:---:|---|
| `presence` | 1 | **O** | 접속/종료/LWT |
| `state` | 1 | **O** | 상태 전이 즉시 + 30초 |
| `telemetry` | **0** | X | 5초 |
| `events/incident` | 1 | X | 결함 확정 시 1회 |
| `events/battery` | 1 | X | 등급 전이 시 1회 |
| `events/safety` | 1 | X | 안전 사건 확정·해제 시 |
| `events/mission` | 1 | X | 미션 상태 전이 시 |
| `commands/result` | 1 | X | 명령 접수·완료 |

웹 구독은 `adapter.setQos(mqtt.qos)` — **모든 topic에 단일 값**(기본 1)이다. 수신 QoS는 `min(발행 QoS, 구독 QoS)`이므로 현재 설정에서는 전부 맞는다. 다만 **`MQTT_QOS=0`으로 바꾸면 QoS 1 topic 7종이 전부 0으로 강등돼 `MQTT_QOS_MISMATCH`로 거부된다.** 환경변수 건드리지 말 것.

### 3.4 신선도 (`MqttInboundFreshnessGuard`)

| topic | 기준 시각 | 최대 지연 | 설정 키 |
|---|---|---:|---|
| `telemetry` | `sampled_at` | 60s | `MQTT_TELEMETRY_MAX_DELAY` |
| `state` | `updated_at` | 300s | `MQTT_STATE_MAX_DELAY` |
| `commands/result` | `completed_at` ?? `received_at` | 60s | `MQTT_COMMAND_RESULT_MAX_DELAY` |
| events 4종 | `occurred_at` | **payload의 `ttl_sec`** | — |
| 전부 | 미래 시각 허용치 | 5s | `MQTT_FUTURE_TIMESTAMP_TOLERANCE` |

- `ttl_sec`은 로봇이 직접 싣는다. `contract.py`: 최소 60 / 최대 300 / 기본 **300**. 서버 DTO도 `@Min(60) @Max(300)`으로 동일.
- **오프라인이 5분을 넘으면 Outbox에 쌓인 event는 재전송해도 `MQTT_MESSAGE_EXPIRED`로 거부된다.** 재전송 시 `occurred_at`은 유지하고 `sent_at`만 갱신하는 규칙(`client._send_stored`) 때문에 신선도 기준은 계속 원래 시각이다. → 장시간 단절 후 밀린 결함은 실질적으로 유실된다. 계약대로 동작하는 것이지만 운영상 반드시 인지해야 한다.
- `presence`는 시각 기준이 없어 신선도 검사 대상이 아니다.

### 3.5 Replay / Sequence 규칙 (`MqttReplayProtectionService`)

여기가 웹 쪽에서 가장 빡빡한 부분이고, 로봇 `seq` 구현이 정확히 맞아야 한다.

**`seq`는 `state` · `telemetry` · `events` 4종이 공유하는 단일 증가 카운터다.** (`presence`·`commands/result`는 `seq` 없음)

| 규칙 | 위반 시 |
|---|---|
| 새 `boot_id`의 첫 메시지는 `seq == 1` | `MQTT_REPLAY_REJECTED` (`new_boot_sequence`) |
| 같은 boot 안에서 `seq` 단조 증가 (`<= last_seen_seq` 금지) | `MQTT_REPLAY_REJECTED` (`non_increasing_sequence`) |
| `(robot_id, boot_id, seq)`를 다른 메시지가 사용 | `MQTT_SEQUENCE_CONFLICT` |
| 같은 `event_id`/`message_id`가 다른 좌표로 재등장 | `MQTT_SEQUENCE_CONFLICT` |
| 교체된(OFFLINE) boot의 지연 메시지 | `MQTT_REPLAY_REJECTED` (`previous_boot`, `closed_boot`) |

로봇 구현 대조 (`factory.py`):

```python
self._seq = 0
def next_seq(self):        # 잠금 하에 +1 → 첫 값이 1
self.boot_id = uuid4()     # 프로세스 시작 시 1회, seq 도 함께 리셋
```
✅ 계약과 일치한다. 단, **같은 `MessageFactory` 인스턴스를 유지해야** 한다. 프로세스를 재시작하지 않고 factory만 새로 만들면 `boot_id`는 새 값인데 서버가 기존 boot를 `REPLACED_BY_NEW_BOOT`로 닫고 `robot_current_state`를 전부 NULL로 초기화한다(관제 화면이 잠깐 빈다).

**event 재전송이 안전한 이유**: 중복 판정에서 EVENT는 `event_id`만 비교하고 raw payload를 비교하지 않는다. 따라서 `sent_at`만 갱신한 재전송은 `DUPLICATE`로 정상 처리되고 새 행을 만들지 않는다. (TELEMETRY·STATE는 payload 동일성까지 보지만, telemetry는 QoS 0로 재전송하지 않고 state는 재발행 시 새 `seq`를 쓰므로 문제되지 않는다.)

### 3.6 topic별 필수 필드 (서버 DTO 기준)

**`presence`** — `schema_version`, `mqtt_id`, `boot_id`, `status`
`ONLINE`이면 `connected_at` 필수 + `reason` 금지 / `OFFLINE`이면 그 반대. 둘 다 있거나 둘 다 없으면 거부.

**`state`** — 위 + `seq`, `updated_at`, `mode`, `reason_code`, `battery`, `health`(6종 전부 필수), `mission`(없으면 null)
`battery.valid=true` → `percent` 필수 & `state != UNKNOWN` / `valid=false` → `percent=null` & `state=UNKNOWN`.

**`telemetry`** — 위 + `message_id`, `sampled_at`, `position`, `motion`, `battery`, `system`
- `mission_id`와 `mission` 블록은 **함께 있거나 함께 null**이어야 함 (`isMissionPresenceConsistent`)
- `position.valid=true` → `lat`,`lon` 필수 / `false` → `lat`,`lon`,`heading_deg` 전부 null
- `battery.valid=true` → `source` **필수** / `false` → `source=null`
- `heading_deg` ∈ [0.0, 360.0), `speed_mps` ≥ 0 (MVP는 항상 null)
- 선택 확장 `voltage_v`/`current_a`/`charging`/`battery_temperature_c`/`estimated_runtime_sec`는 서버 DTO에 있으므로 보내도 됨

**event 공통 envelope** — `event_id`, `event_type`, `mqtt_id`, `boot_id`, `seq`, `source_component`, `occurred_at`, `sent_at`, **`ttl_sec`**, `mission_id`

**`events/incident`** 추가 제약 (가장 까다로움)
- `source_component`는 반드시 `ai`
- `location.zone_id`는 `START_MISSION`으로 받은 구역 코드를 해석하지 않고 그대로 사용
- `evidence.image_id`는 **UUID 또는 null**
- `bbox_norm` 원소 4개, 각 [0.0,1.0], **`x_min < x_max` 그리고 `y_min < y_max`**
- `confidence`·`attributes.damage_ratio` ∈ [0.0,1.0]
- `defect_type`은 MVP `DAMAGED`만, `block_type`은 `LINEAR|DOT|UNKNOWN`

**`commands/result`** — `result_id`, `command_id`, `mqtt_id`, `status`, `received_at`, `reason_code`, `state{mode, reason_code}`
`ACCEPTED`면 `completed_at`은 **반드시 null**, 그 외 상태면 **반드시 존재**하고 `completed_at >= received_at`.
→ 로봇이 `command_id` 없는 명령에 대해 내는 `REJECTED`(`command_id: null`)는 서버 `@NotNull`에 걸려 거부된다. 어차피 서버가 모르는 명령이라 실害는 없지만, 로그에 `MQTT_PAYLOAD_VALIDATION_FAILED`로 남는다.

### 3.7 웹이 데이터를 쓰는 곳

| topic | 서버 처리 |
|---|---|
| `presence` | 온·오프라인 배지, boot 세션 상태 |
| `state` | `telemetry.robot_current_state` UPSERT + `robot_status_history` INSERT |
| `telemetry` | `telemetry.robot_telemetry` INSERT, 지도 위치·궤적·배터리·Jetson 온도 |
| `events/incident` | 관측 저장 → 결함 생성/병합, 업로드된 이미지와 `event_id`로 연결 |
| `events/battery` | 전이 이력 |
| `events/safety` | 안전 사건·알림 |
| `events/mission` | 미션 상태 이력·최종 집계 |
| `commands/result` | `robot_command_result`, 관제 화면 명령 상태 |

`mission.elapsed_sec`는 계약 동결 문서상 **`PAUSED` 중에도 계속 증가**해야 하고, 서버는 이 값과 미션 계획시간으로 진행률을 계산한다(경로 GeoJSON·GPS 유효성에 의존하지 않음). 로봇 `robot_state.py:303`이 monotonic 기준으로 계산하며 일시정지 중에도 멈추지 않는다 → ✅ 일치.

## 4. 증거 이미지 업로드 — `POST /api/v1/images`

웹이 임베디드 코드에 맞춰 구현해 둔 상태다(`ImageUploadController` javadoc에 명시). `uploader.py`의 `⚠️ 추정치` 주석은 이제 **확정**으로 바꿔도 된다.

### 요청

```
POST /api/v1/images
Content-Type: multipart/form-data
X-API-Key: <기기별 키>          ← 세션 쿠키·CSRF 대상 아님

file        : JPEG 바이트   (SOI 마커로 실제 검사, Content-Type 신뢰 안 함)
event_id    : UUID          ← incident event 의 event_id 와 동일
robot_id    : UUID          ← ⚠️ robot.robot_id (DB UUID), mqtt_id 아님
captured_at : 선택, ISO-8601 UTC, 미래 시각 금지
```

크기 상한 **512,000 bytes** — 로봇(`MAX_IMAGE_BYTES = 500 * 1024`)·서버(`MAX_BYTES`)·DB 제약(`ck_robot_image_size`) 세 곳이 같은 값이다. ✅

### 응답 (camelCase — MQTT와 달리 snake_case 아님)

```json
{ "imageId": "...", "eventId": "...", "objectKey": "robots/{robotId}/2026/08/01/{imageId}.jpg",
  "imageWidth": 1280, "imageHeight": 720 }
```

- **201** 신규 / **200** 같은 `event_id` 멱등 재업로드 → 로봇은 둘 다 성공 처리 ✅
- 같은 `event_id`인데 다른 로봇 또는 다른 파일 → **409 Conflict**
- `uploader.py:_extract_image_id`가 `image_id` → `imageId` 순으로 읽으므로 현재 응답과 맞는다 ✅
- 이미지는 incident event보다 먼저 도착하며, 서버가 나중에 `linkAvailableImage()`로 연결한다. 순서를 맞출 필요 없음.
- 업로드 실패해도 `image_id: null`로 incident event는 그대로 발행한다(`events.py`). 결함 사건을 이미지 때문에 삼키지 않는다.

### ⚠️ 현재 깨져 있는 부분

`embedded/events.py:388`

```python
payload["evidence"]["image_id"] = self._upload(
    image_path, payload["event_id"], self._client.messages.robot_id   # → "RBT-001"
)
```

서버는 `UUID.fromString(robot_id)`로 파싱한다(`ImageUploadController:99`). `"RBT-001"`은 UUID가 아니므로 **400 `COMMON_INVALID_REQUEST`**가 떨어지고, 400은 `RETRYABLE_CLIENT_STATUSES`가 아니라 재시도 없이 포기한다.

**결과: 모든 결함 이미지 업로드가 실패하고 `evidence.image_id`가 항상 null이 된다.** 결함은 기록되지만 사진이 안 붙는다.

필요한 조치 (임베디드 범위):
1. `config.yaml`의 `robot:` 섹션에 DB UUID 항목 추가 (예: `uuid: ${env:ROBOT_UUID}`)
2. `events.py`의 업로드 호출이 `mqtt_id` 대신 그 UUID를 넘기도록 변경
3. 웹팀에서 해당 로봇의 `robot.robot_id` UUID와 `X-API-Key`를 받아 환경변수로 주입

## 5. 확인·조치 목록

### 5-1. 임베디드에서 고칠 것

| 항목 | 위치 | 영향 |
|---|---|---|
| 업로드 `robot_id`에 UUID 전달 | `events.py:388`, `config.yaml` | **결함 이미지 100% 유실** |
| `robot.uuid` 설정 항목 신설 | `comms/config.py`, `config.yaml` | 위 항목 전제 |
| `detect.model_version: 0.0.0-stub` 실제 버전 교체 | `config.yaml` | incident `model.version` 부정확 |
| `config.yaml` 주석의 "payload 의 robot_id" → `mqtt_id` | `config.yaml` | 문구만 (동작 정상) |
| 운영 배포 시 `require_tls: true` + `ca_cert` 경로 | `config.yaml` | 평문 접속 시 무한 재접속만 반복 |

### 5-2. 웹팀에 확인·요청할 것

1. **`area_code` 전달.** `zone_id`는 `robot.patrol_area.area_code`를 해석하지 않고 그대로 전달한다. 별도 문자 형식이나 구간 의미를 강제하지 않는다.
2. **거부 사실을 로봇이 알 방법이 없다.** `ingest/receipt`가 MVP 미사용이라 서버가 버린 메시지를 로봇은 `sent`로 지운다. 최소한 `gilbom.mqtt.inbound.rejected` 메트릭(태그 `topic`, `reason`)을 통합 테스트 기간 동안 공유받을 것.
3. **`MQTT_QOS`는 1로 고정.** 0으로 내리면 QoS 1 topic 7종이 전부 `MQTT_QOS_MISMATCH`로 거부된다.
4. **중복 `command_id` 재수신 시 이전 결과 재발행 여부.** `web/docs/mqtt-device-db-mapping.md`는 "이전 결과를 다시 발행"을 요구하지만 v2 계약과 현행 임베디드는 조용히 무시한다. 어느 쪽이 맞는지 확정 필요.
5. **`mqtt-device-db-mapping.md`가 아직 `tbs/v1` · `robot_id` 표기**다. 코드는 `tbs/v2` · `mqtt_id`이므로 문서 갱신 요청.
6. `application.yml`의 `mqtt.publish-topic` 기본값이 `tbs/v2/robots/robot-test/commands/request`로 박혀 있다. 실제 명령은 `MqttV2Publisher`가 topic을 매번 만들어 쓰므로 무해하지만, 읽는 사람이 오해하기 쉽다.
7. 로봇 UUID(`robot.robot_id`)와 이미지 업로드용 `X-API-Key` 전달 요청.
