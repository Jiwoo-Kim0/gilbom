|---|---|---|---|

| Let’s Encrypt ACME | 공개 HTTPS 인증서 발급·갱신 | 운영 HTTPS에 필수 | domain과 연락 email; private key는 Certbot이 host에 생성 |

- Photon Cloud
- Firebase/Cloudinary
- AWS SDK/S3 object storage 연동

Robot image와 보고서 PDF는 현재 운영 Compose의 local named volume(`robot_images`, `report_pdf_data`)에 저장된다.

## 3. Naver Cloud Platform Maps

### 실제 사용 기능

- Web Dynamic Map JavaScript API v3
- Robot 위치 지도
- 결함 위치 지도/marker/cluster
- 순찰 구역 polygon 편집 및 mission 지도
- Frontend가 다음 HTTPS script를 동적으로 불러온다.

```text
https://oapi.map.naver.com/openapi/v3/maps.js?ncpKeyId=<Client-ID>
```

공식 문서:

- Client ID 발급: https://navermaps.github.io/maps.js.en/docs/tutorial-1-Getting-Client-ID.html
- Web Dynamic Map 시작: https://navermaps.github.io/maps.js.en/docs/tutorial-2-Getting-Started.html
- Maps Application 등록: https://guide.ncloud-docs.com/docs/maps-app/

### 가입 및 Application 등록

1. Naver Cloud Platform 계정을 준비하고 결제/대표 계정 정책을 확인한다.
2. Console의 `Services > Application Services > Maps > Application`으로 이동한다.
3. 새 Application을 등록한다.
4. `Dynamic Map` 또는 현재 Console에서 이에 대응하는 Web Dynamic Map 상품을 선택한다.
5. 운영 Web 서비스 URL을 등록한다. 실제 domain과 다르면 인증이 실패할 수 있다.
6. 발급된 Client ID를 복사한다.
7. Client Secret은 현재 Frontend build에 사용하지 않는다. Frontend에 넣지 않는다.

### 작성 필요 값

```text
NCP 대표/소유 계정: _____________________________________
Application 이름: _______________________________________
운영 Web 서비스 URL: ____________________________________
Client ID: ______________________________________________
등록일/만료 또는 검토일: _________________________________
과금 알림 담당자: _______________________________________
```

### 프로젝트 주입 위치

```dotenv
VITE_NAVER_MAP_CLIENT_ID=________________
```

이 값은 `compose.build.yaml`에서 Frontend Docker build argument로 들어가 browser bundle에 포함된다. 공개 Client ID이므로 Backend Secret이 아니지만, 허용 domain과 사용량/과금은 Console에서 제한·감시해야 한다.

값을 변경하면 Frontend image를 다시 빌드해야 한다.

```bash
VITE_NAVER_MAP_CLIENT_ID="________________" \
  docker compose --env-file .env.prod -f compose.build.yaml build frontend
```

### 확인

1. 운영 HTTPS page를 연다.
2. Browser 개발자 도구 Network에서 `maps.js?ncpKeyId=...`가 성공하는지 확인한다.
3. `/defects`, `/robots`, `/patrol-areas`, `/missions` 지도 화면을 확인한다.
4. `401/403/429`이면 Client ID, Dynamic Map 선택, 등록 Web URL과 quota를 확인한다.

## 4. SSAFY GMS LLM

### 저장소에서 확인된 계약

| 항목 | 값 |
|---|---|
| Provider | `GMS` |
| Base URL | `https://gms.ssafy.io/gmsapi/api.openai.com/v1` |
| Egress | `gms.ssafy.io:443` |
| Prompt version | 운영 Compose `report-v3` |
| 최대 output token 기본값 | `1500` |
| connect/read timeout 기본값 | `3s` / `30s` |
| 호출 주체 | Browser가 아닌 Backend |

GMS 가입/Key 발급 절차는 저장소에서 확인할 수 없으므로 추측하지 않는다.

```text
GMS 가입/발급 담당자: ___________________________________
신청 URL 또는 내부 문서: _________________________________
발급 계정: ______________________________________________
승인 모델명: ____________________________________________
API Key Secret 관리 위치: ________________________________
일일 요청 한도: _________________________________________
일일 예산: ______________________________________________
데이터 보존/학습 제외 승인자: ____________________________
```

### Secret 준비

API Key는 한 줄짜리 host 파일에 두고 `.env.prod`에는 그 파일 경로만 기록한다.

```dotenv
GILBOM_LLM_API_KEY_SECRET_FILE=./secrets/gilbom_llm_api_key
```

권장 permission:

```bash
chmod 0700 secrets
chmod 0444 secrets/gilbom_llm_api_key
```

### 환경변수

```dotenv
GILBOM_LLM_PROVIDER=GMS
GILBOM_LLM_BASE_URL=https://gms.ssafy.io/gmsapi/api.openai.com/v1
GILBOM_LLM_MODEL=________________
GILBOM_LLM_CONNECT_TIMEOUT=3s
GILBOM_LLM_READ_TIMEOUT=30s
GILBOM_LLM_MAX_OUTPUT_TOKENS=1500
GILBOM_LLM_DAILY_REQUEST_LIMIT=________________
GILBOM_LLM_DAILY_BUDGET=________________
GILBOM_LLM_MAX_CONCURRENT_REQUESTS=5
GILBOM_LLM_POLICY_APPROVED=________________
GILBOM_LLM_TRAINING_EXCLUSION_APPROVED=________________
GILBOM_LLM_DATA_RETENTION_APPROVED=________________
GILBOM_LLM_OUTBOUND_ALLOWLIST_APPLIED=________________
```

이미지를 LLM 입력으로 사용할 경우 얼굴·차량번호·EXIF 등 비식별화 승인 결과도 확인한다. 승인 전에는 관련 flag를 임의로 `true`로 바꾸지 않는다.

### 활성 조건과 실패 동작

Provider, 정확한 base URL, 허용 model, API Key, timeout, output/concurrency, 양수인 요청 한도·예산, prompt version, 네 가지 정책 승인, outbound allowlist가 모두 유효해야 실제 GMS client가 활성화된다. 하나라도 빠지면 일반 보고서 API는 유지되며 template fallback이 사용된다.

현재 `compose.prod.yaml`은 `GILBOM_LLM_ENABLED=true`, prompt `report-v3`, 이미지 입력 관련 두 flag를 직접 설정한다. 실제 GMS 호출 여부는 나머지 정책 gate와 Secret 상태로 확인한다.

### 검증

- 일반 시연에서는 결함 상세의 `보고서 생성` 후 결과가 `LLM`인지 `TEMPLATE` fallback인지 화면과 Backend log로 확인한다.
- 실제 GMS canary는 승인된 Key/예산이 있는 환경에서만 수행한다.
- Prompt, 응답 원문, image base64, Authorization header를 log/문서에 복사하지 않는다.

### 환경변수


### 발급

운영 domain DNS와 inbound 80이 먼저 준비되어야 한다.

```bash
sudo env \
  DEPLOY_DIR="$PWD" \
  COMPOSE_FILE="$PWD/compose.prod.yaml" \
  ENV_FILE="$PWD/.env.prod" \
  sh infra/certbot/certificate.sh issue
```

발급 후 `dry-run`과 systemd 갱신 timer를 확인한다. private key나 `/etc/letsencrypt` 전체를 Git에 올리지 않는다.

## 6. Mattermost Incoming Webhook

### 실제 사용 위치

- Jenkins CI/deploy/rollback 결과 알림
- Prometheus Alertmanager warning/critical 알림
- Jenkins credential ID: `gilbom-mattermost-webhook`
- Alertmanager Secret 파일 변수: `ALERTMANAGER_WEBHOOK_SECRET_FILE`
- 저장소에 설정된 Alertmanager channel: `d101_alertmanager`
- CI 안내 문서에 정의된 channel: `gilbom-cicd`

두 channel이 실제 Mattermost에 존재하는지는 다음 값으로 확인한다.

```text
CI/CD channel 실제 이름: __________________________________
Alertmanager channel 실제 이름: ___________________________
Mattermost server URL: ____________________________________
Webhook 소유자: ___________________________________________
```

공식 Incoming Webhook 문서:

https://developers.mattermost.com/integrate/webhooks/incoming/

### 생성 절차

1. Mattermost `Product menu > Integrations > Incoming Webhooks`를 연다.
2. `Add Incoming Webhook`을 선택한다.
3. 이름과 수신 channel을 선택한다.
4. 생성된 `https://<mattermost>/hooks/<secret>` URL을 한 번 복사한다.
5. Jenkins에는 `Secret text`, ID `gilbom-mattermost-webhook`으로 등록한다.
6. Alertmanager용 URL은 mode `0600` host Secret 파일 한 줄로 저장한다.

Webhook URL을 아는 사람은 channel에 메시지를 쓸 수 있으므로 Git, `.env`, Jenkinsfile, 채팅, 화면 캡처에 노출하지 않는다.

| Docker Hub 또는 승인 OCI mirror | Corretto, Node, Nginx, Alpine, PostGIS, Mosquitto, Certbot image |

```text
운영 OCI registry/mirror: _________________________________
Registry 계정 필요 여부: _________________________________
Registry credential ID/보관 위치: _________________________
```

운영 release는 가능하면 mutable `latest`가 아니라 Commit SHA tag와 image digest를 기록한다. 외부 registry 인증정보는 `.env.prod`나 Dockerfile에 넣지 않고 host credential store 또는 CI credential을 사용한다.
