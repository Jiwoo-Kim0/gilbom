## 1. 배경

상세 카드의 증거 사진은 카드 폭(340px)에 맞춰 줄어든다. 점자블록 파손은 블록 한두 장

상자 안이 뭉개져 보인다.

## 3. 설계 판단과 그 이유

### 3.1 배율을 CSS class 단계로 둔 이유는 CSP다

`style-src 'self'`라 inline style을 쓸 수 없다. `transform: scale(1.37)`처럼 계산된 값을
넣는 흔한 구현이 막힌다(`scripts/verify-frontend-csp-source.sh`가 소스 단계에서 잡는다).

그래서 배율을 **class로 표현할 수 있는 단계**로 정했다.
`defectPhotoZoom.ts`가 단계 계산을, `App.css`의 `.defect-photo-zoom-*`가 폭을 맡는다.
둘 중 한쪽만 고치면 그 단계가 조용히 ×1로 보이므로, 단위 시험이 **모든 단계에 짝이 되는
클래스 이름이 있는지** 확인한다.

### 3.2 이동은 직접 계산하지 않고 스크롤에 얹었다

확대된 사진을 `overflow: auto` 상자에 담고, 끌면 `scrollLeft/scrollTop`을 옮긴다
(스크롤 위치 변경은 style 변경이 아니라 CSP와 무관하다). 브라우저가 주는 스크롤이라
키보드·트랙패드·스크롤바가 그대로 동작하고, 경계 처리도 공짜로 얻는다.

### 3.3 단계 간격은 20%p다

처음에는 ×1 → ×1.5 → ×2 → ×3 → ×4로 뒀는데 **한 번 누를 때 너무 많이 확대됐다.** 사진에서
파손 부위를 찾는 동작은 조금씩 키우며 맞추는 일이라, 부위를 맞추는 구간(×2 이하)을
20%p로 좁혔다.

```
×1 ×1.2 ×1.4 ×1.6 ×1.8 ×2   ×2.4 ×2.8 ×3.2 ×3.6 ×4
└──────── 20%p ─────────┘   └───── 40%p ─────┘
```

위쪽은 40%p다. 크게 확대한 뒤에는 한 단계의 체감이 작아지는데, 전 구간을 20%p로 두면
×4까지 열여섯 번을 눌러야 한다. 단위 시험이 **×2 이하 구간의 간격이 20%p를 넘지 않는지**
확인한다 — "너무 많이 확대된다"로 돌아오지 않게 하는 선이다.

### 3.4 기준 배율은 "화면에서 사진이 가장 커지는 크기"다

폭만 맞추면 세로로 긴 사진이 열자마자 아래가 잘린다. 전체를 보고 부위를 고르려고 창을
연 것이므로 목적이 무너진다. 그래서 ×1은 사진 전체가 들어오는 가장 큰 크기다.

구현은 **사진 상자가 화면 자리를 꽉 채우고, 사진을 그 안에 `object-fit: contain`으로
담는 것**이다. 배율 단계는 그 상자를 `width/height: 120%…400%`로 키운다. 사진 크기를
몰라도 되고, 아래 §4.4의 어림값도 필요 없어진다.

bbox 오버레이는 사진과 똑같이 여백을 둬야 겹치므로 `aspect`(사진 원본 비율)를 받아
`preserveAspectRatio="xMidYMid meet"`으로 맞춘다. 비율은 서버 응답의
`imageWidth`·`imageHeight`가 null일 수 있어 **그려진 이미지의 `naturalWidth`에서 읽는다.**

그 대신 **배율 표시를 퍼센트에서 배수(`×1`)로 바꿨다.** 기준이 원본 픽셀의 100%가
아니므로 `100%`라고 적으면 거짓이 된다.

### 3.5 사진이 화면을 최대한 쓰게 다듬었다

처음 구현은 ×1에서 사진이 화면 폭의 61%밖에 안 됐다. 창 테두리와 여백이 그만큼 먹고
있었다. 세 가지를 손봤다.

- 창 최대 폭 1100 → 1500px, 배경·창 여백을 줄였다(32 → 18, 16 → 12)
- 조작 안내를 별도 줄에서 머리줄 안으로 옮겼다 — 한 줄이 사라진 만큼 사진이 커진다
- 남는 자리(letterbox)를 **어둡게** 깔았다. 밝으면 "카드가 비어 있다"로 읽혀 사진이
  작아 보인다

1280×720 화면에서 사진이 **780×520 → 886×590**(폭 61% → 69%, 높이 72% → 82%)이 됐다.

### 3.6 확대 기준점 — 버튼은 가운데, 휠은 커서

처음에는 배율만 키웠다. 그러면 스크롤이 0에 머물러 **늘 왼쪽 위로만 확대된다** — 가운데
있던 파손 부위가 확대할수록 오른쪽 아래로 달아난다.

기준점을 화면에 고정한다. 계산은 한 줄이다.

```
새 스크롤 = (이전 스크롤 + 기준점) × 배율비 − 기준점
```

기준점은 **보이는 영역 안의 좌표**다. 버튼·키보드는 가운데(`clientWidth / 2`), 휠은 커서
위치(`event.clientX − 상자 left`)다. 지도 확대와 같은 감각이 된다.

두 가지를 조심했다.

- **눌린 시점의 스크롤을 담아둔다.** 축소할 때는 내용이 줄면서 브라우저가 스크롤을 먼저
  자르므로, effect에서 읽으면 이미 늦다.
- **`useLayoutEffect`로 적용한다.** 보통 effect(paint 후)로 하면 한 프레임 동안 왼쪽 위로
  튀는 것이 보인다.

계산은 `anchoredScroll()`로 빼내 단위 시험을 붙였다.

### 3.7 bbox 오버레이를 파일로 빼냈다

확대 창에서도 AI가 지목한 영역이 보여야 한다 — 확대해서 볼 이유가 대개 그것이다.
카드에서 `import`하면 카드 → 확대 창 → 카드로 순환 참조가 되므로 별도 파일로 옮겼다.
오버레이는 `viewBox="0 0 1 1"` 정규 좌표라 어떤 배율에서도 사진과 정확히 겹친다.

## 4. 작업 중 겪은 함정

### 4.1 사진 위에서 끌면 브라우저가 이미지를 드래그한다

`pointerdown`은 들어오는데 `pointermove`가 끊겨 이동이 전혀 안 됐다. `<img>`를 끌면
브라우저가 HTML5 드래그를 시작해 포인터 이벤트를 가져간다. `draggable={false}`와
`preventDefault()`로 막았다. 끌 때 글자·이미지가 선택되지 않도록 `user-select: none`도
함께 줬다.

### 4.2 grid 자식의 `height: 100%`는 행이 `auto`면 순환한다

창이 화면 높이에 갇히지 않아 사진 상자가 1424px까지 자랐다. 상자 안에서 스크롤되지 않으니
확대해도 끌 수 없고, 심지어 상자 중앙이 화면 밖이었다.

배경 `div`가 `display: grid`인데 행이 기본값 `auto`였다. 자식의 `height: 100%`가 내용
기준으로 되돌아 계산돼 아무 제약이 되지 않는다. 행을 `minmax(0, 1fr)`로 못박아 해결했다.

### 4.3 공통 규칙의 `max-width: 100%`가 확대를 무력화했다

기준 배율에서 사진을 상자에 맞추려고 `.defect-photo-frame`에 `max-width: 100%`를 줬더니,
`.defect-photo-zoom-200 { width: 200% }`가 그 상한에 잡혀 **확대가 전혀 되지 않았다**
(폭이 상자 폭 그대로). 상한은 기준 배율 클래스에만 둬야 한다.

### 4.4 `max-height: 100%`는 부모 높이가 확정돼야 해석된다 — 결국 다른 방법으로 갔다

기준 배율에서 사진 높이를 상자에 맞추려 했지만, 사진을 감싼 상자의 높이가 `auto`라
`max-height: 100%`가 무시됐다. 상자 높이를 확정하면 상자가 사진보다 커져 bbox 오버레이가
어긋난다(오버레이는 상자를 기준으로 그린다).

처음에는 높이 상한을 뷰포트 기준 어림값(`calc(100dvh - 200px)`)으로 우회했다. 창의
머리·안내 줄과 여백을 뺀 값인데, 창 구조를 바꿀 때마다 함께 고쳐야 하는 숫자다.

**§3.4의 방식으로 바꿔 그 숫자를 없앴다.** 상자를 화면 자리에 꽉 맞추고 사진을
`object-fit: contain`으로 담으면 높이 계산이 필요 없다. 오버레이만 같은 비율로 여백을 두게
하면 되는데, 그것이 `aspect` prop이다.

## 5. 확인한 것

브라우저에서 직접 조작해 확인했다(임시 스펙, 커밋하지 않음 — §6).

- 카드 사진 클릭 → `role=dialog` 창이 열리고 배율 표시가 `×1`
- **×1에서 넘침 0** (가로·세로 모두). 열자마자 사진 전체가 보인다
- ×1에서 사진 실제 크기 886×590 = 화면 폭의 69%, 높이의 82%
- 한 번 클릭 → `×1.2`, 상자 `scrollWidth 1282 > clientWidth 1068`
- 네 번 더 → `×2`, 상자 `scrollWidth 2136`
- 사진을 (180, 90)만큼 끌면 스크롤도 정확히 (180, 90) 이동
- `0` 키 → `×1`로 복귀, `Esc` → 닫힘
- **확대 기준점**(1220px 상자, ×2로 확대):
  버튼 다섯 번 → `scrollLeft 610` = (2440 − 1220) / 2 → **가운데 고정**.
  왼쪽 25% 지점(305px)에 커서를 두고 휠 → `scrollLeft 305` → **커서 고정**.
  기준점을 넣기 전에는 둘 다 0이었다
- bbox가 사진의 파손 영역과 정확히 겹치는 것을 눈으로 확인(격자 그림으로 시험)

단위 시험은 배율 계산만 본다: 단계 이동, ×2 이하 구간의 간격 상한, 양 끝에서 멈춤,
모르는 값은 기준으로 복귀, 버튼 활성 여부, 클래스 이름 짝, 배수 표시,
그리고 기준점 고정 스크롤(`anchoredScroll`) — 확대·축소·0 이하 자르기.

### 5.1 dev 서버를 띄우는 우회 경로를 하나 더 찾았다

이 확인을 할 때 node_modules가 Windows용으로 바뀌어(팀원이 WSL 셸에서 Windows npm으로
`npm ci`) 컨테이너 dev 서버가 죽어 있었다. 그래서 **프로젝트를 Windows 파일시스템으로
복사해 Windows node로 vite를 띄웠다** — node_modules가 Windows용이니 그쪽에서는 돈다.

```bash
mkdir -p /mnt/c/temp/gilbom-verify
cp -r package.json package-lock.json index.html tsconfig*.json vite.config.ts public src node_modules /mnt/c/temp/gilbom-verify/
printf 'VITE_NAVER_MAP_CLIENT_ID=e2e-map-client\n' > /mnt/c/temp/gilbom-verify/.env
cd /mnt/c/temp/gilbom-verify && "/mnt/c/Program Files/nodejs/node.exe" node_modules/vite/bin/vite.js --host 127.0.0.1 --port 4175
```

**환경변수는 `.env`로 줘야 한다.** WSL 셸에서 `VAR=x` 접두어로 넘겨도 `WSLENV`에 없으면
Windows 프로세스까지 가지 않아, 클라이언트 ID가 비어 지도가 시작부터 오류 상태가 된다
(그러면 상세 카드가 렌더되지 않아 확대 창을 열 수도 없다).

그리고 상세 카드를 열려면 **`naver.maps` 가짜**가 필요하다. `loadNaverMapsScript`는
`window.naver?.maps`가 있으면 네트워크를 타지 않으므로, `addInitScript`로 `Map`·`Marker`·
`LatLng`·`LatLngBounds`·`Point`·`Size`·`Event`·`Position`·`ZoomControlStyle`만 흉내내면 된다
(§6에 남긴 "공용 support로 빼내기"가 이것이다).

## 6. 남은 것

### 내 몫

- **확대 창 e2e를 커밋하지 못했다.** 상세 카드는 `DefectMap` 안에 있고 그 자리는 지도
  스크립트가 로드돼야 렌더된다. 인터넷 없는 환경에서 깨지므로
  [결함-화면-e2e-스펙_작업내용.md](결함-화면-e2e-스펙_작업내용.md) §4.1의 방침대로 뺐다.
  `naver.maps` 가짜를 공용 support로 빼내면 확대 창·상태 드롭다운 e2e를 함께 넣을 수 있다.
- 모바일 핀치 확대는 없다. 터치는 끌어서 이동만 된다.
- 사진이 여러 장인 결함에서 좌우로 넘기는 기능은 없다. 지금은 대표 이미지 한 장만 받는다.

### 다른 팀원 몫

- 없다. `features/defect` 안에서 끝났다.
