# 세션 폐기 트리거 로그 작업내용

기간: 2026-08-08
범위: V14가 만든 세션 폐기 trigger 함수 6개(V43으로 교체). **판정과 삭제 동작은 하나도
바꾸지 않았고** RAISE LOG만 더했다.

관련 문서: [401-한-건이-세션을-파괴하던-문제_작업내용.md](401-한-건이-세션을-파괴하던-문제_작업내용.md)
(804 — §7.2에서 이 trigger들을 "조용히 사라지는 경로"로 지목했다),
[지도-묶음-401-로그아웃_작업내용.md](지도-묶음-401-로그아웃_작업내용.md) (802)

## 1. 왜 필요했나

804에서 entry point에 로그를 넣어 `cookieValid=false`(쿠키는 보냈는데 서버에 세션이 없다)를
볼 수 있게 됐다. 그런데 **거기서 멈춘다** — 세션이 idle로 만료된 것인지 누가 지운 것인지
구분이 안 됐다.

세션 행이 애플리케이션 로그를 한 줄도 남기지 않고 사라지는 경로가 셋인데, 그중 가장
소리 없는 것이 **V14의 DB trigger 7개**였다. DB 안에서 벌어지는 일이라 backend는 알지
못한다.

## 2. 실증 — trigger 하나가 로그인된 사용자를 즉시 로그아웃시킨다

로컬 DB에서 직접 확인했다. 세션 한 건을 만들어두고 `auth.user_robot_assignment`에
**INSERT 한 번**을 했다.

```
session_before = 1
INSERT 0 1
session_after  = 0
```

이유는 둘이 겹친 것이다.

- `auth.revoke_user_authorization_sessions`는 그 사용자의 **모든 세션을 지운다.**
  현재 세션을 제외하지 않는다.
- `revoke_sessions_on_user_scope_change`에는 **값 비교 가드가 없다.**
  `admin_user` 쪽 trigger는 `IS DISTINCT FROM`으로 실제 값이 바뀔 때만 발동하는데,
  이쪽은 행이 건드려지기만 하면 발동한다.

```sql
CREATE TRIGGER tr_user_robot_assignment_revoke_sessions
    AFTER INSERT OR UPDATE OR DELETE
    ON auth.user_robot_assignment
    FOR EACH ROW
    EXECUTE FUNCTION auth.revoke_sessions_on_user_scope_change();
```

즉 관리자 화면에서 로봇 배정을 저장하면(`AdminRepository.replaceRobotAssignments`는
전체를 비활성화한 뒤 다시 INSERT한다) 대상 사용자는 **그 자리에서 로그아웃된다.**
권한이 바뀌었으니 폐기 자체는 의도된 동작이다. 문제는 **아무도 그 사실을 모른다**는
것이었다.

## 3. 무엇을 바꿨나

`V43__log_session_revocation_triggers.sql`이 trigger 함수 여섯 개를
`CREATE OR REPLACE` 한다.

| 함수 | 대상 표 |
| --- | --- |
| `revoke_sessions_on_user_role_change` | `user_role` |
| `revoke_sessions_on_role_permission_change` | `role_permission` |
| `revoke_sessions_on_role_lifecycle_change` | `role` |
| `revoke_sessions_on_permission_change` | `permission` |
| `revoke_sessions_on_user_scope_change` | `user_permission_override`, `user_robot_assignment` |
| `revoke_sessions_on_account_lifecycle_change` | `admin_user` |

바뀐 것은 두 가지뿐이다. `PERFORM`을 대입으로 바꿔 삭제 건수를 받고, 0보다 클 때
로그를 남긴다.

```
LOG:  session revoked by trigger: table=user_robot_assignment, op=INSERT,
      user=b66358df-…, sessions=1
```

**실제로 폐기된 세션이 있을 때만 남긴다.** 로그인한 사용자가 없는 대상에 대한 평범한
관리 작업까지 남기면 소음만 늘고 정작 찾는 줄이 묻힌다.

### 왜 감사 표가 아니라 로그인가

새 표를 만들면 `SECURITY DEFINER` 함수 여섯 개에 INSERT 권한을 주고 보존 정책까지
정해야 한다. 지금 필요한 것은 "그 시각에 trigger가 지웠나"를 가리는 것뿐이고, db
container 로그는 이미 Alloy가 Loki로 보내고 있다.

### 손대지 않은 것

가드 없이 발동하는 것(§2)은 **그대로 뒀다.** 권한 입력값을 다시 쓰는 것도 stale
authority로 볼 여지가 있고, 보안 판정을 바꾸는 것은 이 작업의 범위가 아니다.
다만 이제 그 사실이 로그에 드러난다.

## 4. 확인한 것

**로컬 DB에서 로그가 실제로 찍히는 것까지 확인했다**(§2의 출력이 그것이다).
마이그레이션 적용도 `psql`로 직접 돌려 확인했다.

**회귀 시험 1개 추가** — `SessionRevocationFunctionPrivilegeIntegrationTest`에
`authorizationChangeRevokesTheUsersSession`. 세션을 하나 심어두고
`user_permission_override`를 넣으면 그 세션이 사라지는지 본다. 함수 여섯 개를 다시 썼으니
**삭제 동작이 그대로인지**를 못박는 것이 목적이다.

`user_robot_assignment`가 아니라 `user_permission_override`를 쓴다 — 같은 함수를 타지만
migration이 `robot.robot`을 시드하지 않아 FK를 채울 수 없다.

## 5. 이제 원인을 어떻게 가리나

`/defects/map`이 401이고 사용자가 로그인 화면으로 튕겼을 때:

| backend 로그 (804) | db 로그 (805) | 결론 |
| --- | --- | --- |
| `cookieValid=false` | `session revoked by trigger`가 **같은 시각에 있다** | trigger가 지웠다 — 누가 그 표를 건드렸는지 본다 |
| `cookieValid=false` | 없다 | **idle 30분 만료**다 |
| `cookieValid=false` | 없고 비밀번호 변경 기록이 있다 | 전체 세션 폐기 |
| `sessionCookie=false` | — | 브라우저가 쿠키를 안 보냈다 |
| `liveSession=true` | — | 세션은 살아 있는데 인증 컨텍스트가 없다 |

db 로그는 backend와 다른 container다.

```sh
sudo docker compose --project-directory /opt/gilbom/deploy \
  --env-file /opt/gilbom/deploy/runtime.env \
  --env-file /opt/gilbom/deploy/image.env \
  -f /opt/gilbom/deploy/compose.prod.yaml \
  logs --no-color --since 24h db 2>&1 | grep 'session revoked by trigger'
```

## 6. 남은 것

### 내 몫

- 아직 **원인을 확정하지 못했다.** 802·803·804·805는 전부 "증상을 줄이거나 다음 발생을
  특정할 수 있게" 한 것이지, 사용자가 겪은 그 401이 무엇이었는지는 다음 재현에서 갈린다.
- SSE emitter 타임아웃(30분)이 세션 idle 타임아웃(30분)과 같아 탭만 열어두면 세션을
  갱신하는 요청이 하나도 없다. 아직 손대지 않았다. 고치려면 30분 규칙을 무력화하지 않는
  쪽(만료 예고)이어야 한다.

### 알아둘 것

- `RAISE LOG`는 postgres의 `log_min_messages` 기본값(`warning`)에서도 서버 로그에
  기록된다. 이 값을 올리면 로그가 사라진다.
- trigger는 **자기 트랜잭션 안에서** 세션을 지운다. 관리 작업이 롤백되면 폐기도 함께
  롤백되지만, 로그 줄은 이미 남는다. 로그가 있는데 세션이 살아 있으면 롤백된 것이다.
