## 3. 설계 판단과 그 이유

### 3.1 `<select>`을 걷어낸 이유

선택지가 넷뿐이다. 접어두면 **열어봐야 알고**, 지금 값이 무엇인지도 한 줄 안에서만 보인다.
펼쳐 놓으면 고를 것과 고른 것이 한눈에 들어오고, 무엇보다 **필터 모달과 같은 언어**가 된다.

요소는 `<input type="radio">` 그대로다. 버튼으로 바꾸면 "하나만 고른다"·방향키 이동·
`aria-checked`를 직접 만들어야 한다. 라디오는 공짜로 준다 — 감춘 것은 동그라미 표식뿐이고
포커스는 살아 있다(`opacity: 0` + 크기 0).

### 3.2 알약 CSS는 필터와 한 곳에서 쓴다

필터의 다중 선택(`.defect-filter-checkbox`)과 여기의 단일 선택(`.defect-choice`)은
**같은 모양이어야 한다.** 규칙을 복사하면 한쪽만 고쳐진다. 그래서 선택자를 쉼표로 묶어
한 블록에 뒀다. 클래스 이름을 둘로 나눈 것은 쓰이는 자리를 코드에서 읽히게 하려는 것뿐이다.

### 3.3 고른 심각도는 목록 표의 배지와 같은 색

같은 값이 화면마다 다른 색이면 눈이 짝을 못 짓는다. `.defect-risk-*` 배지 팔레트를 그대로
가져와 고른 알약에 입혔다.

**문제는 "낮음"이었다** — 배지 색이 회색이라 고른 것이 안 골라진 것과 구분되지 않았다.
테두리를 두껍게 하면 알약 크기가 달라져 줄이 덜컥이므로, `box-shadow: inset 0 0 0 1px
currentcolor`로 테두리를 한 겹 더 그렸다. 크기는 그대로고 옅은 색에서도 고른 것이 보인다.

### 3.4 체크박스 → 스위치

"재검토 필요"는 켜짐·꺼짐이 즉시 읽혀야 하는 값이다. 작은 네모 하나보다 손잡이 위치가
훨씬 빠르다. 요소는 체크박스 그대로여서 키보드·스크린리더 동작은 변하지 않는다
(`getByRole('checkbox', { name: /재검토 필요/ })`로 여전히 찾힌다 — e2e가 지킨다).
설명 한 줄을 붙여 무엇을 표시하는 것인지 알 수 있게 했다.

### 3.5 저장이 막힌 이유를 버튼 옆에 둔다

흐려진 버튼만으로는 무엇이 모자란지 알 수 없다. 두 단계로 말이 바뀐다.

1. 아무것도 안 바꿨다 → "아직 바꾼 항목이 없습니다."
2. 바꿨지만 사유가 없다 → "수정 사유를 적어야 저장할 수 있습니다."
3. 다 됐다 → "저장하면 변경 이력에 기록됩니다."

`role="status"`라 스크린리더도 바뀔 때 읽는다. 사유 칸에는 `*`와 글자 수(22/1000)를 붙였다.

### 3.6 순수 계산을 `.ts`로 뺀 이유

`buildDefectUpdateRequest`(바뀐 축만 담기)는 이 창에서 **가장 틀리기 쉬운 부분**인데
컴포넌트 안에 있어 시험할 수 없었다. `defectEditForm.ts`로 옮겨 단위 시험 4개를 붙였다.
컴포넌트 파일이 순수 함수를 함께 내보내면 eslint(`react-refresh/only-export-components`)도
막는다 — 이 저장소에서 세 번째로 만난 규칙이다.

## 4. 작업 중 겪은 함정

### 4.1 저장이 아무 반응도 없었다 — CSRF 스텁 누락

e2e에서 저장을 눌러도 PATCH가 **한 번도 나가지 않았다.** `apiClient`는 POST·PATCH·PUT·
DELETE 앞에 `/api/v1/auth/csrf-token`을 먼저 받아오는데, 새로 만든 스텁이 그것을 404로
답하고 있었다. 요청 로그를 찍어(`page.on('request')`) 비-GET 요청이 아예 없는 것을 보고
알았다.

**결함 화면에서 쓰기 동작을 e2e로 볼 때는 `csrf-token`을 반드시 막아야 한다.**
`e2e/mission-time.spec.ts`가 같은 것을 이미 하고 있었다. 이번에는 보낸 헤더까지
(`x-csrf-token`) 단정에 넣었다.

### 4.2 목록 스펙이 전체 실행에서만 깨졌다 (내 변경과 무관)

`defect-list.spec.ts`의 `행을 고르면 지도까지 화면이 올라간다`가 **전체 스위트에서만**
실패했다(단독 실행은 통과). 원인은 그 시험의 대기 조건이었다 — 부드러운 스크롤이
`top >= 0`이 되는 순간 통과시키고, 그 다음 줄에서 `>= 상단 바 높이(100)`를 요구한다.
미끄러지는 중간 값(41px)을 읽으면 실패한다.

도착 지점(`top - 상단 바 높이 >= -1`)까지 기다리도록 고쳤다. 전체 스위트 47개를 두 번
연달아 돌려 확인했다.

**부드러운 스크롤을 기다릴 때는 "움직이기 시작했나"가 아니라 "도착했나"를 봐야 한다.**

## 7. 2차 — 창이 상단 바 뒤로 깔려 있었다 (같은 날)

창을 열면 **제목 줄이 고정된 상단 바에 잘렸고**, 화면을 덮는 어두운 막이 상단 바만
비껴가 그 줄만 환하게 남았다.

### 7.1 원인은 z-index 하나

| 층 | 값 |
| --- | --- |
| 왼쪽 바 `.nb-sidebar` | 40 |
| 상단 바 `.topbar` | 50 |
| 필터 모달 `.defect-filter-modal-backdrop` | 60 |
| **결함 수정·병합 모달 `.defect-modal-backdrop`** | **40 → 150** |
| 사진 확대 창 `.defect-photo-backdrop` | 200 |

`40`이라 상단 바(50)에 졌다. 필터 모달은 60이라 처음부터 문제가 없었고, 사진 확대 창은
200이라 마찬가지였다 — **이 창만 홀로 낮았다.**

`document.body`로 portal하고 있어서 DOM 순서로는 가장 마지막인데도 소용이 없다.
**z-index가 DOM 순서를 이긴다.** portal은 stacking context에 갇히는 것을 막아줄 뿐이고,
층 번호는 따로 정해야 한다.

값을 150으로 둔 이유: 두 바(40·50)보다 확실히 위이고, 사진 확대 창(200)보다는 아래여야
한다 — 상세 카드에서 사진을 크게 볼 때 그쪽이 위로 와야 맞다. 앞으로 헷갈리지 않게 층
순서를 CSS 주석에 표로 남겼다.

### 7.2 눈으로 보지 말고 재서 확인했다

스크린샷만 보고는 "막이 덮였는가"를 잘못 읽기 쉽다(55% 막은 축소된 그림에서 그냥 회색
배경처럼 보인다). 두 가지로 확인했다.

1. `document.elementFromPoint(상단 바 중앙)`이 이 창 안의 요소인가 → e2e로 고정.
2. 스크린샷 픽셀을 직접 읽어 상단 바·왼쪽 바·본문이 모두 `rgb(123,128,138)`
   (= 흰 바탕에 `#0f172a` 55%)인지, 창만 `rgb(255,255,255)`인지 확인.

### 7.3 e2e 1개 추가 (수정 창 6개, 결함 전체 48개)

`고정된 상단 바보다 앞에 나오고 상단 바까지 덮는다` — 상단 바·왼쪽 바 자리에서 이 창이
가장 위인지, 막이 화면 전체를 덮는지, **층 번호가 두 바보다 큰지**를 함께 못박았다.
숫자 단정을 넣은 이유는, 창이 커서 우연히 상단 바 자리를 가리는 경우와 정말 위에 있는
경우를 구분하기 위해서다.

`elementFromPoint`가 돌려주는 것이 막일 수도, 창 카드일 수도 있어(창이 크면 카드가 그
자리를 차지한다) `overlay.contains(...)`로 판정한다. 처음에는 막만 기대해 실패했다.
