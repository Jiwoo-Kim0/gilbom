## 1. 배경

보고서 방향이 **"기간 기준"에서 "결함 단건 기준"으로** 정해졌다(7/31). 그런데 구현은
기간 기준이라, 결함 카드에서 "리포트 생성"을 눌러도 그 결함의 정보로 만들어지지 않았다.

**증상은 조용한 실패였다.** `ReportLlmRequestFactory`가
`findReportImages(userId, from, to, 1)`로 *기간 내 위험도 최상위* 결함의 이미지를 가져온
뒤, `matchesEvidence()`로 근거 결함과 대조해 불일치면 제거한다. 단건 보고서에서는 근거가
그 결함 하나뿐이므로 대개 불일치 → **이미지 없는 보고서**가 되고 에러도 나지 않는다.

보고서는 원래 A의 도메인이라 이관 요청만 해두었는데, 8/1에 **"보안은 건드리지 말고 생성
자체는 수정해도 된다"**는 결정이 나와 직접 마무리했다.

## 3. 설계 판단과 그 이유

### 3.1 통계는 좁히지 않았다

단건 보고서라고 통계까지 그 결함 하나로 줄이면 "결함 수 1, 상태 1건"이 되어 의미가
없어진다. **통계는 필터링을 돕는 값이지 단건 보고서의 본문이 아니다.**

그래서 집계 CTE(`visible_defects` 기반)는 그대로 두고 **근거 결함을 고르는 `top_defects`
에만** 필터를 걸었다.

```sql
WHERE CAST(:defectId AS uuid) IS NULL
   OR defect.defect_id = CAST(:defectId AS uuid)
```

결과적으로 LLM은 "이 기간의 전체 현황 + 이 결함 상세"를 함께 받는다. 저장소 쿼리 변경도
두 줄로 끝나 위험이 낮다.

### 3.2 이미지를 기간이 아니라 **근거 결함에서** 고른다

이게 이번 작업의 핵심이다. 기존 구조는 이미지를 독립적으로 선택한 뒤 근거와 대조해
버리는 방식이라, 어긋나면 조용히 사라졌다.

```java
prepared.source().defectEvidence().stream()
        .limit(CURRENT_MAX_IMAGES)
        .flatMap(evidence -> imageService.get()
                .findReportImagesForDefect(actorUserId, evidence.defectId())
                .stream())
```

근거에서 직접 가져오므로 **단건이든 기간이든 이미지가 항상 근거와 일치**한다.
단건 보고서만 고치는 게 아니라 기간 보고서의 잠재적 불일치까지 함께 없앤다.

`matchesEvidence()` 검증은 지웠어도 됐지만 **안전망으로 남겼다.** 앞으로 이미지 선택이
바뀌어도 근거와 다른 이미지가 외부로 나가지 않는다.

`evidenceById`가 아니라 `source().defectEvidence()`를 쓴 이유는 순서다. 전자는
`toUnmodifiableMap`이라 순서가 없고, 후자는 `top_defects`의 위험도 순 정렬을 유지한다.

### 3.3 보안 경계는 넘지 않았다

지시받은 대로 다음은 손대지 않았다.

- LLM 정책 게이트 (`LlmProperties.isImageInputAllowed`, 승인 플래그)
- Secret·API 키 주입
- `GeneratedReportTextGuard` (출력 정화)
- 멱등성·CSRF·권한 (`ReportAccessService`)
- `matchesEvidence` 검증

`filterCriteria`에 필드를 하나 더한 것도 **allowlist 방식을 그대로 유지**했다.
`ALLOWED_FIELDS`에 `defectId`를 추가했을 뿐 임의 키를 허용하지 않는다.

### 3.5 대상 결함을 **필수로** 만들었다 (커밋 `0fb1555`)

여기까지 하고 나니 구멍이 하나 남았다. 결함 카드에서 들어오면 `defectId`가 붙지만,
**보고서 목록의 "새 보고서" 버튼으로 들어오면 안 붙는다.** 그러면 `defectId`가 없는
채로 LLM 생성이 돌아가 예전처럼 기간 전체를 근거로 하는 보고서가 만들어진다.

우리 제품에 기간 보고서는 없다. 그래서 **선택값이 아니라 필수값으로 바꿨다.**

```java
// ReportGenerationDataService.prepare()
if (!criteria.isSingleDefect()) {
    throw new BusinessException(
            ErrorCode.REPORT_VALIDATION_FAILED,
            "LLM 보고서는 대상 결함을 지정해야 합니다.");
}
```

`filterCriteria`를 파싱한 직후라 우회 경로가 없다. **수동·템플릿 보고서는 이 경로를
타지 않아 영향이 없다** — 사람이 직접 쓰는 보고서까지 결함에 묶으면 안 된다.

화면에서도 같이 막았다. 결함 없이 들어오면 LLM 선택지를 비활성화하고
`결함 상세에서 "리포트 생성"으로 시작하세요`를 띄운다. 기본 생성 방식도 갈린다 —
결함이 있으면 LLM, 없으면 수동이다.

**"새 보고서" 버튼 자체는 남겼다.** 수동·템플릿 보고서는 여전히 목록에서 만드는 게 맞다.

> 서버에서 막으면 충분한데 화면까지 손댄 이유는, 서버 검증만 있으면 사용자가 LLM을
> 고르고 폼을 다 채운 다음에야 422를 보게 되기 때문이다. 고를 수 없게 하는 편이 낫다.

### 3.4 편집 화면에 무엇을 근거로 만드는지 표시한다

`?defectId=`로 들어오면 "결함 INC-… 한 건을 근거로 생성합니다. 통계는 아래 기간 전체를
기준으로 집계됩니다."를 띄운다. 사용자가 기간을 바꿀 수 있는 화면에서 **근거는 결함 한
건이고 통계만 기간을 따른다**는 것이 드러나지 않으면 혼란스럽다.

## 4. 작업 중 겪은 함정

### 4.1 A의 테스트가 호출 자체를 검증하고 있었다

`ReportLlmRequestFactoryTest`가 `verify(imageService).findReportImages(USER_ID, FROM, TO, 1)`
로 **어떤 메서드를 부르는지**를 검증한다. 이미지 선택 방식을 바꾸니 당연히 깨졌다.

→ 스텁·검증을 `findReportImagesForDefect`로 바꾸고(4곳), 쓰이지 않게 된 `FROM`·`TO`
상수와 `Instant` import를 정리했다. **동작 변경에 따른 수정이지 테스트를 느슨하게 만든
것이 아니다** — 여전히 "어떤 결함의 이미지를 부르는가"를 검증한다.

남의 도메인 코드를 고칠 때는 **그 도메인 테스트가 무엇을 고정하고 있는지 먼저 보는 편이**
빠르다. 이번엔 전체 스위트를 돌리고 나서야 알았다.

### 4.2 `Map`은 순서를 보장하지 않는다

`prepared.evidenceById()`로 상위 N건을 뽑으려 했는데, `toUnmodifiableMap`이라 순서가
없다. 위험도 순으로 정렬된 것은 `source().defectEvidence()` 리스트 쪽이다.
그대로 갔으면 "상위 1건"이 매번 달라졌을 것이다.

## 5. 미완 항목

### 확인 필요

- **실제 LLM 호출로 이미지가 실려 가는지** — `GILBOM_LLM_ENABLED`와 정책 승인 플래그가
  꺼져 있으면 템플릿으로 생성되고 이미지는 실리지 않는다. **A의 보안 설정 영역**이라
  건드리지 않았다. 켠 환경에서 한 번 확인해야 한다
- 결함 카드 → 리포트 생성 → 편집 화면 프리필까지의 브라우저 확인

### 테스트 공백

`prepare()`에 **직접 들어가는 테스트가 없다.** §3.5에서 넣은 필수화 규칙도 테스트로
고정돼 있지 않다.

확인해보니 `ReportControllerTest`는 `commandService`를,
`ReportApplicationServiceIntegrationTest`는 `generationDataService` 자체를 mock한다.
즉 **기간 기준 생성을 실제로 검증하던 테스트가 원래 없었다.** 그래서 이번 변경으로
깨진 테스트도 없었다(764 tests / 0 failures).

바꿔 말하면 이 경로는 계속 테스트 밖에 있었다. 나중에 누가 `defectId`를 선택값으로
되돌려도 아무도 모른다. 저장소가 실제 DB를 타서 통합 테스트가 필요하다(약 40분).

### 후속으로 볼 만한 것

- 단건 보고서에 **결함의 반복 관측 이력**을 근거로 넣을지. 지금은
  `DefectEvidence`(유형·위험도·상태·`lastSeenAt`·`locationLabel`)만 간다.
  좌표·AI 신뢰도·모델 버전·관측 횟수는 LLM 입력 allowlist에 없다
- `CURRENT_MAX_IMAGES = 1`. 단건 보고서라면 그 결함의 관측이 여러 건일 때
  2~3장을 보내는 선택지도 있다. 조회 쪽(`findReportImagesForDefect`)은 0~1개만 준다

### A와 공유할 것

보고서 생성 경로를 수정했으므로 알려야 한다. 특히 **이미지 선택 방식이 바뀐 것**과
**`ReportLlmRequestFactoryTest`를 고친 것** 두 가지다.
