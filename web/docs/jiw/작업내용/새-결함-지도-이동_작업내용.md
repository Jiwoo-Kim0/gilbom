# 새 결함이 들어왔을 때 지도 이동 작업내용

기간: 2026-08-07
범위: 결함 지도(`DefectMap`)와 결함 화면(`DefectManagePage`)의 실시간 반응.
새 결함이 **화면 밖일 때만** 그 위치로 지도를 옮긴다.

관련 문서: [결함-API와-SSE_작업내용.md](결함-API와-SSE_작업내용.md)(SSE 계약),

## 1. 무엇을 만들었나

로봇이 새 결함을 올리면 목록과 마커는 갱신됐지만 **어디에 생겼는지 알 수 없었다.** 화면
밖이면 알림 줄만 뜨고 지도는 그대로였다.

이제 새 결함이 **지금 보이는 범위 밖일 때만** 그 위치로 지도를 옮기고, **알아볼 배율까지
확대한다.** 이미 보이는 자리에 생겼으면 **움직이지도 확대하지도 않는다** — 보고 있던 위치를
이유 없이 빼앗지 않는다.

---

## 2. 좌표를 어디서 얻나 — SSE에는 위치가 없다

`DefectSseEventResponse`에는 좌표가 없다. 계약(24장)이 "이벤트는 변경 알림만 주고
클라이언트는 REST로 다시 조회한다"이기 때문이다. 그래서 지도가 직접 찾는다.

```ts
getDefectMap({ ...filtersRef.current, bbox: '' })   // 뷰포트 bbox 없이
  .then((response) => response.features.find((f) => f.properties.defectId === id))
```

**bbox를 걸지 않는 것이 요점이다.** 평소 지도 조회는 뷰포트 bbox로 걸러 받는데, 지금 찾는
것은 바로 그 **화면 밖에 있는 결함**이라 bbox를 걸면 응답에 아예 없다.

세 가지 선택지 중에서 이 방법을 골랐다.

| 방법 | 문제 |
| --- | --- |
| `getDefect(defectId)` 상세 조회 | 좌표는 오지만 **지금 필터에 맞는지 알 수 없다.** 필터에 걸려 그려지지도 않을 마커로 화면을 끌고 가면 사용자는 빈 지도를 본다. 필터 판정을 프론트에서 다시 구현하는 것은 서버와 어긋나기 쉽다 |
| 평소 조회(bbox 있음) 결과에서 찾기 | 화면 밖 결함은 응답에 없다 — 이 기능이 성립하지 않는다 |
| **bbox 없이 지도 조회 한 번**(택함) | 요청이 한 번 더 나간다. 대신 **서버 필터를 그대로 쓴다** — 지금 조건에 맞지 않으면 응답에 없어서 지도가 움직이지 않는다 |

이 응답으로 마커를 바꾸지는 않는다. 찾는 목적뿐이다. 지도를 옮기면 `idle`이 오고, 그때
뷰포트 bbox로 정상 조회가 다시 돌아 마커가 올라온다.

## 3. "화면 밖"의 기준 — 가장자리에 걸친 것도 밖이다

`isPointOutsideMapView(point, view)`를 순수 함수로 뺐다(`defectMapState.ts`).

```ts
const latitudeMargin = (view.north - view.south) * 0.08
```

경계에서 **폭·높이의 8% 안쪽까지는 "밖"으로 친다.** 마커(44px)가 딱 경계에 걸리면 반쯤
잘려서, 사용자에게는 "새 결함이 왔다는데 어디 있는지 안 보인다"가 된다.

판단을 지도가 하는 이유는 단순하다 — **지금 보이는 범위를 아는 쪽이 지도다.** 페이지는
"이 결함이 새로 생겼다"만 내려보낸다(`revealRequest`).

```tsx
<DefectMap revealRequest={revealRequest} … />
```

`revealRequest`는 `lastEvent`가 바뀔 때마다 새 객체가 되므로, 같은 결함이 다시 들어와도
지도가 반응한다. `defect.created`만 대상이다 — 상태가 바뀐 결함(`defect.updated`)으로
화면을 옮기면 남이 처리한 건 때문에 내 화면이 튄다.

---

## 3.1 옮기기만으로는 부족하다 — 확대까지

넓게 보고 있었다면 마커가 화면에 들어와도 **어느 길인지 알 수 없다.** 그래서 옮긴 뒤
`REVEAL_ZOOM`(17)까지 확대한다. 17이면 1px이 약 1.2m라 블록 하나가 구분된다 — "어디에
생겼는지"를 알아볼 수 있는 가장 얕은 배율이고, 더 깊이 넣으면 주변 맥락이 사라진다.

**줄이지는 않는다.**

```ts
revealZoom(currentZoom) = max(currentZoom, min(REVEAL_ZOOM, 지도 최대 배율))
```

이미 19에서 보고 있었다면 그대로 둔다. 사용자가 확대해 둔 것을 되돌리는 것은 화면을
빼앗는 것과 같다.

**순서는 옮기기 → 확대다.** 먼저 확대하면 아직 옛 중심이라 엉뚱한 자리를 파고들고, 그
다음 이동이 튀어 보인다.

---

## 4. 곁들여 고친 것 — 지도가 재조회 신호를 못 받고 있었다

`DefectMap`의 `reloadToken` prop은 "SSE로 새 결함이 오면 지도도 다시 읽어라"는 신호인데,
**페이지가 그 값을 넘기지 않고 있었다.** 그래서 새 결함 마커가 새로고침 전까지 올라오지
않았다. 한 줄을 이었다.

```tsx
reloadToken={reloadToken}
```

이번에 만든 e2e 두 개 중 하나가 이 줄이 없으면 실패한다(이벤트가 마커까지 도달하는 것을
전제로 세기 때문이다).

## 5. 확인한 것

**단위 시험 6개**(`test/defectUiState.test.ts`): 가운데는 밖이 아니다, 네 방향 이탈은 모두
밖이다(한 방향만 보면 부호 실수를 놓친다), 가장자리 8% 안쪽은 밖으로 친다, 넓게 보고
있었으면 17까지 확대, 이미 깊으면 그대로, 지도 최대 배율을 넘지 않는다. 전체 93 pass.

**e2e 3개**(`e2e/defect-realtime-map.spec.ts`). 지도 SDK와 SSE 가짜를 심고, 시험이 원하는
순간에 `defect.created`를 밀어 넣는다.

| 상황 | 결과 |
| --- | --- |
| zoom 16, 3km 밖 | 중심이 **그 좌표로**(`37.52818, 127.04321`) 옮겨지고 **배율 17**로 확대 |
| zoom 19, 500m 밖 | 옮기지만 **배율은 건드리지 않는다**(`setZoom` 호출 없음) |
| zoom 16, 100m 안 | 중심 이동 **0회**, 배율도 그대로 |

앞의 두 시험은 **기능이 없는 코드에서 실패하는 것까지 확인했다.**

**가짜를 `e2e/support/fakeNaverMap.ts`로 뺐다.** 지도 SDK 가짜 + 시험이 조종하는
`EventSource`(`pushSseEvent`)를 담았다 —
[결함-지도-묶음-확대_작업내용.md](결함-지도-묶음-확대_작업내용.md) §6에 "빼는 것이 낫다"고
적어둔 것을 여기서 했다.

`npm run test:e2e:defect`에 넣었다 — 결함 화면 e2e 40개 통과.
`tsc -b`·`eslint`·CSP 게이트 PASS.

## 6. 남은 것

### 내 몫

- `defect-cluster.spec.ts`는 아직 자기 안에 지도 가짜를 들고 있다(다른 작업이 그 파일을
  동시에 고치고 있어 건드리지 않았다). 그쪽이 정리되면 `support/fakeNaverMap.ts`로 합친다.
- 실제 지도 SDK로는 확인하지 못했다. 로컬에서 지도 스크립트가 받아지지 않는다(네트워크).
  판단에 쓰는 값은 `map.getBounds()`뿐이라 SDK 의존은 얕다.

### 알아둘 것

- 결함이 **연달아** 들어오면 마지막 것으로 옮긴다(`lastEvent` 하나만 본다). 초당 여러 건이
  들어오는 상황에서 화면이 계속 튀면, 그때는 "옮기지 않고 알림 줄에 '보기' 버튼을 두기"가
  더 나을 수 있다.
- 로봇 지도(`RobotMap`)에는 같은 처리가 없다.
