# 401 한 건이 세션을 파괴하던 문제 작업내용

기간: 2026-08-08
범위: `AuthenticationSessionEnforcementFilter`의 거부 처리. 세션 정책(idle 30분·absolute
8시간·단일 세션)과 만료 판정 자체는 그대로다.

관련 문서: [지도-묶음-401-로그아웃_작업내용.md](지도-묶음-401-로그아웃_작업내용.md)
(802 — 같은 증상의 **프론트 쪽** 절반)

---

## 1. 802로 끝나지 않았다

802 배포 뒤에도 지도 묶음을 누르면 로그인 화면으로 튕겼다. 이번에는 401이
`GET /api/v1/defects/map`에서 났다.

배포된 번들에 `cluster-details`가 들어 있는 것을 확인했으므로 **802는 배포돼 있었고,
설계대로 동작했다** — 401을 받고 `/auth/session-state`에 물어봤는데 "끊겼다"는 답이 와서
로그아웃한 것이다. 답이 맞았다. 세션이 정말 없었기 때문이다.

**세션을 없앤 것은 서버였다.**

```java
// AuthenticationSessionEnforcementFilter.rejectAndInvalidate (고치기 전)
repository.deleteBySessionId(sessionId);   // DB에서 세션 행 삭제
session.invalidate();                       // 서블릿 세션 폐기
```

이 필터가 **한 번이라도** 거부하면 세션이 영구히 사라진다. 그 뒤로는 무엇을 해도 401이고,
클라이언트가 아무리 신중하게 재확인해도 결과는 로그아웃이다. 802는 프론트가 401에
과잉반응하지 않게 했을 뿐, **서버가 세션을 파괴하는 경로는 그대로였다.**

## 2. 네 갈래가 한 코드로 뭉쳐 있었다

거부 조건은 넷인데 응답이 전부 같은 401 `AUTH_UNAUTHENTICATED`였다. 로그를 봐도 어느
갈래였는지 알 수 없었다.

| 갈래 | 뜻 | 세션 파괴 (전) | 시험 (전) |
| --- | --- | :---: | :---: |
| `STATE_MISSING` | 보안 상태 행이 없다 — 다른 곳 로그인에 밀렸거나 로그아웃됨 | O | 없음 |
| `EXPIRED` | absolute 8시간 또는 challenge 만료 | O | 있음 |
| `PRINCIPAL_MISMATCH` | 인증 주체가 세션 소유자와 다름 | O | 있음 |
| **`CONTEXT_MISSING`** | **세션은 AUTHENTICATED인데 이 요청에 인증 컨텍스트가 없다** | **O** | **없음** |

"방금 로그인했는데 그런다"는 제보에서 `EXPIRED`는 빠진다. `PRINCIPAL_MISMATCH`는 다른
사용자의 컨텍스트를 들고 와야 한다. 남는 것은 `STATE_MISSING`과 `CONTEXT_MISSING`이고,
**네 갈래 중 유일하게 시험이 없던 것이 `CONTEXT_MISSING`이었다.**

## 3. 무엇을 바꿨나

### 3.1 `CONTEXT_MISSING`은 세션을 지우지 않는다

인증 컨텍스트가 실리지 않았다는 것은 **공격의 증거가 아니다.** 이 요청 하나가 인증 없이
들어왔다는 뜻이고, 그 요청을 401로 거부하는 것으로 데이터는 이미 지켜진다. 거기에 더해
세션까지 파괴하면 **그 한 건이 곧바로 전면 로그아웃**이 된다.

응답은 그대로 401이다. 바뀐 것은 세션을 남겨두는 것뿐이라, 다음 요청이 컨텍스트를 제대로
싣고 오면 그대로 이어갈 수 있다.

나머지 셋은 그대로 파괴한다. 상태 행이 없거나 주체가 어긋나는 것은 실제로 수상하다.

### 3.2 어느 갈래였는지 로그에 남긴다

```java
LOGGER.warn(
    "Authenticated session request rejected: reason={}, sessionDestroyed={}",
    reason, reason.destroysSession);
```

세션 id·사용자 id는 넣지 않는다 — MDC의 `requestId`(모든 요청에 실린다)로 이미 특정할 수
있고, 인증 실패 지점에 식별자를 남기면 그대로 유출 통로가 된다. 사용자가 본 401 응답
본문의 `requestId`와 이어붙이면 원인이 바로 나온다.

판정도 `evaluate()`로 분리했다. 예전에는 한 줄짜리 boolean 식에 네 조건이 뭉쳐 있어
어느 것이 참인지 코드로도 읽기 어려웠다.

## 4. 확인한 것

**백엔드 834 tests, 0 failures, 0 skipped** (`scripts/backend-test.sh`, Testcontainers 포함.
802 시점의 831에서 새 시험 3개가 늘었다).
필터 시험은 4개 → 7개.

새 시험 3개:
- `missingSecurityContextIsRejectedWithoutDestroyingTheSession` — 401은 내되
  `deleteBySessionId`를 부르지 않고 세션도 살아 있다
- `missingSecurityStateStillDestroysTheSession` — 상태 행이 없으면 그대로 파괴
- `mismatchedPrincipalDestroysTheSession` — 주체가 어긋나면 그대로 파괴

**첫 번째가 옛 동작에서 실패하는 것까지 확인했다.** `CONTEXT_MISSING(false)`를 `(true)`로
되돌리면 그 시험만 FAILED가 된다(나머지 6개는 통과).

## 5. 남은 것 — **이것이 원인이라고 확정한 것은 아니다**

`CONTEXT_MISSING`이 운영에서 실제로 발동했다는 증거는 **아직 없다.** 정황(방금 로그인,
요청이 몰리는 순간, 네 갈래 중 유일하게 시험이 없던 곳)이 맞을 뿐이다.

그래서 이번 변경의 절반은 **다음 발생을 특정하기 위한 것**이다. 또 튕기면 로그에
`reason=`이 남으므로 그때 확정된다.

- `reason=CONTEXT_MISSING`이 찍히는데도 로그아웃된다면 → 컨텍스트가 왜 안 실리는지가
  다음 과제다(Spring Session 저장 시점과 동시 요청의 경합을 의심하고 있다).
- `reason=STATE_MISSING`이 찍힌다면 → 단일 세션 강제(`maximumAuthenticatedSessions = 1`)에
  밀린 것이다. 다른 탭·기기의 로그인을 봐야 한다.
- 아무것도 안 찍히는데 401이라면 → 이 필터가 아니라 서블릿 세션 자체가 idle 만료된
  것이다(§6).

### 알아둘 것

- SSE emitter 타임아웃(`DefectSseService` 30분)이 세션 idle 타임아웃(30분)과 **같은 값**이다.
  앱에 주기적 폴링이 없어 그 30분 안에 세션을 갱신하는 요청이 하나도 없다. 탭만 열어두면
  세션이 조용히 죽고, SSE 재연결의 401은 `source.onerror`가 상태 표시만 바꾸고 삼킨다 —
  **다음에 누르는 것**이 튕긴다. 이번 건과는 별개이고(제보는 로그인 직후였다) 아직 손대지
  않았다. 고치려면 30분 idle 규칙을 무력화하지 않는 쪽(만료 예고)이어야 한다.

## 7. 배포 결과 — **803이 원인이 아니었다** (2026-08-08 추가)

803 배포 뒤에도 같은 증상이 났고, `/api/v1/defects/map`이 401이었다. 그런데 백엔드 로그에
`Authenticated session request rejected:`가 **한 줄도 없었다.**

**즉 그 필터가 거부한 것이 아니다.** §2의 네 갈래 전부 해당 없다. 803은 헛다리였다
(다만 `CONTEXT_MISSING`이 세션을 지우던 것은 그 자체로 고칠 값어치가 있었다).

### 7.1 그러면 401은 어디서 났나

필터는 **세션이 아예 없으면 아무 로그 없이 통과시킨다.**

```java
HttpSession session = request.getSession(false);
if (session == null) {
    filterChain.doFilter(request, response);   // 조용히 통과
    return;
}
```

그 뒤 `SecurityConfig`의 `authenticationEntryPoint`가 401을 낸다 — **여기도 로그가
없었다.** 사용자가 로그인 화면으로 튕겨도 백엔드에는 아무 흔적이 남지 않는 구간이다.

즉 `/defects/map`이 도착했을 때 **세션은 이미 사라진 뒤였다.** 네이버 지도가 다시 그려지며
지도 재조회가 나간 것은 맞지만, 그것이 세션을 죽인 것이 아니라 **죽은 세션을 처음 발견한
요청**이었을 뿐이다.

### 7.2 세션이 조용히 사라지는 경로들

애플리케이션 로그를 한 줄도 남기지 않고 세션 행이 없어지는 곳이 이만큼 있다.

| 경로 | 로그 |
| --- | --- |
| Spring Session 자체의 idle 만료(30분) | 없음 |
| **V14의 DB 트리거 7개** | 없음 (DB 안에서 벌어진다) |
| `MyPasswordChangeCommitService.invalidateAllUserSessions` | 없음 |

V14 트리거가 특히 눈에 띈다. `auth.revoke_user_authorization_sessions`는 그 사용자의
**모든 세션을 지운다 — 현재 세션도 제외하지 않는다.** 그리고
`revoke_sessions_on_user_scope_change`에는 **값 비교 가드가 없다.**

```sql
CREATE TRIGGER tr_user_robot_assignment_revoke_sessions
    AFTER INSERT OR UPDATE OR DELETE
    ON auth.user_robot_assignment
    FOR EACH ROW
    EXECUTE FUNCTION auth.revoke_sessions_on_user_scope_change();
```

`admin_user` 쪽 트리거는 `IS DISTINCT FROM`으로 실제 값이 바뀔 때만 발동하는데, 이쪽은
행이 건드려지기만 하면 발동한다. 관리자 화면에서 로봇 배정을 저장하면
(`AdminRepository.replaceRobotAssignments`) 대상 사용자는 **그 자리에서 로그아웃된다.**
권한이 바뀌었으니 의도된 동작이지만, 값이 그대로여도 발동한다는 점은 알아둘 일이다.

### 7.3 그래서 사각지대를 막았다

`SecurityConfig`의 entry point에서 401을 내기 직전에 남긴다.

```
Unauthenticated request rejected: method=GET, path=/api/v1/defects/map,
  sessionCookie=true, cookieValid=false, liveSession=false
```

세 값이면 갈린다.

| 로그 | 뜻 |
| --- | --- |
| `sessionCookie=false` | 브라우저가 쿠키를 안 보냈다 (쿠키 유실·SameSite·Secure) |
| `sessionCookie=true, cookieValid=false` | 보냈는데 서버에 그 세션이 없다 — **만료됐거나 지워졌다** |
| `liveSession=true` | 세션은 살아 있는데 인증 컨텍스트가 없다 |

세션 id는 남기지 않는다. 요청 특정은 MDC의 `requestId`로 한다.

**주의** — 이 로그는 401마다 WARN으로 찍힌다. 로그인 전 화면이나 SSE 재연결이 만드는
정상적인 401도 포함되므로, 운영에서 소음이 심하면 수준을 낮추거나 경로로 걸러야 한다.

### 7.4 다음에 볼 것

`cookieValid=false`가 찍히면 세션이 **왜** 없어졌는지가 다음 질문이고, 그때는 §7.2의 세
경로를 DB에서 갈라야 한다. 이 로그만으로는 만료와 트리거 삭제를 구분하지 못한다.
