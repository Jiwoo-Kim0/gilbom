## 1. 801이 이것을 고쳐주는가 — 아니다

먼저 확인한 것이다. **801(`1699acb`)은 이 경로와 한 줄도 겹치지 않는다.**

| 801이 건드린 것 | 이 문제의 경로 |
| --- | --- |
| `defectMapState.ts` — `defectMapFeaturesEqual` | `DefectClusterList.tsx` — 구성원별 조회 |
| `DefectMap.tsx` — 전면 로딩 조건, 갱신 칩 | `AuthContext.tsx` — 401 → `SIGNED_OUT` |
| `App.css`, 단위·e2e 시험 | `apiClient.ts` — 401 전역 알림 |

801은 **마커를 다시 만들지 않게** 한 것이라 지도 조회의 표현만 바꿨다. 묶음을 눌렀을 때
나가는 요청 수도, 401을 로그아웃으로 옮기는 경로도 그대로였다.

## 2. 증상과 원인

지도 묶음을 누르면 로그인 창으로 튕겼다. 로그아웃 버튼을 누른 적이 없다.

원인은 두 가지가 **겹친 것**이고, 각각 따로 고쳐야 한다.

### 2.1 묶음 하나에 요청 스무 개

지도 GeoJSON에는 결함 코드까지만 담겨 있다. 위치 이름과 사진은 목록이 따로 받아야 했고,
그것을 **결함마다 두 번씩** 불렀다.

```
묶음 10건 클릭 → 상세 10회 + 이미지 URL 10회 = 20회
```

게다가 목록을 닫아도 요청을 **취소하지 않고 결과만 버렸다**(`cancelled` 플래그). 여러 번
누르면 이전 요청들이 계속 살아 있었다.

### 2.2 401 한 건이 곧바로 로그아웃

`apiFetch`는 401이면 전역 listener에 알리고(`notifyUnauthorized`), `AuthContext`는 그 자리에서
`SIGNED_OUT`을 던졌다. 라우트 가드가 곧바로 `/login`으로 보낸다.

즉 **화면 한 귀퉁이의 보조 조회 하나가 실패했을 뿐인데 로그아웃 버튼을 누른 것과 같은
일**이 벌어졌다. 목록은 오류를 "사진·위치 없음"으로 조용히 접어서 원인 메시지도 남지 않았다.

### 2.3 확정하지 못한 것

**최초 401이 어느 요청이었는지는 확정하지 못했다.** 로컬 컨테이너가 재시작된 뒤라 그
시각의 401 기록이 남아 있지 않다. 요청 폭증은 재현 조건이고, 401을 로그아웃으로 증폭시키는
경로는 코드상 확정이다 — 그 증폭 경로를 e2e로 못박았다(§5).

## 3. 무엇을 바꿨나

### 3.1 백엔드 — 묶음 목록 전용 배치 조회

`GET /api/v1/defects/cluster-details?defectIds=a,b,c`

**GET이다.** POST로 두면 읽기가 변경 계열의 CSRF 절차를 지고, 캐시·재시도 규칙도 어긋난다.
id 10개는 370자 남짓이라 URL 길이도 문제되지 않는다.

응답은 목록이 실제로 쓰는 값만 담는다.

```json
{ "items": [
  { "defectId": "...", "incidentCode": "INC-...",
    "locationLabel": "역삼역 3번 출구 앞 보도", "zoneId": null,
    "imageUrl": "/api/v1/images/.../content?sig=...", "imageUrlExpiresAt": "..." }
] }
```

- `locationLabel`과 `zoneId`를 **따로** 준다. 어느 쪽을 먼저 쓸지는 화면이 정한다 —
  `locationLabel` 자리에 구역 코드를 넣어 보내면 이름이 아닌 값이 이름 필드에 들어간다.
- **질의는 두 번으로 고정된다.** 결함 행 한 번, 결함별 대표 이미지 한 번
  (`DISTINCT ON (COALESCE(od.merged_into_defect_id, od.defect_id))`). 우선순위는 단건
  발급(`issueImageUrl`)과 같게 맞췄다 — 목록의 사진과 상세 카드의 사진이 어긋나면 안 된다.
- **보이지 않는 id는 404가 아니라 응답에서 빠진다.** 여러 건을 한 번에 묻는 요청이라 한 건
  때문에 전체가 실패하면 목록이 통째로 빈다. 어떤 id가 존재하는지 알려주는 탐색 통로가
  되지도 않는다.
- 서명 실패는 그 줄의 사진만 비운다. 목록 전체를 503으로 만들지 않는다.
- 상한 50건. 화면 상한(`CLUSTER_LIST_MAX` = 10)보다 넉넉하되 무제한은 아니다 — 이 요청
  하나가 만드는 일을 묶어두기 위한 값이다.

### 3.2 프론트 — 한 번 부르고, 끊을 수 있게

```ts
const controller = new AbortController()
getDefectClusterDetails(defectIds, controller.signal)
  .then((response) => settle(response.items))
  .catch(() => { if (!controller.signal.aborted) settle([]) })
return () => controller.abort()
```

`settle`은 요청한 결함 **전부**에 값을 채운다. 응답에 없는 결함까지 `null`로 못박아야 사진
자리표시가 영영 돌지 않는다.

`apiClient`도 한 군데 고쳤다. `fetch`의 예외를 전부 "서버에 연결할 수 없습니다"로 바꾸고
있어서, **스스로 끊은 요청이 네트워크 오류로 둔갑했다.** `AbortError`는 그대로 올려 보낸다.

### 3.3 401을 "로그아웃하라"가 아니라 "다시 확인해봐라"로

`createUnauthorizedRecovery`(`src/features/auth/unauthorizedRecovery.ts`)로 정책만 떼어냈다.
React 밖의 순수 함수라 단위 시험으로 못박을 수 있다.

- 401이 오면 세션을 **한 번 다시 확인**한다(`/auth/session-state`, 이 조회 자체는 401을 다시
  알리지 않는다 — 무한 되돌이).
- 살아 있으면 그 요청만 실패한 것이다. 화면은 그대로 둔다.
- 확인이 도는 동안 들어온 401은 **버린다.** 같은 세션에 대한 같은 질문이라 스무 개가
  한꺼번에 와도 확인은 한 번이다.
- 확인 자체가 실패하면 **로그아웃 쪽으로 기운다.** 살아 있다는 근거가 없는데 열어두면
  끊긴 세션에서 계속 조작하게 된다.

`AuthContext`는 `subscribeToUnauthorized(clearAuthentication)`을
`subscribeToUnauthorized(recoverFromUnauthorized)`로 바꾼 것이 전부다.

### 3.4 "동시성 제한"은 따로 두지 않았다

권장 3번의 절반이다. 요청이 20개에서 1개가 되면서 제한할 동시성이 남지 않았고, 취소는
`AbortController`로 붙였다. 쓰지 않을 제한기를 넣지 않았다.

## 4. 바뀌지 않은 것

묶기, 클러스터 숫자, 클릭 시 확대, 목록 UI, 줄을 눌렀을 때의 상세 카드·마커 선택 —
전부 그대로다. **목록 데이터를 가져오는 방식만** 바뀌었다.

상세 카드는 여전히 단건 조회(`GET /{defectId}`, `/{defectId}/image-url`)를 쓴다. 한 건뿐이라
묶을 것이 없고, 카드는 목록보다 훨씬 많은 값을 쓴다.

## 6. 남은 것

### 내 몫

- 목록(`DefectManagePage`)과 상세 카드의 조회도 취소하지 않는다. 같은 손질이 필요한지는
  보지 않았다.
- 401을 "이 요청만 실패"로 접는 곳이 늘어나면, 사용자에게 아무 말도 하지 않는 실패가
  늘어난다. 지금은 묶음 목록만이라 사진·위치 빈 칸으로 드러나지만, 다른 화면까지
  같은 방식으로 접으면 조용한 실패가 쌓인다.

### 알아둘 것

- `cluster-details`의 대표 이미지 우선순위는 `issueImageUrl`과 **수동으로** 맞춰져 있다
  (`is_representative DESC, confidence DESC, created_at DESC`). 한쪽을 바꾸면 다른 쪽도
  바꿔야 목록과 상세 카드의 사진이 같다.
- 개발 빌드는 StrictMode가 effect를 두 번 돌려 묶음 조회가 두 번 나간다(첫 요청은 곧바로
  취소된다). e2e가 요청 수를 세지 않고 "구성원 수만큼 늘어나지 않는가"를 보는 이유다.

## 7. 이 환경에서 시험을 돌린 방법

[[wsl-has-no-linux-node]] 메모가 오래돼서 다시 적는다.

- **백엔드**: `sh scripts/backend-test.sh` (프로젝트가 제공하는 컨테이너 러너). WSL에 java가
  없고 Windows 쪽은 JDK 17이라 gradle(21 필요)이 안 돈다.
- **프론트 tsc/eslint/단위**: Windows node로 직접
  (`"/mnt/c/Program Files/nodejs/node.exe" node_modules/typescript/bin/tsc -b`).
- **vite dev**: `node_modules`가 Windows에서 설치돼 `@rolldown/binding-linux-x64-gnu`가
  없다. alpine 컨테이너도 musl이라 안 맞는다. **glibc 이미지 + 리눅스 바인딩만 따로
  마운트**해서 띄웠다(호스트 `node_modules`는 건드리지 않는다).

  ```sh
  docker run --rm -w /out node:24.18.0 sh -c \
    'npm pack @rolldown/binding-linux-x64-gnu@1.1.5 && tar xzf *.tgz'
  docker run -d --rm --name gilbom-vite-ui -p 4174:4174 \
    -e VITE_NAVER_MAP_CLIENT_ID=e2e-map-client \
    -v <프로젝트>/frontend/gilbom:/app \
    -v <위 package>:/app/node_modules/@rolldown/binding-linux-x64-gnu:ro \
    -w /app node:24.18.0 node node_modules/vite/bin/vite.js --host 0.0.0.0 --port 4174
  ```

- **e2e**: `playwright.config.ts`의 `webServer`가 `npm run dev`라 WSL에서 안 뜬다. 이미 떠 있는
  서버를 쓰는 `playwright.live.config.ts`로 돌린다.

  ```sh
  export MISSION_LIVE_FRONTEND_URL=http://127.0.0.1:4174 \
         WSLENV=MISSION_LIVE_FRONTEND_URL
  "/mnt/c/Program Files/nodejs/node.exe" node_modules/@playwright/test/cli.js \
    test e2e/defect-*.spec.ts --config=playwright.live.config.ts
  ```

  **`WSLENV`을 빼먹으면 안 된다.** WSL은 환경변수를 Windows 프로세스로 넘기지 않아서,
  `MISSION_LIVE_FRONTEND_URL`이 사라지고 기본값 `127.0.0.1:3000`(빌드된 컨테이너)으로
  붙는다. 그러면 **고친 코드가 아니라 옛 빌드를 시험하게 된다** — 여기서 한 번 속았다.
