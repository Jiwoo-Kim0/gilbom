## 1. 무엇을 만들었나

이전까지 결함 이미지는 **어디에도 저장되지 않았다.** `storage.robot_image` 테이블(V22)과
`DefectImageUrlIssuer` 인터페이스는 있었지만 업로드 엔드포인트가 없었고, 유일한 구현인
`UnavailableDefectImageUrlIssuer`가 `Optional.empty()`를 반환해
`GET /api/v1/defects/{id}/image-url`은 **항상 503**이었다.

한편 임베디드는 `embedded/comms/uploader.py`를 이미 완성해 두고 서버만 기다리고 있었다.
그 파일 주석에 "`POST /api/v1/images`가 openapi-v1.yaml에 없다 — form 필드명은 산문 계약에서
읽은 추정치다. 서버팀 확인 후 이 세 줄만 고치면 된다"라고 적혀 있었다.

이번 작업으로 다음이 동작한다.

| 경로 | 인증 | 용도 |
| --- | --- | --- |
| `POST /api/v1/images` | 로봇 `X-API-Key` | 로봇 증거 이미지 업로드 |
| `GET /api/v1/images/{imageId}/content?token=` | 서명 URL | 브라우저 `<img src>` |
| `DefectReportImageService` (빈) | 호출자 권한 | LLM 보고서 입력용 바이트 |

추가 파일: `com.gilbom.storage` 패키지, `defect/DefectEvidenceImageLoader`,
`defect/DefectReportImageService`, `V31__create_robot_image_api_key.sql`,
`scripts/issue-robot-image-api-key.py`.
삭제: `defect/UnavailableDefectImageUrlIssuer`.

테스트: 신규 41건. 작업 종료 시점의 전체 스위트는 703 tests, 0 failures, 0 skipped.

## 2. 설계 판단과 그 이유

### 2.1 S3를 기다리지 않고 로컬 디스크로 완결시켰다

> **2026-08-01 후일담 — 팀이 S3를 아예 쓰지 않기로 정했다.** 이 판단은 "기다리지 않기"가
> 아니라 그냥 정답이 됐다. 미뤄둔 어댑터 작업 2~3시간은 통째로 사라졌고, 대기하던 A의
> 버킷·IAM 인수인계도 없어졌다.

A의 AWS 작업이 주말 예정이었다. 이미지 저장을 `ObjectStorageClient` port 뒤에 두고
`LocalFileObjectStorageClient`로 먼저 완결시켰다.

**읽기가 `bucketName`을 인자로 받는 이유가 여기 있다.** 저장소가 하나 더 생겨도 그 전에
올라간 행은 `local-disk` bucket을 가리키므로, 구현을 갈아끼우는 것이 아니라 두 구현을
동시에 두고 `ObjectStorageRegistry.forBucket()`이 행의 bucket으로 고른다. 재업로드나 데이터
마이그레이션이 필요 없다.

**포트를 남긴 판단은 S3가 없어진 뒤에도 유효한가?** 지운다고 얻는 게 없어서 남겼다.
`ImageUploadServiceTest`가 이 포트를 스텁하므로 테스트 이음매로 계속 쓰이고, 구현이 하나뿐
이어도 업무 코드가 파일 시스템을 직접 아는 것보다 낫다. 다만 **"S3 전환 대비"라는 원래
명분은 더 이상 쓰면 안 된다** — 주석도 그렇게 고쳤다.

### 2.1.1 실제로 무엇이 어디에 있나

| | 위치 |
| --- | --- |
| 메타데이터 (`object_key`·`byte_size`·SHA-256·가로세로·촬영시각·상태) | `storage.robot_image` |
| JPEG 원본 | 백엔드 볼륨 `/app/data/robot-images` |
| 저장 경로 | `robots/{robotId}/{yyyy}/{MM}/{dd}/{imageId}.jpg` |
| 결함 ↔ 이미지 연결 | `defect.defect_observation.image_id` |

**DB에 바이트를 넣지 않는다.** 표시 흐름은 `GET /defects/{id}/image-url`로 5분짜리 서명 URL을
받고, 브라우저가 `GET /api/v1/images/{imageId}/content?token=...`을 호출하면 서버가
`bucket_name`·`object_key`로 파일을 읽어 `image/jpeg`로 인라인 응답한다
(`Content-Disposition: attachment`가 아니다).

보고서도 이미지를 **복사하지 않는다.** 생성 순간에 기존 결함 이미지를 읽어 쓸 뿐,
보고서 테이블에는 바이트도 URL도 남기지 않는다.

### 2.2 브라우저와 LLM은 필요한 것이 다르다 — 진입점을 둘로 나눴다

- 브라우저: **URL**이 필요하다. `<img src>`는 헤더를 못 붙이고, 개발 서버(5173)와 운영
  Nginx의 Origin이 달라 쿠키에도 기대기 어렵다. 그래서 URL 자체가 자격증명이다.
- LLM: **바이트**가 필요하다. 서버 안에서 호출되므로 URL을 발급받아 자기 서버가 다시 HTTP로
  되받아오는 왕복은 낭비이고, 로컬 디스크 단계에서는 외부 접근이 아예 안 된다.

둘 다 `ObjectStorageClient` 하나를 쓰고 진입점만 다르다(`ImageUrlSigner` /
`ImageBytesReader`).

### 2.3 서명 URL은 S3 presigned URL의 의미론을 그대로 흉내 냈다

토큰은 `<만료 epoch 초>.<base64url HMAC-SHA256>`이고 **서명 대상에 imageId를 포함**한다.
다른 이미지의 토큰을 옮겨 쓰면 검증에 실패한다.

`SignedUrlDefectImageUrlIssuer`는 **발급 시점에 저장소를 조회하지 않는다.** S3 presigned URL도
존재하지 않는 key에 서명할 수 있고 존재 여부는 가져올 때 판정된다. S3를 안 쓰기로 한 뒤에도
이 의미론은 그대로 두는 게 낫다 — 발급이 디스크 I/O를 하지 않아 목록 화면에서 URL을 여러 개
찍어도 비용이 없다.

URL은 **상대 경로**로 발급한다. `vite.config.ts`에 "브라우저는 same-origin 상대 경로만
사용한다"는 규약이 있고 `/api`가 프록시된다.

### 2.4 A 소유 파일을 하나도 고치지 않았다

- `ErrorCode`에 `IMAGE_NOT_FOUND`, `IMAGE_TOO_LARGE`, `IMAGE_UNSUPPORTED_MEDIA_TYPE`,
  `S3_UNAVAILABLE`이 **이미 있었다.** 새 코드가 필요 없었다.
- `SecurityConfig`를 열지 않고 `securityMatcher("/api/v1/images/**")`를 가진 별도
  `SecurityFilterChain`을 `@Order(HIGHEST_PRECEDENCE + 10)`으로 추가했다. 관리자 체인은
  세션·CSRF 전제이고 이미지 체인은 API Key·서명 URL만 본다. 성질이 반대인 두 인증을 한
  체인에 넣으면 서로의 예외 조건이 된다.
- `application.yml`도 건드리지 않았다. `StorageProperties`에 기본값을 두고 환경변수는 Spring의
  relaxed binding(`GILBOM_STORAGE_LOCAL_ROOT_DIRECTORY`)으로 받는다.

### 2.5 API Key 해시는 SHA-256이다

`storage.robot_image_api_key.key_hash`는 SHA-256 hex다. Argon2를 쓰지 않은 이유는 두 가지다.
키가 **서버가 만드는 32바이트 난수**라 사전 공격 대상이 아니고, 모든 업로드 요청마다 검증하는
경로라 Argon2의 의도적인 지연이 그대로 처리량 손실이 된다.

로봇당 ACTIVE 키는 부분 unique index로 하나만 허용하고, 교체 시 이전 키는 REVOKED로 남긴다.
발급 API는 만들지 않았다 — `scripts/issue-robot-image-api-key.py`가 키와 INSERT 문을 출력하고
운영자가 psql로 실행한다. 그래서 GRANT도 SELECT·UPDATE만 준다.

### 2.6 인증 필터는 실패해도 응답을 쓰지 않는다

키가 없든 틀리든 인증을 세우지 않고 그대로 넘긴다. 체인의 `authenticationEntryPoint`가 401을
쓰므로 **"키 없음"과 "키 틀림"이 같은 응답**이 되어 키 존재 여부를 알아내는 데 쓸 수 없다.

### 2.7 `@PreAuthorize`를 붙이려고 필터가 권한을 실었다

`ApiPreAuthorizationContractTest`가 모든 `@RestController` 메서드에 `@PreAuthorize`를
요구한다(허용 목록은 A의 테스트 파일에 있다). 그 파일을 고치지 않으려고, 필터가
`ROBOT_IMAGE_UPLOAD` / `IMAGE_CONTENT_READ` 권한을 담은 `Authentication`을 세우고 컨트롤러가
그 권한을 선언하도록 했다. 결과적으로 보안 의도가 컨트롤러에 드러나서 더 낫다.

### 2.8 이미지 장수는 서버가 자른다

`DefectReportImageService`는 보고서당 최대 3장(`MAX_IMAGES`), 기본 1장(`DEFAULT_IMAGES`)이다.
A와 합의한 실제 사용량은 1장이고 3은 나중에 늘릴 때 계약을 다시 바꾸지 않기 위한 여유다.

512KB JPEG는 base64로 약 683KB다. **결함당 3장이 아니라 보고서당 3장**이어야 한다 — 결함
20건이면 60장 40MB로 요청이 터진다. 상한을 클라이언트 선의에 맡기지 않는다.

반환은 고정 슬롯이 아니라 **0~3개 가변 리스트**다. 결함 대부분은 관측이 1건이라 고정 슬롯을
쓰면 null이 예외가 아니라 기본값이 되고, 빈 image content block을 그대로 실어 보내면 LLM
provider가 400을 낸다.

`ImageContent`에 `defectId`와 `incidentCode`를 함께 넣는다. 여러 장일 때 어느 이미지가 어느
결함인지 모델이 알아야 한다.

한 장을 읽지 못해도 나머지로 계속한다. `StoredEvidenceImageLoader`가 예외를 빈 값으로 바꾼다.
보고서가 이미지 한 장 때문에 실패하면 안 된다.

## 3. 작업 중 겪은 함정

### 3.1 PostgreSQL `NOW()`는 트랜잭션 시작 시각이다 — CHECK 제약 위반

`storage.robot_image.uploaded_at`의 DB 기본값이 `NOW()`인데, 앱이 그 뒤에 계산한
`captured_at`이 더 미래가 되어 `ck_robot_image_timestamps(uploaded_at >= captured_at)`에
걸렸다. **`NOW()`는 문장 실행 시각이 아니라 트랜잭션 시작 시각**이다.

→ `uploaded_at`을 DB 기본값에 맡기지 않고 앱이 명시한다. 두 값을 같은 시계에서 뽑아야 순서가
보장된다. 통합 테스트가 아니었으면 운영에서 첫 업로드에 500이 났을 것이다.

### 3.2 생성자가 두 개면 Spring이 기본 생성자를 찾는다

`ImageUploadService`와 `ImageUrlSigner`에 테스트용 `Clock` 주입 생성자를 함께 두었더니
`BeanInstantiationException: NoSuchMethodException`으로 컨텍스트가 뜨지 않았다. 생성자가
정확히 하나일 때만 Spring이 자동 선택한다.

→ 컨테이너가 쓸 생성자에 `@Autowired`를 명시. **이것도 통합 테스트가 잡았다.** 단위 테스트만
있었으면 앱을 띄우는 순간 알았을 것이다.

### 3.3 마이그레이션 번호가 세 개나 밀렸다

작업 시작 시점에 최신은 V27이었는데, 파일을 쓰는 동안 V28(내 이전 작업 `77085f7`),
V29·V30(A의 보고서 작업)이 들어왔다. 처음에 V28로 만들어 두었다가 **같은 번호가 두 개** 되는
것을 발견하고 V31로 옮겼다.

→ 마이그레이션은 **파일을 만들기 직전에** `ls | sort -V | tail`로 번호를 다시 확인한다.
`defect-schema.md` 5.1절에 이미 "번호 변경 금지" 경고가 있을 만큼 팀이 한 번 데인 지점이다.

### 3.4 `ErrorCode`가 작업 중에 바뀌었다

`REPORT_PERIOD_INVALID`를 쓰고 컴파일했더니 없는 심볼이라고 나왔다. A가 커밋 `d7507e5`에서
그 상수를 지우고 `REPORT_VALIDATION_FAILED`·`REPORT_ACCESS_DENIED`·`IDEMPOTENCY_KEY_REUSED`·
`LLM_UNAVAILABLE`·`LLM_RESPONSE_INVALID`를 넣었다.

→ 공용 enum을 참조할 때는 **읽은 시점의 기억이 아니라 그 순간의 파일**을 확인한다.

### 3.5 테스트 픽스처의 비밀번호 해시에 CHECK 제약이 있다

`auth.admin_user.password_hash`는 V5의 `ck_admin_password_hash_argon2id`를 통과해야 한다.
그럴듯한 Argon2 문자열을 만들어 넣었더니 거부됐다. 기존 통합 테스트가 쓰는
`'{argon2}$argon2id$integration-test-...'` 형식을 그대로 따라야 한다.

### 3.6 컨테이너의 작업 디렉터리는 쓸 수 없다 — 실행 확인에서만 드러났다

테스트는 전부 통과했는데 실제 compose 스택에 올리니 첫 업로드가 **503 S3_UNAVAILABLE**로
실패했다. 인증·검증은 다 통과했고 저장 단계에서만 깨졌다.

원인은 컨테이너가 비특권 사용자(`spring`, uid 1883)로 도는데 작업 디렉터리 `/app`이
root 소유 `drwxr-xr-x`라는 것이다. 기본 저장 경로 `./data/robot-images`는 `/app` 아래로
풀리므로 디렉터리를 만들 수 없다.

→ 기동 시 저장 경로 생성·쓰기 가능 여부를 확인하고 **WARN을 남긴다**. 기동을 막지는
않는다. 이미지 업로드는 관제·결함 조회와 독립적이라 경로 설정 하나로 서버 전체가 뜨지
않는 편이 더 나쁘다. 볼륨이 붙은 뒤에는 fail-fast로 바꾸는 것을 고려한다.

**해소됨.** A가 `compose.yaml`에 볼륨과 환경변수를 추가했고(커밋 `d50b597`) 기본 스택에서
재검증했다. 위 "실행 확인 2차" 참고.

### 3.7 로컬에 JDK가 없다

이 저장소는 `scripts/backend-test.sh`가 `amazoncorretto:21` 컨테이너에서 빌드한다. 그 스크립트는
tmpfs를 GRADLE_USER_HOME으로 쓰므로 매번 Gradle 배포판과 의존성을 새로 받는다. 반복 컴파일이
필요할 때는 Gradle 홈을 영속 경로에 두는 편이 훨씬 빠르다(4분 → 20초).

## 4. 백업 (2026-08-01 추가)

S3를 쓰지 않기로 하면서 생긴 책임이다. 볼륨이 JPEG의 **유일한 사본**이다.

### 4.1 왜 스크립트로 만들었나 — 반쪽 복원이 조용하기 때문

파일은 볼륨에, 경로·크기·SHA-256은 DB에 있다. 둘은 따로 백업할 수 있지만
**따로 복원하면 안 된다.** 문제는 어긋났을 때 티가 안 난다는 점이다.

| 복원한 것 | 증상 |
| --- | --- |
| DB만 | 결함 목록·지도는 **정상으로 보인다.** 사진만 전부 `503 S3_UNAVAILABLE` |
| 볼륨만 | 파일은 있는데 참조하는 행이 없어 어디서도 열리지 않는다 |

DB만 복원한 경우가 특히 나쁘다. 화면이 멀쩡해 보여서 사진을 클릭하기 전까지 모른다.
그래서 명령어를 문서에 적어두는 대신 **둘을 한 번에 뜨는 스크립트**로 만들었다.

- `scripts/backup-defect-images.sh` — 볼륨 tar + DB 덤프 + manifest
- `scripts/RESTORE.md` — 복원 순서와 검증

manifest에 **JPEG 파일 수와 `AVAILABLE` 행 수를 같이 적는다.** 복원 후 이 두 숫자를
다시 세어 대조하면 반쪽 복원을 바로 알아챌 수 있다. 스크립트는 백업 시점에 두 수가
다르면 경고만 남기고 실패시키지는 않는다 — 업로드 직후에는 잠깐 어긋날 수 있고,
그렇다고 백업을 안 뜨는 게 더 나쁘다.

### 4.2 복원 절차를 실제로 검증했다

절차만 적어두고 안 돌려보면 필요한 순간에 처음 실행하게 된다.
**운영 스택을 건드리지 않는 방법으로** 확인했다.

- 아카이브를 **임시 볼륨**에 풀어 파일 수(6) 확인
- 각 파일의 SHA-256을 `storage.robot_image.sha256_hex`와 대조 → **6건 전부 일치**
- 덤프를 **임시 DB**(`restore_check`)에 `pg_restore` → 결함 41행, 이미지 6행 복원
- 임시 볼륨·임시 DB 삭제

해시까지 본 이유는 개수만 맞고 내용이 깨질 수 있어서다. tar가 성공했다는 것과
바이트가 온전하다는 것은 다른 얘기다.

### 4.3 함정 — 볼륨 이름을 추측하면 빈 백업이 나온다

`web_robot_images`로 알고 있었는데 실제 이름은 **`gilbom_robot_images`**다
(compose 프로젝트 이름이 `gilbom`이다). 없는 볼륨 이름으로 `docker run -v`를 하면
**오류가 아니라 빈 볼륨을 새로 만든다.** 그래서 `du`가 4KB를 찍었고, 잠깐
"이미지가 없다"고 오해했다.

스크립트가 `docker volume inspect`로 **먼저 존재를 확인하고 없으면 볼륨 목록을 찍으며
중단하는** 이유가 이것이다. 빈 백업만큼 나쁜 게 없다.

`backups/`는 `.gitignore`에 넣었다. 원본 데이터라 저장소에 올리지 않는다.

## 6. 운영 메모

**API Key 발급**

```
python scripts/issue-robot-image-api-key.py --robot-id <uuid>
```

키 원문은 이때 한 번만 출력된다. 서버에는 SHA-256 해시만 남으므로 분실하면 회수하고 새로
발급한다. 출력된 INSERT 문을 psql로 실행한다.

**이미지 저장 경로**

`robots/{robotId}/{yyyy}/{MM}/{dd}/{imageId}.jpg`.
로컬 어댑터의 루트는 `gilbom.storage.local-root-directory`
(기본 `./data/robot-images`, 환경변수 `GILBOM_STORAGE_LOCAL_ROOT_DIRECTORY`).

**멱등성**

자연 키는 `event_id`다(V22의 부분 unique index). 같은 로봇이 같은 파일을 재전송하면 200과 같은
`imageId`를, 내용이 다르거나 다른 로봇이면 409를 반환한다. `uploader.py`가 타임아웃에 최대 3회
재시도하므로 이 동작이 없으면 행이 늘어난다.
