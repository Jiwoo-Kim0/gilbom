# 목록에서 고른 결함 마커 확대 작업내용

기간: 2026-08-07
범위: 결함 지도(`DefectMap`). 목록에서 결함을 고르면 그 마커로 옮기면서 **묶이지 않을
만큼** 확대한다. 두 목록(아래 표, 묶음 목록) 모두 같다.

관련 문서: [결함-묶음-목록_작업내용.md](결함-묶음-목록_작업내용.md)(목록에서 고르면 마커가

[새-결함-지도-이동_작업내용.md](새-결함-지도-이동_작업내용.md) §3.2(이동+확대를 한 번에 해야

## 1. 무엇이 문제였나

목록에서 결함을 고르면 그 마커가 지도 가운데로 왔다. **그런데 넓게 보고 있으면 어느 것이
고른 것인지 알 수 없었다.**

고른 결함은 원래도 묶음에서 빠져 따로 그려진다(`DefectMap`의 "선택한 결함은 묶음에 숨기지
않는다"). 문제는 **겹침**이다. zoom 14에서 1px은 약 7.6m라, 8m 옆의 이웃이 만든 묶음 마커가
같은 자리에 앉는다. 시험으로 재보니 두 마커 간격이 **1.06px**이었다 — 사실상 같은 점이다.

---

## 2. 무엇을 바꿨나

옮기면서 **가장 가까운 이웃과 격자 한 칸(44px)만큼 벌어지는 배율까지** 확대한다.

```
확대 단계 = ceil(log2(44px / 가장 가까운 이웃까지의 화면 거리))
```

묶기와 같은 기준이다 — 격자가 정사각형이라 축 방향 최대값(Chebyshev)으로 재고, 거리는
미터로 구해 지도에서 직접 잰 배율(m/px)로 나눈다. `unclusterZoomStep()`으로 빼서
`defectMapState.ts`에 뒀다(순수 계산 → 단위 시험 가능).

**확대하지 않는 경우도 규칙에 넣었다.**

| 상황 | 단계 |
| --- | --- |
| 이웃이 없다(혼자다) | 0 — 어떤 배율에서도 묶이지 않는다 |
| 이미 44px 이상 벌어져 있다 | 0 — 확대할 이유가 없다 |
| 좌표가 완전히 같은 이웃이 있다 | 상한(21)까지. 그래도 갈리지 않지만 갈 수 있는 데까지 간다 |

**줄이지 않는다.** 단계는 0 이상이고 최대 배율에서 자른다.

### 2.1 이웃을 알려면 bbox 없이 조회해야 한다

지금 그려진 결함만 보면 안 된다. **화면 밖에 있는 결함을 골랐을 때 그 주변을 아예 모른다** —
그 자리로 옮긴 뒤에야 이웃이 조회되고, 그때는 이미 묶여 보인다. 그래서 뷰포트 bbox 없이 지도
GeoJSON을 한 번 받아 이웃을 찾는다(새 결함 이동과 같은 방법이다).

조회가 실패하면 **확대 없이 가운데로만 옮긴다.** 옮기기는 살려야 한다.

### 2.2 이동과 확대는 한 번에

`focusMapOn`을 그대로 쓴다 — `morph` 한 번, 없으면 `setCenter` + `setZoom`이다. `panTo` 뒤에
`setZoom`을 부르면 이동이 끊겨 엉뚱한 자리에서 확대된다
([새-결함-지도-이동_작업내용.md](새-결함-지도-이동_작업내용.md) §3.2에서 겪었다).

## 3. 다른 작업의 시험을 함께 고쳤다

`defect-cluster.spec.ts`의 "고른 결함 가운데 정렬" 세 건이 **`panTo`가 불렸는지**로 확인하고
있었다. 이동 방식이 `setCenter`(+확대)로 바뀌었으니 그대로 두면 깨진다. 보는 대상을
"무엇을 호출했나"에서 **"지도가 어디로 옮겨졌나"**(`center`)로 바꾸고, 확대 배율을 알아내려고
조회를 한 번 하므로 **클릭 직후가 아니라 기다린 뒤** 보게 했다(`expect.poll`).

> 이 파일은 다른 세션이 함께 고치고 있다. 시험 세 건의 판정 기준만 손댔고 마크업·기능
> 코드는 건드리지 않았다.

## 4. 확인한 것

**단위 시험 3개**(`test/defectUiState.test.ts`): 22m→1단계·11m→2단계·이웃 여럿이면 가장 가까운
것 기준, 이미 갈렸거나 혼자면 0단계(배율을 못 재도 0), 좌표가 같으면 상한. 전체 96 pass.

**e2e 2개**(`e2e/defect-focus-zoom.spec.ts`). 보는 것은 배율이 아니라 **가장 가까운 두 마커
사이의 화면 거리**다 — 그게 요구사항이기 때문이다.

| 상황 | 결과 |
| --- | --- |
| zoom 14, 8m 옆에 이웃 | 처음 한 묶음(1.06px) → 고르면 **zoom 20, 마커 2개, 간격 68px** |
| 이웃 없음 | 옮기기만 하고 **배율은 14 그대로** |

첫 시험을 고치기 전 코드에 돌려 **간격 1.06px로 실패하는 것까지 확인했다.**

스텁 서버가 **bbox로 실제로 걸러** 응답한다. 확대가 모자라면 옮겨간 자리의 재조회 결과가
묶여 나오므로, 이 필터가 없으면 시험이 통과해 버린다.

`npm run test:e2e:defect`에 넣었다 — 결함 화면 e2e 42개 통과.
`tsc -b`·`eslint`·CSP 게이트 PASS.

## 5. 남은 것

### 내 몫

- 목록에서 고를 때마다 지도 조회가 한 번 더 나간다(이웃을 알기 위해). 목록·묶음 목록을
  빠르게 훑으면 요청이 그만큼 쌓인다. 눈에 걸리면 **같은 필터의 전체 GeoJSON을 잠깐
  캐시**하는 것이 다음 수다.
- 좌표가 완전히 같은 두 결함은 최대 배율에서도 갈리지 않는다(격자 방식의 한계). 그때는
  묶음 목록에서 고르는 것이 유일한 길이다.

### 알아둘 것

- 확대 배율은 **이웃까지의 거리**로 정해진다. 촘촘한 도심에서는 zoom 20~21까지 들어가고,
  한적한 곳에서는 배율이 그대로일 수 있다. "항상 같은 배율"이 필요하면 규칙을 바꿔야 한다.
