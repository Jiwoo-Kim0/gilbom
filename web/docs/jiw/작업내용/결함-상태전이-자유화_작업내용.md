## 1. 배경

상세 카드에서 신규 결함의 상태를 바꾸려 하면 **접수·오탐·반려 세 개만** 나왔다. 단계별
전이표를 그대로 드롭다운에 쓰고 있었기 때문이다.

```
NEW         → ACCEPTED, FALSE_POSITIVE, REJECTED
ACCEPTED    → IN_PROGRESS, FALSE_POSITIVE, REJECTED
IN_PROGRESS → RESOLVED, FALSE_POSITIVE, REJECTED
종결 3종     → (없음)
```

현장 처리는 이 순서대로 흐르지 않는다. 접수 절차 없이 바로 고쳐 완료하는 건이 있고,
완료한 뒤 재작업이 필요해 되돌려야 하는 건도 있다. **단계를 강제하면 담당자가 상태를
실제와 다르게 남기거나 아예 갱신하지 않는다.**

계획 문서에 남아 있던 미해결 질문("반려하면 되살릴 수 없다 — ① 기각으로 확정할지
② 재작업 전이를 열지")도 이번에 ②로 정리됐다.

## 3. 설계 판단과 그 이유

### 3.1 표를 지우고 집합 하나로 줄였다

여섯 상태 × 여섯 상태 표를 유지할 이유가 없어졌다. 규칙이 "지금 상태만 빼고 전부"이므로
집합 하나와 조건 두 개로 끝난다.

```java
private static final Set<String> ASSIGNABLE_STATUSES =
        Set.of(ACCEPTED, IN_PROGRESS, RESOLVED, FALSE_POSITIVE, REJECTED);
```

프론트도 표 대신 함수로 바꿨다. 표를 두면 서버와 어긋날 자리가 6곳 생긴다.

```ts
export function allowedTransitions(from: WorkflowStatus): WorkflowStatus[] {
  return ASSIGNABLE_STATUSES.filter((status) => status !== from)
}
```

### 3.2 `NEW`는 대상에서 뺐다

결함이 적재될 때 시스템이 붙이는 상태다. 사람이 "아직 안 본 것"으로 되돌리면 관측 이력과
어긋난다(이미 여러 번 관측됐고 담당자가 손을 댄 결함이 신규로 보인다). 요청하면 409
`DEFECT_STATE_CONFLICT`에 "신규 상태로는 되돌릴 수 없습니다."다.

**같은 상태로의 요청도 그대로 409로 남겼다.** 바뀌는 것이 없는데 이력에 줄이 쌓인다.

### 3.3 종결 표식의 뜻을 좁혔다

`TERMINAL_STATUSES`는 원래 두 가지를 뜻했다.

1. 처리 결과(`resolution`)를 가질 수 있는 상태
2. 더 전이하지 않고 내용 수정도 막히는 상태

전이 제한만 떼어내고 **1과 "내용 수정 차단"은 그대로 뒀다.** 종결 결함을 고치려면
상태를 먼저 비종결로 바꾼 뒤 수정한다. 순서가 하나 늘지만, "완료된 결함의 내용이 조용히
바뀌어 있다"보다 낫다. 카드의 차단 문구도 막다른 길처럼 읽히지 않게 바꿨다.

> 종결된 결함은 **처리 상태를 먼저 바꿔야** 수정할 수 있습니다.

### 3.4 처리 결과는 상태를 따라간다

종결 → 비종결로 바꾸면 `resolution`·`resolution_note`가 비워진다. 새로 만든 규칙이
아니라, `updateWorkflowStatus`가 두 컬럼을 **요청 값으로 항상 덮기** 때문에 그렇게 된다
(요청에 없으면 null). 처리 중인 결함이 `REPAIRED`를 달고 있으면 `resolution`은 종결
상태에만 있다는 불변식이 깨지므로, 이 동작이 맞다. 계약 설명에 명시해뒀다.

### 3.5 재검지 규칙은 건드리지 않았다

`IncidentEventIngestionService`는 병합 후보에서 `RESOLVED`만 제외한다(오탐·반려는 계속
흡수한다). 이제 `RESOLVED → IN_PROGRESS`로 되살릴 수 있으므로, 되살린 결함은 다시 관측을
흡수한다. 종결이 아니게 됐으니 그게 맞는 동작이다. 코드 변경은 없다.

## 5. 검증

### 5.1 백엔드

이 WSL에는 Linux JDK가 없어 컨테이너로 돌린다. 먼저 영향 클래스만 빠르게 돌려
규칙 변경을 확인하고(아래), 그다음 프로젝트 스크립트로 전체를 돌렸다.

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  --env HOME=/test-home --env GRADLE_USER_HOME=/gradle-home \
  --volume /home/ssafy/S15P11D101/web/backend:/backend:ro \
  --volume <캐시 디렉터리>:/gradle-home \
  --tmpfs "/test-home:rw,uid=$(id -u),gid=$(id -g)" \
  --workdir /backend amazoncorretto:21.0.12-alpine3.22 \
  sh -ec 'sh ./gradlew --project-cache-dir /test-home/project-cache \
    -PisolatedBuildDirectory=/test-home/build test \
    --tests "com.gilbom.defect.DefectWorkflowTest" \
    --tests "com.gilbom.defect.DefectControllerTest" --no-daemon --rerun-tasks'
```

결과: `Backend test summary: tests=50, failures=0, skipped=0`, BUILD SUCCESSFUL (2m 2s).
Testcontainers가 필요한 통합 테스트는 이 범위에 없다.

그다음 프로젝트 스크립트로 **전체 스위트**를 그대로 돌렸다.

```bash
sh web/scripts/backend-test.sh
```

결과: `Backend test summary: tests=817, failures=0, skipped=0`, BUILD SUCCESSFUL (5m 10s).
`skipped=0`이라 Testcontainers 통합 테스트도 실제로 실행됐다(build.gradle이 skip을 에러로
처리한다). §4 목록에서 걱정했던 지점들 — 종결 결함 재검지(`RobotEventMissionDefectIntegrationTest`),
상태 변경 권한·스코프(`DefectQueryScopeIntegrationTest`), 409 매핑 — 이 함께 통과했다.

> **최종 상태에서 다시 돌렸다(같은 날, 커밋 784 시점).** 위 817개는 이 변경을 넣은 직후
> 값이고, 그 뒤 `master`가 두 번 머지돼 백엔드에도 다른 사람 작업(보고서 한글화 —
> `LlmPromptCatalog`, `ReportKoreanLabels`, `ReportLlmResultValidator`)이 들어왔다.
> 그 상태에서 `scripts/backend-test.sh`를 다시 돌려
> **`tests=821, failures=0, skipped=0`, BUILD SUCCESSFUL (5m 32s)**를 받았다.
> 늘어난 4개는 머지로 들어온 보고서 테스트다. 이 브랜치의 백엔드는 최종 상태 기준으로
> 검증됐다.

### 5.2 프론트 — 드롭다운 항목을 직접 읽었다

상세 카드를 열어 `<option>` 텍스트를 그대로 비교했다(임시 스펙, 커밋하지 않음).

| 결함 상태 | 고를 수 있는 것 |
| --- | --- |
| 신규 | 접수, 처리 중, 완료, 오탐, 반려 (5개) |
| 완료 | 접수, 처리 중, 오탐, 반려 (자기 자신만 빠짐) |

그밖에 확인한 것:

- 완료 결함에서 "종결된 결함이라 상태를 더 바꿀 수 없습니다" 안내가 사라졌다
- 완료 결함의 `결함 수정` 버튼은 여전히 비활성이고 title이 새 문구다
- `완료`를 고르면 처리 결과 드롭다운이 나오고, 고르기 전에는 `상태 변경`이 비활성이다
- 비종결(`처리 중`·`오탐`)로 되살릴 때는 처리 결과를 묻지 않는다

**함정:** 상세 카드를 여는 스펙은 `image-url`까지 스텁해야 한다. 필드가 빠지면
`BoundingBoxOverlay`가 `undefined.length`로 터져 라우터 에러 화면으로 넘어간다
(404로 두면 "이미지 없음"으로 정상 처리된다).
[결함-필터-UI-드롭다운_작업내용.md](결함-필터-UI-드롭다운_작업내용.md) §13.4와 같은 함정이다.

## 6. 남은 것

### 내 몫

- 종결 결함의 수정 차단 사유가 **비활성 버튼의 `title`로만** 붙어 있다. 터치 기기와
  스크린 리더에서는 읽히지 않는다. 이전부터 그랬고 이번에도 문구만 바꿨다.
- 상태를 되돌릴 때 확인 절차가 없다. 완료 → 처리 중처럼 되돌리는 전이는 실수로 누르면
  통계가 흔들린다. 확인 모달을 붙이는 것이 다음 후보다.

### 다른 팀원 몫

- **A(보고서):** 상태별 통계 해석이 달라진다. 이제 완료·반려된 결함이 다시 처리 중으로
  돌아올 수 있어, 특정 시점 스냅샷과 누적 집계가 어긋날 수 있다. 계획 문서에 적혀 있던
  "A의 보고서 상태별 통계 해석에도 영향"이 이 지점이다.
