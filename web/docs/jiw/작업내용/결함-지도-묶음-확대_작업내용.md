# 결함 지도 묶음 클릭 확대 작업내용

기간: 2026-08-06
범위: 결함 지도에서 묶인 마커를 클릭했을 때의 확대 단계 계산.

관련 문서: [결함-목록-지도-상세화면_작업내용.md](결함-목록-지도-상세화면_작업내용.md)(지도·묶기),
[결함-화면-e2e-스펙_작업내용.md](결함-화면-e2e-스펙_작업내용.md) §4.1(지도 스텁 방침)

---

## 1. 무엇이 문제였나

묶인 마커를 클릭하면 **고정 두 단계**만 확대했다.

```ts
map.setZoom(Math.min(map.getZoom() + 2, 21))   // "두 단계면 대개 나뉜다"
```

촘촘한 묶음에서는 두 단계로 부족해 **같은 숫자가 다시 나온다.** 사용자는 갈릴 때까지
여러 번 눌러야 했고, 몇 번을 더 눌러야 하는지 알 수 없다.

---

## 2. 필요한 단계를 계산한다

묶음은 화면 좌표를 `CLUSTER_CELL_PX`(44px) 격자로 나눠 만든다. 두 점이 같은 칸에 들어간다는
것은 **가로·세로 차이가 둘 다 44px보다 작다**는 뜻이다. 그래서 갈리는 조건은 축 방향
최대값(Chebyshev 거리)이 44px 이상이 되는 것이고, 확대 한 단계가 화면 거리를 두 배로
만들므로 필요한 단계는 이렇게 나온다.

```
필요 단계 = ceil(log2(격자 한 칸 / 가장 가까운 쌍의 축 방향 거리))
```

`clusterSplitZoomStep()`으로 빼서 `defectMapState.ts`에 뒀다(순수 계산 → 단위 시험 가능).

**가장 가까운 쌍이 기준이다.** 멀리 있는 점이 섞여 있어도 촘촘한 쌍이 갈리지 않으면 묶음이
그대로 남는다.

화면 거리를 무엇으로 재는지가 이 계산의 전부인데, **처음 만든 방식이 틀렸다.** §3에 따로
적었다.

### 2.1 상한을 넉넉히 둔 이유

좌표가 완전히 같으면 `log2(∞)`가 되어 계산이 서지 않는다. 그때는 상한으로 멈춘다.
처음에 상한을 6으로 잡았는데, **그러면 촘촘한 묶음에서 쓸 수 있는 확대폭을 스스로 버린다**
(zoom 14에서 21까지 7단계가 남아 있는데 6에서 멈춘다). 상한은 21로 넉넉히 두고 실제
자르기는 부르는 쪽에서 지도 최대 확대 단계로 한다.

### 2.2 갈리지 않는 경우는 남는다

최대 확대(21)에서 격자 44px은 약 3.3m다. **그보다 가까운 결함들은 어떤 배율에서도 갈리지
않는다.** 같은 블록에 두 건이 겹쳐 있으면 묶음으로 남고, 그때는 목록에서 고르는 것이
빠르다. 계산으로 해결되는 문제가 아니라 격자 방식의 한계다.

---

## 3. 처음 만든 방식이 틀렸다 — 화면 거리를 무엇으로 재는가

첫 구현은 클릭 시점의 projection으로 구성원의 좌표를 구해 그 차이를 화면 픽셀로 썼다.

```ts
const offsets = cluster.features.map((m) => projection.fromCoordToOffset(latLngOf(m)))
```

**되돌아보면 이건 SDK가 무슨 단위를 주는지에 대한 가정이다.** 묶기(`clusterFeatures`)는 같은
값을 44로 나눠 칸을 만들 뿐이라 단위가 상수배로 어긋나도 "묶인다/안 묶인다"는 얼추 맞는다.
반면 확대 단계는 **거리의 절대값**을 쓰므로 배율이 어긋나면 그대로 틀린다. 값이 화면
픽셀보다 크게 오면 이미 멀리 떨어져 있다고 판단해 **덜 확대한다.**

그래서 계산을 지도에서 **직접 잰 값** 위에 다시 세웠다.

```ts
metersPerPixel = |NE.lng − SW.lng| × 111320 × cos(lat) / 지도 폭(px)
```

축척 바(`computeScale`)가 쓰는 것과 같은 방법이다. 구성원 사이 거리는 위경도로 미터를
구하고(등거리 근사, 축 방향 최대값), `metersPerPixel`로 나눠 화면 거리를 만든다. 이제
projection이 무엇을 돌려주든 결과가 같다.

곁들여, `ceil` 앞에서 아주 작은 값(1e-9)을 깎는다. 딱 떨어지는 경우(11px → ×4 = 44px)에
부동소수 오차로 `2.0000000001`이 나와 한 단계를 더 얹는 것을 막는다.

## 4. 사용자가 본 증상과의 대응

"13개짜리 묶음을 눌러도 갈리지 않는다"는 보고를 받고 나서야 §3을 찾았다. 확인하며 알게 된
두 가지를 남긴다.

- **어긋난 단위가 3배면 두 단계 덜 확대한다.** 8m 격자로 놓은 13건을 zoom 14에서 클릭했을 때
  예전 구현은 18까지만 올라가 **4덩어리(3~4건씩)로 남았다.** 간격이 더 촘촘하면 한 덩어리
  그대로다.
- **배포된 것이 무엇인지 먼저 확인해야 했다.** 첫 커밋은 push하지 않은 상태였다. 로컬
  컨테이너 이미지에는 들어 있었지만(번들에서 확인), git으로 배포되는 곳에는 없었다.
  화면 동작이 안 맞는다는 보고를 받으면 **코드보다 먼저 그 화면이 어느 빌드인지**를 본다.

## 5. 확인한 것

**단위 시험 7개**(`test/defectUiState.test.ts`): 22px → 1단계, 11px → 2단계, 3px → 4단계,
가장 가까운 쌍이 기준, 가로가 멀면 이미 다른 칸, 이미 떨어져 있어도 최소 한 단계,
좌표가 같으면 상한, **같은 좌표라도 지금 배율에 따라 단계가 달라진다**(§3이 만든 시험),
배율을 재지 못하면(폭 0) 한 단계. 전체 78 pass.

**e2e로 남겼다** — `e2e/defect-cluster.spec.ts`. 지도 SDK 가짜를 심고 **8m 격자로 13건**을
한 묶음으로 만들어 클릭한다. 가짜의 `fromCoordToOffset`은 **화면 픽셀의 3배**를 돌려준다 —
§3이 말하는 단위 어긋남을 시험 안에 박아 넣은 것이다.

| | 예전 구현 | 지금 |
| --- | --- | --- |
| 클릭 한 번의 `setZoom` | `18` | **`20`** |
| 확대 뒤 덩어리 수 | 4 (3~4건씩 남음) | **13 (전부 갈림)** |
| 시험 | 실패 | 통과 |

같은 스펙을 예전 코드에 돌려 **실패하는 것까지 확인했다.** 회귀를 잡는 시험인지 확인하는
가장 확실한 방법이다.

`npm run test:e2e:defect`에 이 스펙을 넣었다 — 결함 화면 e2e 19개 통과.
`tsc -b`·`eslint`·CSP 게이트 PASS.

## 6. 남은 것

### 내 몫

- 지도 SDK 가짜가 `defect-cluster.spec.ts` 안에 있다. **상세 카드·사진 확대 창 e2e를 쓸 때
  `e2e/support`로 빼는 것이 낫다** — 세 기능이 같은 이유로 e2e가 비어 있었다.
- 실제 SDK로는 확인하지 못했다. 로컬에서 지도 스크립트가 받아지지 않는다(네트워크). 그래서
  **projection 단위에 기대지 않는 방식**을 골랐다 — 어느 쪽이든 맞게 동작한다.
- 로봇 지도에도 묶기가 있으면 같은 문제가 있을 수 있다(확인하지 않았다).
