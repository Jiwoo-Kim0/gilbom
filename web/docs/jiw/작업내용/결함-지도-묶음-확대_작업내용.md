# 결함 지도 묶음 클릭 확대 작업내용

기간: 2026-08-06
범위: 결함 지도에서 묶인 마커를 클릭했을 때의 확대 단계 계산.

관련 문서: [결함-목록-지도-상세화면_작업내용.md](결함-목록-지도-상세화면_작업내용.md)(지도·묶기),
[결함-화면-e2e-스펙_작업내용.md](결함-화면-e2e-스펙_작업내용.md) §4.1(지도 스텁 방침)

## 1. 무엇이 문제였나

묶인 마커를 클릭하면 **고정 두 단계**만 확대했다.

```ts
map.setZoom(Math.min(map.getZoom() + 2, 21))   // "두 단계면 대개 나뉜다"
```

촘촘한 묶음에서는 두 단계로 부족해 **같은 숫자가 다시 나온다.** 사용자는 갈릴 때까지
여러 번 눌러야 했고, 몇 번을 더 눌러야 하는지 알 수 없다.

---

## 2. 기준: "구성원 전체가 화면에 담기는 가장 큰 배율"

두 가지가 함께 지켜져야 한다.

1. **누른 것을 잃지 않는다.** 10건 묶음을 눌렀으면 확대된 화면에 (묶음이든 낱개든) 10건이
   들어 있어야 한다.
2. **묶음이 갈린다.** 같은 숫자가 다시 나오면 누른 의미가 없다.

그래서 구성원을 감싸는 사각형이 화면의 70%를 채우는 배율을 구한다.

```
필요 배율(m/px) = max(동서 폭 / (화면 폭 × 0.7), 남북 폭 / (화면 높이 × 0.7))
확대 단계 = floor(log2(지금 배율 / 필요 배율))
```

담기는 한 최대로 확대하니 1번이 지켜지고, 사각형이 화면의 70%를 채우니 가장 먼 쌍이 격자
한 칸(44px)보다 훨씬 멀어져 2번도 지켜진다. 여백 30%는 마커 아이콘(44px)이 가장자리에서
잘리는 것과 아래를 덮는 상세 카드를 감당한다.

중심도 **평균이 아니라 사각형의 중심**으로 옮긴다. 평균은 결함이 몰린 쪽으로 끌려가서
반대쪽 끝이 화면 밖으로 나간다.

`clusterZoomPlan()`으로 빼서 `defectMapState.ts`에 뒀다(순수 계산 → 단위 시험 가능).
배율은 미터로 계산한다 — 그 이유는 §3이다.

### 2.1 처음엔 "가장 가까운 쌍을 갈라내기"였다

`ceil(log2(44px / 가장 가까운 쌍의 거리))`로 **완전히** 갈리게 만들었다. 이게 지나쳤다.
2m 붙은 쌍이 하나만 있으면 그 쌍을 갈라내려고 최대 배율까지 뛰고, 그 배율에서 화면은
95m밖에 담지 못해 **100m에 퍼진 나머지 결함이 밖으로 밀려났다.** 10건을 눌렀는데 화면에는
4건이 남는다.

**완전히 갈리는 것보다 누른 것을 잃지 않는 것이 먼저다.** 남은 작은 묶음은 다시 누르면
되고, 그때는 그 묶음만 감싸므로 훨씬 깊이 들어간다.

### 2.2 갈리지 않는 경우는 남는다

최대 확대(21)에서 격자 44px은 약 3.3m다. **그보다 가까운 결함들은 어떤 배율에서도 갈리지
않는다.** 같은 블록에 두 건이 겹쳐 있으면 묶음으로 남고, 그때는 목록에서 고르는 것이
빠르다. 계산으로 해결되는 문제가 아니라 격자 방식의 한계다.

---

## 3. 처음 만든 방식이 틀렸다 — 화면 거리를 무엇으로 재는가

첫 구현은 클릭 시점의 projection으로 구성원의 좌표를 구해 그 차이를 화면 픽셀로 썼다.

```ts
const offsets = cluster.features.map((m) => projection.fromCoordToOffset(latLngOf(m)))
```

**되돌아보면 이건 SDK가 무슨 단위를 주는지에 대한 가정이다.** 묶기(`clusterFeatures`)는 같은
값을 44로 나눠 칸을 만들 뿐이라 단위가 상수배로 어긋나도 "묶인다/안 묶인다"는 얼추 맞는다.
반면 확대 단계는 **거리의 절대값**을 쓰므로 배율이 어긋나면 그대로 틀린다. 값이 화면
픽셀보다 크게 오면 이미 멀리 떨어져 있다고 판단해 **덜 확대한다.**

그래서 계산을 지도에서 **직접 잰 값** 위에 다시 세웠다.

```ts
metersPerPixel = |NE.lng − SW.lng| × 111320 × cos(lat) / 지도 폭(px)
```

축척 바(`computeScale`)가 쓰는 것과 같은 방법이다. 구성원을 감싼 사각형의 폭도 위경도로
미터를 구해(등거리 근사) 이 값과 견준다. 이제 projection이 무엇을 돌려주든 결과가 같다.

곁들여, `floor` 앞에 아주 작은 값(1e-9)을 얹는다. 딱 떨어지는 경우에 부동소수 오차로
`2.9999999999`가 나와 한 단계를 잃는 것을 막는다.

---

## 4. 사용자가 본 증상과의 대응

"13개짜리 묶음을 눌러도 갈리지 않는다"는 보고를 받고 나서야 §3을 찾았다. 확인하며 알게 된
두 가지를 남긴다.

- **어긋난 단위가 3배면 두 단계 덜 확대한다.** 8m 격자로 놓은 13건을 zoom 14에서 클릭했을 때
  예전 구현은 18까지만 올라가 **4덩어리(3~4건씩)로 남았다.** 간격이 더 촘촘하면 한 덩어리
  그대로다.
- **너무 확대하는 것도 고장이다.** 위를 고친 뒤에는 "확대는 되는데 결함이 화면 밖으로
  나간다"는 보고가 왔다. 갈라내기만 목표로 두면 이렇게 된다 — §2.1.
- **배포된 것이 무엇인지 먼저 확인해야 했다.** 첫 커밋은 push하지 않은 상태였다. 로컬
  컨테이너 이미지에는 들어 있었지만(번들에서 확인), git으로 배포되는 곳에는 없었다.
  화면 동작이 안 맞는다는 보고를 받으면 **코드보다 먼저 그 화면이 어느 빌드인지**를 본다.

## 5. 확인한 것

**단위 시험 7개**(`test/defectUiState.test.ts`): 담기는 만큼만 확대, 확대 뒤에도 구성원이
화면 안(10건·2m 쌍 포함), 세로로 긴 묶음은 높이에 맞춤, 중심은 사각형 중심, 좌표가 같으면
상한, 이미 가득 차 있어도 한 단계, 배율·화면 크기를 못 재면 한 단계. 전체 78 pass.

**e2e 2개**(`e2e/defect-cluster.spec.ts`). 지도 SDK 가짜를 심고, 클릭 뒤의 배율·중심으로
좌표를 **다시 재서** 화면에 남은 건수와 덩어리 수를 센다. 가짜의 `fromCoordToOffset`은
일부러 화면 픽셀의 3배를 돌려준다(§3을 시험 안에 박았다).

| 상황 | 예전(가장 가까운 쌍) | 지금(전체를 담는 배율) |
| --- | --- | --- |
| 100m에 퍼진 10건 + 2m 쌍 | zoom 21, **화면에 4건만** | zoom 19, **10건 모두**, 9덩어리(가장 큰 2) |
| 8m 격자 촘촘한 13건 | — | zoom 20, 13건 모두, **13덩어리(전부 갈림)** |

퍼진 10건 시험을 예전 코드에 돌려 **실패하는 것까지 확인했다**(4건). 회귀를 잡는 시험인지
확인하는 가장 확실한 방법이다.

`npm run test:e2e:defect`에 넣었다 — 결함 화면 e2e 20개 통과. `tsc -b`·`eslint`·CSP 게이트
PASS.

## 6. 남은 것

### 내 몫

- 지도 SDK 가짜가 `defect-cluster.spec.ts` 안에 있다. **상세 카드·사진 확대 창 e2e를 쓸 때
  `e2e/support`로 빼는 것이 낫다** — 세 기능이 같은 이유로 e2e가 비어 있었다.
- 실제 SDK로는 확인하지 못했다. 로컬에서 지도 스크립트가 받아지지 않는다(네트워크). 그래서
  **projection 단위에 기대지 않는 방식**을 골랐다 — 어느 쪽이든 맞게 동작한다.
- 로봇 지도에도 묶기가 있으면 같은 문제가 있을 수 있다(확인하지 않았다).
