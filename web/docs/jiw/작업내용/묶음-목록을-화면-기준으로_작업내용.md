# 묶음 목록을 "화면에 보이는 결함"으로

- **날짜:** 2026-08-08
- **범위:** `/defects` 지도의 묶음 클릭 목록. `web/frontend/gilbom/src/features/defect/`와
  그 e2e·단위 시험.
- **한 줄:** 묶음을 누르면 목록에 **누른 묶음의 구성원만** 담기던 것을, **확대된 화면에
  보이는 결함 전부**로 바꿨다.

---

## 1. 무엇이 문제였나

묶음을 누르면 구성원 전체가 담기는 배율로 확대한다. 그런데 확대된 화면에는 **누르지 않은
이웃 결함도 함께 보인다** — 화면 마커는 여덟 개인데 목록은 다섯 줄이었다.

목록을 훑어 지도를 읽는 것이 이 목록의 쓸모인데, 둘이 어긋나면 그게 안 된다.

```
전:  마커 8개 / 목록 5줄 (누른 묶음의 구성원만)
후:  마커 8개 / 목록 8줄 (지금 화면에 보이는 전부)
```

| 파일 | 무엇 |
| --- | --- |
| `defectMapState.ts` | `viewBoundsAt`, `featuresInView` 추가(순수 함수) |
| `DefectMap.tsx` | 묶음 클릭 시 확대 뒤 범위를 계산해 그 안의 결함을 목록에 담음 |
| `DefectClusterList.tsx` | 상한 `CLUSTER_LIST_VISIBLE_MAX`, 제목을 "화면의 결함 N건"으로 |
| `test/defectUiState.test.ts` | 범위 계산·고르기 단위 시험 4개 |
| `e2e/defect-cluster.spec.ts` | 회귀 시험 1개, 순서에 기대던 기존 단정 정리 |

## 2. 설계 판단과 그 이유

### 2.1 확대 뒤 범위는 우리가 계산한다

`map.setZoom(...)` 직후의 `getBounds()`는 **아직 이전 값일 수 있다**(SDK가 배율을 비동기로
적용한다). 그래서 지도에 묻지 않고 계산한다 — 중심(`clusterZoomPlan`이 정한 값)과 확대 뒤
1px이 몇 m인지만 있으면 된다.

```ts
const nextZoom = Math.min(currentZoom + plan.step, MAX_MAP_ZOOM)
const view = viewBoundsAt(plan.center, metersPerPixel / 2 ** (nextZoom - currentZoom), viewport)
```

**실제로 적용된 단계**(`nextZoom - currentZoom`)를 쓴다. 최대 배율에 걸려 확대가 덜 되면
화면은 그만큼 넓게 남는데, 계획한 단계로 계산하면 실제보다 좁은 범위를 보게 된다.

### 2.2 가장자리 판정은 이미 있던 규칙을 쓴다

`isPointOutsideMapView`(화면 폭·높이의 8%를 안쪽으로 당겨 봄)를 그대로 쓴다. 마커(44px)가
반쯤 걸쳐 있으면 사용자에게는 안 보이는 것과 같다. **"보이는 것"의 정의가 화면마다 다르면
안 된다** — 새 결함이 화면 밖인지 판단하는 곳과 같은 함수를 쓴다.

여기서 누른 구성원이 잘려나가지 않는 것도 확인된다. `clusterZoomPlan`이 구성원을 화면의
70%에 맞추므로 중심에서 최대 35%인데, 8%를 뺀 경계는 42%다.

### 2.3 가운데에서 가까운 순으로 정렬하고, 넘치면 자른다

조밀한 동네에서는 화면에 보이는 것이 수십 건일 수 있다. 서버 `cluster-details` 상한(50)
아래인 **30건**으로 자르되, 자를 때 **누른 자리에서 가까운 것부터** 남긴다. 가운데가 곧
누른 묶음의 자리라, 잘려도 "내가 누른 것"은 언제나 목록에 있다.

정렬은 자르기 때문만이 아니다 — 누른 것이 맨 위에 오는 것이 읽기에도 맞다.
**대신 목록 순서가 결함 번호와 무관해졌다.** 순서에 기대던 e2e 단정을 코드로 집도록 고쳤다.

### 2.4 열지 말지는 여전히 "누른 묶음"으로 판단한다

`cluster.features.length <= CLUSTER_LIST_MAX(10)`이라는 기존 규칙을 그대로 뒀다. 화면에
보이는 수로 판단하면 같은 묶음을 눌러도 주변 상황에 따라 목록이 열렸다 말았다 한다 —
**누른 것에 대한 반응은 예측 가능해야 한다.**

### 2.5 계산이 서지 않으면 예전대로

배율·화면 크기를 못 재면(`viewBoundsAt`이 `null`) 구성원만 담는다. 걸러낸 결과가 비어도
마찬가지다. 목록이 비어 뜨는 것보다 낫다.

## 3. 검증

| 무엇 | 결과 |
| --- | --- |
| `tsc -b --force` | 통과 |
| `eslint .` | 통과 |
| 단위 시험 115개 (범위·고르기 4개 추가) | 전부 통과 |
| 결함 e2e 65개 (묶음 목록 1개 추가) | 전부 통과 |
| `scripts/verify-frontend-csp-source.sh` | PASS |

단위 시험이 규칙을 못박는다 — 범위 계산(800×500 화면, 1px=1m이면 동서 800m), 화면 밖
제외, 가장자리 8% 여유(가운데에서 336m까지가 "보임"), 상한을 넘을 때 가까운 것부터 남기기.

e2e는 **최대 배율에서 시작**해 회귀를 만든다. 같은 자리에 둘(=한 묶음) + 4m 떨어진 하나를
두고 묶음을 누르면, 더 확대할 수 없어 셋이 모두 화면에 남는다 → 목록은 3건이어야 한다.
예전 코드에서는 2건이 나온다.

  살아 움직이게 하면 읽는 중에 줄이 바뀌고 조회도 그때마다 나간다 — 지금은 일부러 고정이다.
- 30건 상한에 걸려 잘려도 화면에 그 사실을 적지 않는다. 실제로 걸리는 일이 드물어 미뤘다.
