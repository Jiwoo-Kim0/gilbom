# 화면 타임존을 서울로 고정 작업내용

기간: 2026-08-06
범위: 프론트 전체의 시각 표시·입력(`src/shared/time/seoulTime.ts` + 25개 파일).
서버·DB는 그대로 UTC다.

관련 문서: [defect-schema.md](../../defect-schema.md)(`TIMESTAMPTZ`),
[결함-필터-UI-드롭다운_작업내용.md](결함-필터-UI-드롭다운_작업내용.md) §9.2(시작 날짜 입력)

> **담당 범위 참고:** 결함(내 몫) 외에 로봇·보고서·임무·감사·관리자·인증 화면의 시각
> 표시도 함께 바꿨다. 타임존은 화면 전체가 같은 기준이어야 의미가 있어 한 번에 처리했다.
> 각 화면의 **형식은 그대로** 두고 타임존만 박았다.

---

## 1. 무엇이 문제였나

층별 기준을 먼저 정리하면 이렇다.

| 층 | 기준 |
| --- | --- |
| DB | `TIMESTAMPTZ` — UTC 순간(instant) |
| 컨테이너 | `TZ: ${TZ:-UTC}` |
| API 응답 | Java `Instant` → `2026-08-04T02:00:00Z` |
| **화면 표시** | **브라우저 로컬 타임존** ← 문제 |
| **화면 입력** | **브라우저 로컬로 파싱** ← 문제 |

저장·전송은 순간이라 문제가 없다. 화면이 문제였다.

**표시**: `new Intl.DateTimeFormat('ko-KR', …)`과 `toLocaleString('ko-KR', …)`은 타임존을
주지 않으면 **보는 사람 기계 설정**을 쓴다. 같은 결함이 사람마다 다른 시각으로 찍힌다.

**입력**: `<input type="date">`는 `2026-08-03`, `<input type="datetime-local">`은
`2026-08-03T09:30`처럼 **타임존이 없는 값**을 준다. 그걸 `new Date(값)`으로 파싱하면 로컬로
해석돼 **조회 경계가 사람마다 달라진다.**

## 2. 무엇을 바꿨나

`src/shared/time/seoulTime.ts` 하나를 만들고 모든 자리에서 그걸 쓰게 했다.

| 함수 | 쓰임 |
| --- | --- |
| `SEOUL_TIME_ZONE` | 표시 formatter에 박는 상수 |
| `seoulDateTimeFormat(options)` | 서울로 고정된 `Intl.DateTimeFormat` |
| `seoulParts(date)` | 서울 기준 벽시계 값 — `getHours()` 같은 로컬 getter 대체 |
| `seoulInputToInstant(value)` | 타임존 없는 입력 → UTC ISO (서울로 해석) |
| `instantToSeoulInput(value)` | UTC → `datetime-local` 입력 값 |
| `instantToSeoulDateInput(value)` | UTC → `date` 입력 값 |

손댄 자리는 세 갈래다.

1. **표시 formatter 20곳** — `timeZone: SEOUL_TIME_ZONE`을 옵션에 넣었다(형식은 그대로).
2. **입력 → 순간 변환 4곳** — 결함·감사·임무 조회 쿼리, 보고서 기간 경계.
3. **직접 조립한 형식 3곳** — 결함 목록 표(`seoulParts`), 로봇 텔레메트리 입력 값,
   결함 상세의 "그날 하루" 보고서 기간.

## 3. 서버·컨테이너는 왜 그대로 두었나

`TZ: ${TZ:-UTC}`를 서울로 바꾸지 않았다.

- DB는 `TIMESTAMPTZ`로 **순간**을 저장한다. 타임존을 바꿔도 저장·비교 결과가 달라지지
  않는다(바뀌는 것은 로그·psql 표시뿐이다).
- 로그 시각이 KST로 바뀌면 Grafana·Loki 대시보드에서 기존 UTC 기준 눈금과 어긋난다.
  얻는 것보다 흔드는 것이 많다.
- 한국 날짜가 꼭 필요한 곳은 이미 서버가 명시한다 — 결함 코드
  (`INC-YYYYMMDD-…`)는 `ZoneId.of("Asia/Seoul")`로 일자를 뽑는다.

즉 **순간은 UTC로 다루고, 사람이 읽는 자리에서만 서울로 바꾼다.** 컨테이너 TZ까지
서울로 옮길지는 별도 판단이 필요하다(§6).

## 4. 함정 — 값 import는 `.ts` 확장자가 필요하다

새 모듈을 `'../../shared/time/seoulTime'`으로 들여왔더니 **단위 시험 4개가 깨졌다.**

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '…/shared/time/seoulTime'
  imported from …/features/robot/robotTelemetryStatistics.ts
```

단위 시험은 `node --experimental-strip-types --test`로 **소스를 직접** 불러서 돌린다.
Node의 ESM 해석은 확장자를 붙여야 한다. `vite`·`tsc`는 없어도 되므로 타입 검사와 lint는
통과하고, **시험만 깨진다.**

기존 소스가 두 방식을 섞어 쓰고 있어(`apiClient.ts` / `apiClient`) 눈치채기 어려웠다.
`import type`은 런타임에 지워져 확장자가 없어도 되기 때문에 그렇게 굳은 것으로 보인다.
**값 import는 `.ts`를 붙인다**가 안전한 규칙이다.

## 5. 확인한 것

**브라우저 타임존을 뉴욕(`America/New_York`)으로 두고** 결함 목록을 열었다. 서울 고정이
안 됐다면 값이 다르게 나온다.

| 서버가 준 값 | 기대(서울) | 뉴욕 로컬이었다면 |
| --- | --- | --- |
| `2026-08-04T02:00:00Z` | `08.04 11:00` ✅ | 08.03 22:00 |
| `2026-08-05T16:00:00Z` | `08.06 01:00` ✅ (날짜가 넘어간다) | 08.05 12:00 |

시작 날짜에 `2026-08-03`을 넣으면 조회가 `from=2026-08-02T15:00:00.000Z`로 나갔다 —
**서울 자정**이다(뉴욕 자정이면 `2026-08-03T04:00Z`가 됐을 것이다).

단위 시험 9개를 새로 붙였다(총 78 pass). 기대값을 서울 기준으로 못박아 적었으므로
**구현이 로컬로 돌아가면 KST가 아닌 기계에서 바로 깨진다.** `resolvedOptions().timeZone`도
확인해, 옵션을 넘겨도 타임존이 덮이지 않는 것을 지킨다.

`tsc -b`·`eslint`·`verify-frontend-csp-source.sh` PASS.

## 6. 남은 것

### 내 몫

- 없다.

### 팀 판단이 필요한 것

- **컨테이너 `TZ`를 서울로 옮길지**(§3). 지금은 UTC다. 로그를 KST로 읽고 싶으면 바꿀 수
  있지만 Grafana·Loki 대시보드 눈금과 함께 봐야 한다.
- 서버가 문자열로 만들어 내려주는 시각이 있다면(보고서 본문 등) 그쪽은 이번 범위 밖이다.
  현재 결함·로봇 API는 모두 `Instant`라 해당 없다.
