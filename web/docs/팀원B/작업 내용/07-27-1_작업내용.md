# 07/27-1 작업 내용

> 담당: 팀원 B — 로봇 통신·임무·실시간 관제  
> 작업일: 2026-07-27  
> 우선순위: 로봇 MQTT 통신, Credential·Telemetry DB, 외부 로봇 PC 연동

## 1. 오늘 확정한 범위

로봇 통신을 우선하기 위해 팀원 B 전체 DB를 한 번에 만들지 않고, 다음 네
테이블만 Flyway V5에 먼저 작성하기로 결정했다.

| Schema | 테이블 | 역할 |
|---|---|---|
| `robot` | `robot` | Credential과 Telemetry가 참조하는 로봇 기준정보 |
| `robot` | `robot_credential` | MQTT Credential 발급·활성·실패·만료·폐기 상태 |
| `telemetry` | `robot_telemetry` | GPS·배터리·온도 등 MQTT Telemetry 이력 |
| `telemetry` | `robot_current_state` | 실시간 관제에 사용하는 로봇별 최신 상태 |

`robot_credential`은 단독으로 만들 수 없으므로 FK 대상인 `robot.robot`을 최소
기준정보 테이블로 함께 포함했다.

이번 V5에서 제외한 범위:

- `robot_boot_session`
- 순찰 구역과 임무
- 로봇 명령과 명령 결과
- 상태 변경 이력
- Battery·Safety·Mission Event
- Mission FK와 Boot Session FK
- Credential 발급 REST API
- 동적 Mosquitto Credential Provisioner

제외한 테이블과 FK는 요구사항 검수 후 V6 이상의 새 migration으로 추가한다.
한 번 적용한 V5는 수정하지 않는다.

## 2. Flyway V5 구현

작성 파일:

```text
backend/src/main/resources/db/migration/
└─ V5__create_robot_credential_and_telemetry_schema.sql
```

### 2.1 Robot

- 내부 PK는 UUID를 사용한다.
- `robot_code`는 MQTT username, Topic, Payload의 로봇 식별자로 사용한다.
- `robot_code`와 `serial_number`는 중복을 허용하지 않는다.
- 최초 운영 상태는 `PROVISIONING`이다.
- 등록자는 Request Body가 아닌 인증된 관리자 ID를 사용한다.
- 물리 삭제 대신 운영 상태 변경을 전제로 runtime `DELETE` 권한을 부여하지 않는다.

### 2.2 Robot Credential

- MQTT 비밀번호 원문은 DB에 저장하지 않는다.
- Mosquitto 호환 `secret_hash`와 SHA-256 `secret_fingerprint`만 저장한다.
- Credential 상태는 다음 값으로 제한한다.

```text
PENDING
ACTIVE
REVOKED
EXPIRED
FAILED
```

- 로봇·Credential 종류별 version을 1부터 증가시킨다.
- 같은 로봇에는 `ACTIVE` MQTT Password를 하나만 허용한다.
- 만료 시각은 발급 시각보다 늦고 최대 180일 이내여야 한다.
- `REVOKED`에는 폐기자·폐기 시각·폐기 사유가 필요하다.
- `FAILED`에는 Secret이나 예외 원문이 아닌 제한된 오류 코드만 기록한다.
- password, hash, fingerprint는 API·감사 로그·일반 로그에 반환하지 않는다.

### 2.3 Robot Telemetry

- MQTT `message_id`를 PK와 멱등 키로 사용한다.
- `(robot_id, boot_id, seq)`를 UNIQUE로 제한한다.
- MQTT Schema Version은 `2.0`만 허용한다.
- `sampled_at`과 서버의 `received_at`을 분리한다.
- GPS는 PostGIS `GEOMETRY(POINT,4326)`로 저장한다.
- 위치·방향·속도·배터리·임무 집계 값에 범위와 상태 일관성 CHECK를 적용한다.
- 검증된 Secret 없는 Payload를 `raw_payload JSONB`로 보존한다.
- Telemetry 이력은 append-only로 취급하여 runtime에는 `SELECT`, `INSERT`만
  허용하고 `UPDATE`, `DELETE`는 허용하지 않는다.

`robot_boot_session`을 이번 범위에서 제외했으므로 `boot_id` 값은 보존하지만
아직 FK를 연결하지 않는다.

### 2.4 Robot Current State

- 로봇별 한 행만 유지하는 실시간 관제 read model이다.
- 연결 상태 기본값은 `OFFLINE`이다.
- State와 Telemetry의 기준시각과 `seq`를 분리해 저장한다.
- 오래된 메시지가 최신 상태를 덮지 않도록 서비스 UPSERT 조건에서 비교한다.
- 최신 GPS가 유효하지 않더라도 마지막 유효 위치는 유지할 수 있도록 설계했다.
- 현재 상태는 lifecycle 갱신이 필요하므로 runtime `UPDATE`를 허용한다.

## 3. DB 검증 결과

실행 중인 개발 DB에는 V5를 영구 적용하지 않고, PostgreSQL transaction 안에서
migration과 smoke test를 실행한 뒤 전부 rollback했다.

검증 결과:

- 네 테이블만 생성되는지 확인
- Robot·Credential·Current State·Telemetry 정상 INSERT 확인
- Robot FK와 관리자 FK 확인
- Telemetry `(robot_id, boot_id, seq)` 중복 차단 확인
- 유효 GPS인데 좌표가 없는 데이터 차단 확인
- 활성 MQTT Credential 중복 차단 확인
- Credential 최대 180일 만료 제한 확인
- Runtime Role의 Schema `CREATE` 금지 확인
- Telemetry 이력 `UPDATE`, `DELETE` 금지 확인
- Current State와 Credential `UPDATE` 허용 확인
- 검증 transaction rollback과 임시 Schema 제거 확인
- Backend 전체 Gradle 테스트 성공

```text

Runtime DML and least-privilege contract: PASS
```

재사용 가능한 DB 검증 스크립트도 V5 기준으로 갱신했다.

## 4. 외부 로봇 PC 통신 방식 결정

Broker PC와 로봇 역할을 하는 팀원 PC가 서로 다른 Wi-Fi를 사용하므로, 오늘
단기 통합에는 공유기 포트포워딩보다 ngrok TCP를 사용하기로 했다.

통신 경로:

```text
팀원 로봇 PC
→ ngrok TCP endpoint
→ Broker PC의 ngrok agent
→ 127.0.0.1:8883
→ Mosquitto
→ Backend MQTT Adapter
```

선택 이유:

- 공유기 관리자 설정과 공인 IP 고정이 필요하지 않다.
- CGNAT 환경에서도 outbound tunnel을 만들 수 있다.
- Broker의 Docker port를 계속 localhost에만 제한할 수 있다.
- 하루 단위 통합 테스트의 시작·종료가 간단하다.

장기 운영은 ngrok이나 가정용 포트포워딩이 아니라 EC2 운영 Broker와 정식
인증서를 사용한다.

## 5. ngrok과 MQTT TLS 구성

ngrok TCP가 MQTT byte stream을 전달하더라도 MQTT Client의 Broker 인증서
검증은 유지한다. `tls_insecure` 또는 hostname 검증 해제는 사용하지 않는다.

ngrok hostname이 Broker 인증서의 DNS SAN과 일치하도록 다음 설정을 추가했다.

```dotenv
MQTT_BIND_ADDRESS=127.0.0.1
MQTT_LAN_IP=
MQTT_PUBLIC_HOSTNAME=<ngrok TCP hostname>
```

예를 들어 ngrok 주소가 다음과 같다면:

```text
tcp://0.tcp.ap.ngrok.io:12345
```

`.env`에는 hostname만 저장한다.

```dotenv
MQTT_PUBLIC_HOSTNAME=0.tcp.ap.ngrok.io
```

`mqtt-init`은 기존 Broker 인증서에 이 hostname이 없을 때 Broker 인증서만
재발급한다. 로컬 CA는 재사용하므로 팀원이 신뢰할 CA는 동일하게 유지된다.

임시 인증서 발급 검증에서 다음 SAN이 모두 포함되는 것을 확인했다.

```text
DNS:mosquitto
DNS:localhost
IP:127.0.0.1
선택한 LAN IP
선택한 ngrok hostname
```

## 6. Backend 실행 방식

Backend는 로컬 실행과 Docker 실행을 모두 지원한다. ngrok 공개 주소는 외부
로봇 PC만 사용하며, Backend는 자신과 같은 PC의 Mosquitto에 직접 연결한다.

| 구분 | Spring Profile | Backend의 MQTT Broker | CA 경로 |
|---|---|---|---|
| Backend 로컬 실행 | `local` | `ssl://localhost:8883` | 로컬 파일 경로 |
| Backend Docker 실행 | `local,docker` | `ssl://mosquitto:8883` | 컨테이너 마운트 경로 |
| 외부 로봇 PC | 해당 없음 | ngrok hostname과 할당 port | 전달받은 로컬 CA 경로 |

### 6.1 권장: Backend 로컬 실행

오늘 통합에서는 DB와 Mosquitto만 Docker로 실행하고 Backend는 IDE 또는 Gradle로
직접 실행한다.

먼저 `web/.env`에 DB와 MQTT 컨테이너용 로컬 Secret을 설정하고 필요한
컨테이너만 실행한다.

```powershell
cd C:\ssafy\SSAFY-TASK\web
docker compose up --build --detach db mqtt-init mosquitto
```

`web/backend/.env.example`을 `web/backend/.env`로 복사하고 실제 로컬 값은
ignored `.env`에만 입력한다.

```dotenv
SPRING_PROFILES_ACTIVE=local

SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/gilbom
SPRING_DATASOURCE_USERNAME=gilbom_app
SPRING_DATASOURCE_PASSWORD=<로컬 Runtime DB 비밀번호>
SPRING_FLYWAY_USER=gilbom_flyway
SPRING_FLYWAY_PASSWORD=<로컬 Flyway DB 비밀번호>

MQTT_BROKER=ssl://localhost:8883
MQTT_CLIENT_ID=gilbom-local-ide
MQTT_USERNAME=gilbom
MQTT_PASSWORD=<Backend MQTT 비밀번호>
MQTT_TRUST_CERTIFICATE=../infra/mosquitto/local/runtime/certs/local-ca-cert.pem
```

Backend 작업 디렉터리에서 실행한다.

```powershell
cd C:\ssafy\SSAFY-TASK\web\backend
.\gradlew.bat bootRun
```

IntelliJ에서 실행할 때 working directory가 `web/backend`가 아니라면
`MQTT_TRUST_CERTIFICATE`를 절대 경로로 지정한다. V5는 이 로컬 Backend가
기동하면서 Docker PostgreSQL에 Flyway로 적용한다.

### 6.2 선택: Backend Docker 실행

Backend까지 Docker로 통합 실행할 때는 `web/.env`에 필요한 값을 설정한 뒤
다음처럼 실행한다.

```powershell
cd C:\ssafy\SSAFY-TASK\web
docker compose up --build --detach db mqtt-init mosquitto backend
```

Docker Backend 설정:

```text
MQTT_BROKER=ssl://mosquitto:8883
MQTT_TRUST_CERTIFICATE=/app/config/mqtt/certs/local-ca-cert.pem
```

Compose가 위 연결정보와 CA volume mount를 Backend 컨테이너에 전달한다.

### 6.3 두 방식의 공통 원칙

- 로컬 Backend와 Docker Backend를 동시에 실행하지 않는다.
- 두 Backend가 같은 `MQTT_CLIENT_ID`를 사용하지 않는다.
- Backend는 ngrok 공개 주소로 우회하지 않고 로컬 Mosquitto에 직접 연결한다.
- 외부 로봇만 ngrok endpoint를 사용한다.
- Backend와 외부 로봇은 서로 다른 MQTT username/password를 사용한다.
- 실제 Secret은 `web/.env`, `web/backend/.env`, 로그, 문서에 복사하지 않는다.

## 7. 실제 통신 실행 순서

### 7.1 ngrok tunnel 시작

가능하면 팀원 PC의 공인 egress IP 하나만 허용한다.

```powershell
ngrok tcp 8883 --cidr-allow=<TEAMMATE_PUBLIC_IP>/32
```

ngrok authtoken은 저장소나 문서에 기록하지 않는다.

### 7.2 Broker 인증서와 Mosquitto 재생성

ngrok hostname을 `.env`의 `MQTT_PUBLIC_HOSTNAME`에 넣은 뒤 실행한다.

```powershell
cd C:\ssafy\SSAFY-TASK\web
docker compose up --build --detach --force-recreate mqtt-init mosquitto
```

### 7.3 팀원 로봇 PC에 전달

```text
MQTT_HOST=<ngrok hostname>
MQTT_PORT=<ngrok 할당 port>
MQTT_USERNAME=<robot_id와 동일>
MQTT_PASSWORD=<해당 로봇의 비밀번호>
MQTT_CA_CERT=<local-ca-cert.pem의 로봇 PC 내 경로>
```

전달 가능한 파일:

```text
infra/mosquitto/local/runtime/certs/local-ca-cert.pem
```

전달하거나 커밋하면 안 되는 항목:

```text
local-ca-key.pem
local-broker-key.pem
runtime/passwd
Backend MQTT 비밀번호
ngrok authtoken
```

## 8. MQTT 접근 제어

- MQTT username은 `robot_id`와 같아야 한다.
- 로봇은 자기 `tbs/v2/robots/{robot_id}/...` Topic만 사용할 수 있다.
- Telemetry는 QoS 0, State·Presence·Command Result는 QoS 1을 사용한다.
- 로봇은 자기 Telemetry·State·Event·Command Result만 발행한다.
- 로봇은 자기 Command Request와 Ingest Receipt만 구독한다.
- Backend는 로봇 비밀번호를 공유하지 않고 별도 `gilbom` 계정을 사용한다.
- MQTT 평문 `1883`은 외부에 열지 않는다.

## 9. 현재 미실행·후속 작업

현재까지 구현과 로컬 검증은 완료했지만 다음 작업은 아직 실행하지 않았다.

- 실제 ngrok TCP tunnel 개방
- ngrok 실제 hostname을 `.env`에 반영
- 실제 Broker 인증서·Mosquitto 재생성
- 팀원 PC에 CA와 로봇 Credential 전달
- 다른 Wi-Fi에서 TLS handshake 확인
- 로봇 → Broker → Backend Telemetry 수신 확인
- Backend → Broker → 로봇 Command 수신 확인
- 로봇 → Broker → Backend Command Result 확인
- 다른 로봇 Topic ACL 거부 확인
- V5를 실제 개발 DB에 Flyway로 적용
- MQTT Handler에서 Telemetry INSERT·Current State UPSERT 구현
- Credential Provisioner와 발급·폐기 API 구현

DB에 Credential 행을 INSERT하는 것만으로 Mosquitto 계정이 생성되는 것은 아니다.
동적 Provisioner가 구현되기 전까지는 `mqtt-init`의 테스트 로봇 계정을 사용하거나
제한된 운영 절차로 `mosquitto_passwd`를 관리해야 한다.

## 10. 로봇 등록 API

구현 경로:

```text
POST /api/v1/robots
```

적용 내용:

- Request는 `robotName`, `serialNumber`만 받는다.
- `ROBOT_REGISTER` 권한, 서버 세션 인증, CSRF, UUID `Idempotency-Key`를 확인한다.
- `registered_by`는 Request가 아닌 인증된 관리자 username으로 DB에서 결정한다.
- `robot_code_sequence`로 `RBT-001` 형식의 `robotCode`를 서버가 생성한다.
- `robot.robot(PROVISIONING)`과 `telemetry.robot_current_state(OFFLINE)`을 생성한다.
- `ROBOT_REGISTERED` 감사 로그와 멱등 응답을 같은 트랜잭션에 저장한다.
- 중복 Serial Number는 `409 ROBOT_SERIAL_NUMBER_CONFLICT`로 응답한다.
- MQTT Credential은 이 API에서 생성하거나 반환하지 않는다.
- OpenAPI operation과 Request/Response schema를 함께 갱신했다.
- `robot/controller`의 MockMvc JUnit으로 성공, 인증, 권한, CSRF, 멱등키,
  입력 검증, 중복 충돌을 검증한다.
- `robot/integration`의 Testcontainers JUnit으로 PostGIS와 Flyway V1~V5를 실제
  적용한 뒤 HTTP → Robot → Current State → Audit → 멱등 replay 전체 흐름을 검증한다.
- 통합 테스트 관리자 비밀번호는 Argon2 hash로만 DB에 저장되는지 확인한다.
- 로봇 등록 단계에서는 `robot_credential`이 생성되지 않는지 확인하여 등록과
  Credential 발급의 책임 경계를 유지한다.

로봇 측 로컬 테스트 설정 예제는 다음 경로에 추가했다.

```text
web/test/mqtt/로봇-config.local.env.example
```

Broker는 우선 `localhost:8883`, 로봇 식별자는 `RBT-001`, MQTT v2 발행·구독
Topic을 사용한다. 실제 파일 `로봇-config.local.env`와 `MQTT_PASSWORD`는
`.gitignore` 대상이며 저장소에 커밋하지 않는다.

## 11. 팀원 B DTO 패키지 분류

팀원 B의 `com.gilbom.robot` 영역에만 다음 DTO 구조를 적용했다.

```text
robot/data/
├─ api/
│  ├─ request/
│  └─ response/
├─ application/
│  ├─ command/
│  └─ result/
└─ mqtt/v2/
   ├─ inbound/
   ├─ outbound/
   └─ common/
```

- REST 입력과 출력은 `api/request`, `api/response`로 분리한다.
- Service 입력과 결과는 `application/command`, `application/result`로 분리한다.
- MQTT 방향은 Backend 기준으로 `inbound`, `outbound`를 사용한다.
- MQTT 공통 Interface와 Enum은 `common`에 둔다.
- `common`, `auth`, `security`, `report` 등 다른 팀원 영역의 DTO는 이동하지 않았다.
