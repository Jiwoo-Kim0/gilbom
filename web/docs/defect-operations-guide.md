# 결함 운영 가이드

시연 진행자와 평가자를 위한 한 장짜리 설명이다. **화면에서 무엇을 누를 수 있고, 왜
그렇게 동작하는가**만 담는다. 스키마와 API는 [defect-schema.md](defect-schema.md)와
[openapi-v1.yaml](openapi-v1.yaml)에 있다.

---

## 1. 결함은 어떻게 생기나

```
로봇(Jetson) --MQTT--> 서버 --> 결함 생성 --SSE--> 관리자 화면
```

로봇이 점자블록 이상을 탐지하면 incident 이벤트를 올린다. 서버가 그것을 결함으로
만들고, 열려 있는 관리자 화면에 **새로고침 없이** 바로 뜬다 — 알림·목록·지도가 함께
갱신된다.

### 결함이 만들어지지 않는 두 경우

탐지가 올라와도 결함이 안 생기는 경우가 있다. 버려지는 것이 아니라
`defect.incident_ingestion_issue`에 사유와 함께 남는다.

| 사유 | 뜻 |
| --- | --- |
| `INVALID_GPS` | 로봇이 위치를 신뢰할 수 없다고 보고했다(`location.valid = false`) |
| `PATROL_AREA_UNRESOLVED` | 보고된 구역이 등록된 순찰구역에 매칭되지 않는다 |

**시연 중 결함이 0건이면 이 두 가지를 먼저 의심한다.** 화면에는 "아무 일도 일어나지
않음"으로 보여서 원인을 알기 어렵다.

```sql
SELECT created_at, issue_type, zone_id
FROM defect.incident_ingestion_issue
ORDER BY created_at DESC LIMIT 5;
```

## 2. 같은 자리를 다시 탐지하면

새 결함을 만들지 않고 **기존 결함에 관측을 더한다.** 카드의 "누적 N회"가 늘어난다.

조건 넷이 **모두** 맞아야 한다.

- 반경 **2m** 이내
- 같은 결함 유형
- 같은 블록 타입
- 같은 순찰구역

하나라도 어긋나면 별개 결함이 된다. GPS 오차가 2m를 넘으면 같은 블록이라도 나뉠 수
있는데, 그때는 사람이 **수동 병합**으로 합친다(목록에서 여러 건 선택 → 병합).

### 수리 완료된 결함은 예외다

`완료(RESOLVED)` 상태인 결함은 자동 병합 후보에서 빠진다. **수리한 자리에서 다시
탐지되면 새 결함**이다. 옛 결함에 관측만 붙이면 "고쳤는데 또 났다"는 사실이 관측
횟수 뒤로 숨기 때문이다.

`오탐`·`반려`는 빠지지 않는다. 판단만 바뀐 것이고 대상은 계속 거기 있어서, 순찰마다
같은 것이 새 결함으로 쌓이면 목록이 잠긴다.

## 3. 처리 상태

| 상태 | 뜻 |
| --- | --- |
| 신규 | 방금 탐지됨. **적재 시점에만 붙고 사람이 지정할 수 없다** |
| 접수 | 확인함 |
| 처리 중 | 조치 진행 중 |
| **완료** | 조치 끝. 처리 결과 필수 |
| **오탐** | AI 오검출로 판정 |
| **반려** | 조치하지 않기로 함 |

굵은 셋이 **종결 상태**다.

### 전이는 자유롭다 (2026-08-05 변경)

`신규`를 뺀 다섯 상태 사이를 **어느 방향으로든** 바꿀 수 있다. 단계에 묶여 있지
않다.

> **왜 그런가.** 현장에서는 판단이 자주 뒤집힌다. 반려한 결함이 민원으로 다시
> 올라오고, 완료 처리한 자리가 재점검에서 문제로 나온다. 전이를 한 방향으로 묶으면
> 그때마다 결함을 새로 만들어야 하고, 그러면 **같은 자리의 이력이 끊긴다.**
>
> 잘못 누른 것을 되돌릴 수 없는 것도 문제였다. 종결은 "끝"이 아니라 **"지금은 더 볼
> 것이 없다"**는 표시로 다룬다.

바뀔 때마다 **변경 이력**에 누가·언제·왜가 남는다. 사유는 필수다. 되살리는 것이
쉬워진 대신 **모든 판단이 기록으로 남는다.**

### 종결 상태가 뜻하는 것

두 가지뿐이다.

1. **처리 결과**를 가질 수 있다 (종결이 아닌 상태에는 지정할 수 없다)
2. **결함 내용 수정이 잠긴다** — 유형·심각도·구역 등

내용을 고치려면 **처리 상태를 먼저 되살린 뒤** 수정한다. 카드가 그렇게 안내한다.

### 처리 결과

`완료`에는 반드시 하나 지정한다. 다른 종결 상태에는 선택이다.

수리 완료 · 청소 완료 · 중복 · 재점검 필요 · 해당 없음

## 4. 심각도는 자동으로 매겨진다

로봇이 보낸 **파손 면적 비율**을 점수(0~100)로 바꾸고 구간으로 나눈다.
규칙 버전은 `DAMAGE_RATIO_V1`이다.

| 점수 | 심각도 |
| --- | --- |
| 75 이상 | 심각 |
| 50 이상 | 높음 |
| 25 이상 | 보통 |
| 25 미만 | 낮음 |

**파손 면적이 없으면 임의 점수를 만들지 않는다.** 대신 `보통`으로 두고 검토 대상으로
표시한다 — 근거 없는 숫자를 만드는 것보다 "판단할 수 없음"을 남기는 편이 낫다.

사람이 결함 수정에서 심각도를 바꿀 수 있고, 그 경우도 이력에 남는다.

## 5. 결함 유형과 사람의 교정

| 유형 | 로봇이 올릴 수 있나 |
| --- | --- |
| 파손 | **가능** |
| 유실 | **가능** |
| 설치 이상 | 불가 — 사람만 지정 |
| 기타 이상 | 불가 — 사람만 지정 |

MQTT 계약이 `DAMAGED`·`MISSING` 둘만 받는다. **AI는 두 가지만 판정하고, 나머지는
관리자가 보고 재분류한다.**

결함 수정에서 **네 유형 사이를 아무 방향으로나** 바꿀 수 있다. 유형에는 전이 규칙이
없다. AI가 `파손`이라 한 것을 `기타 이상`으로 내리는 것도 된다. 사유는 필수다.

## 6. 화면에서 할 수 있는 것

| 위치 | 동작 |
| --- | --- |
| 목록·지도 | 상태·유형·심각도·기간·신뢰도로 거르기, 검색 |
| 지도 마커 | 눌러서 상세 카드 열기. 가까운 것끼리 묶이며 숫자를 누르면 확대 |
| 상세 카드 | 사진(AI 검출 영역 표시), 위치, 시각, 관측 이력, 변경 이력 |
| 상세 카드 | 처리 상태 변경, 결함 수정, 리포트 생성 |
| 목록 | 여러 건 선택 → 수동 병합 |

**기본 필터는 미종결만 보여준다.** 종결된 결함은 조치할 것이 없어 지도와 목록을
가리기만 한다. 필터에서 체크하면 다시 보인다.

---

## 7. 보고서

결함 상세의 **"리포트 생성"**을 누르면 그 결함 한 건에 대한 보고서를 LLM이 만들고,
완료되면 보고서 상세로 이동한다. 최대 30초 걸린다.

- **근거는 그 결함 하나로 고정된다.** 기간 전체를 근거로 하는 보고서는 만들지 않는다
- **통계는 그날 하루 전체**를 집계한다. 결함 하나만 세면 "결함 수 1"이 되어 의미가 없다
- 사진이 있으면 **이미지도 함께** LLM에 전달된다. 없으면 텍스트만으로 만든다
- 발행 뒤 사람이 손봐야 하면 보고서 상세에서 **새 버전**으로 편집한다

## 8. 시연 중 문제가 생기면

| 증상 | 먼저 볼 것 |
| --- | --- |
| 결함이 안 올라옴 | §1의 적재 실패 사유 조회 |
| 화면이 실시간으로 안 바뀜 | 상단의 `실시간 연결됨` 표시. `연결이 끊겨 재연결 중`이면 잠시 대기 |
| 사진이 안 보임 | 이미지 없는 결함일 수 있다. 카드에 "연결된 이미지가 없습니다"로 뜨면 정상 |
| 지도가 안 뜸 | 브라우저 콘솔의 CSP 차단 메시지 확인 |
| 결함이 너무 많아 안 보임 | 기본 필터가 미종결만이므로, 종결을 체크했는지 확인 |

로봇 없이 결함을 만들어야 하면 `scripts/publish-dev-incident.py`를 쓴다.
사용법은 [지우-remaining-7days.md](jiw/지우-remaining-7days.md) §6.6에 있다.
